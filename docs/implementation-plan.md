# План: области наблюдения на странице с несколькими микрофронтами

Обновлено: 2026-09-13. Статус: **подключены селективная запись, Scenario v4, blur-only ввод, группы и общий ownership
dropdown**. Это следующий цикл после завершённого [spike](./spike/PLAN.md), а не пересмотр его результатов.

**Актуальный порядок по решению пользователя от 2026-09-13:** сначала этап 6 — удаление записанных действий с отменой,
затем авторская обратная связь для каждого действия. Оставшаяся оптимизация этапа 5 переносится в конец обязательных
работ MVP, после проверки этих функций. Уже выполненную оптимизацию сохраняем. Нумерация этапов оставлена для сохранения
ссылок; прежние списки следующих работ ниже отражают историю. Этап 7 остаётся необязательным расширением.

Новые вводные: интерфейс меняется редко; страница содержит несколько микрофронтов, обычно
`<microfrontend><some-mf>content</some-mf></microfrontend>`. Нужно наблюдать один небольшой MF или выбранный набор,
подключать/отключать наблюдение, а позднее — при необходимости блокировать взаимодействие с отдельными MF. Driver.js не
используется. Формы demo остаются на Taiga UI 4. Новые tracking-атрибуты/hooks в целевые формы не добавляются.

## Библиотека и приложения

Библиотека работает **без UI**: наблюдает DOM, описывает и находит цели, проверяет действия и условия, отдаёт состояние
и события через программный API. Angular-интеграция отвечает за DI и lifecycle, без визуальных компонентов.

**Админка** — отдельное приложение для записи и редактирования заданий, подсказок, значений, веток и completion. **Режим
ученика** — существующий рабочий интерфейс с автоматической проверкой. При входе в тренировку интеграция загружает
сценарий и запускает наблюдение без кнопки «Начать обучение» и отдельной панели. Подсказки отображает приложение по
событиям/состоянию библиотеки; renderer подсказок не входит в ядро.

Наблюдение ученика не создаёт новый авторский сценарий. Постоянное сохранение журнала прохождения — отдельная политика
приложения. При выходе интеграция останавливает сеанс и освобождает ресурсы. Повторный вход не дублирует listeners. До
загрузки сценария проверка не готова; прошлые действия не засчитываются задним числом. После загрузки запуск
автоматический. Отсутствующий MF ожидается, ошибка загрузки сообщается приложению.

В demo автоматический запуск ученика уже подключён. Панель заданий показывает результаты проверки библиотеки; ручное
управление сеансом и JSON находятся в дополнительных настройках.

## Порядок действий: группы ожиданий

Уточнение 2026-09-12: механизм библиотеки не знает о процедурах, плеере, поиске или конкретных микрофронтах. **Область
наблюдения** ограничивает доступ к DOM; **группа ожиданий** определяет, какие задания сейчас проверяются; **переход**
задаёт явное условие смены группы. Эти понятия независимы: одна область может содержать несколько групп, одна группа —
цели нескольких разрешённых областей. Имена host-тегов и маршрутов задаёт интеграция, а не ядро.

Экран формы, вкладка или часть рабочего процесса могут быть представлены группой, но физический экран не является
обязательной сущностью библиотеки. Сценарий без смены контекста использует одну группу. Видимость ограничивает
доступность цели внутри группы и не определяет всю группу автоматически. Прокрутка не переключает контекст;
сохранившиеся видимые поля прошлого контекста не включаются в новую группу автоматически.

Порядок заполнения полей администратором не задаёт порядок для ученика. В активной группе доступные независимые ожидания
можно выполнять в любом порядке. Timestamp и sequence записи сохраняются для диагностики и корректного intent/commit, но
не становятся зависимостями полей.

### Ожидания и переходы

Каждое подтверждённое действие сопоставляется с доступными ожиданиями активной группы по области, элементу, типу и
значению. Единственное надёжное соответствие учитывается; несколько равноправных соответствий дают ambiguity. Неактивные
группы не получают действия задним числом. Невидимая или ещё не появившаяся цель не готова к взаимодействию; её
отсутствие не доказывает выполнение и не является ошибкой заполнения ученика.

Повторные исправления одного поля объединяются в итоговое ожидаемое значение только внутри подтверждённой группы.
Правильное → неправильное значение делает ожидание невыполненным. Старое совпадение и незавершённый черновик не
разрешают переход. Одно событие не закрывает несколько неоднозначных ожиданий.

Переход задаётся сценарным действием, prerequisites и наблюдаемым postcondition. До его зачёта должны быть выполнены
обязательные ожидания группы и явно заданные зависимости. После действия runtime ждёт postcondition следующей группы;
сам click, исчезновение кнопки или изменение DOM недостаточны. Библиотека не классифицирует переход по тексту кнопки,
HTTP endpoint, названию компонента или внутреннему состоянию приложения. Prerequisites проверяются на intent, пока
исходный контекст ещё доступен. Поколение активной группы защищает от запоздалых commits прежнего контекста.

Библиотека не блокирует взаимодействия приложения на этом этапе. Если пользователь изменил интерфейс без выполнения
prerequisites, переход в обучении не засчитывается и интеграция получает объяснение. Способ возврата/восстановления
определяет приложение; отсутствие нужного DOM нельзя исправлять фиктивным завершением задания.

### Локальные зависимости

Сценарий может потребовать одно действие перед другим, сохраняя свободный порядок независимых полей. Например, открытие
справки может быть обязательным перед переходом. Это обычное ожидание с условием появления содержимого и, при
необходимости, закрытия; специального типа «справка» в ядре не требуется. DOM подтверждает наблюдаемые действия, а не
факт прочтения или понимания текста.

Открытие/закрытие popup, сообщение валидации, disabled-состояние или появление условного поля не переключают группу
автоматически. Условные ожидания имеют собственную доступность и обязательность в активной ветке. Пример с несколькими
формами и кнопкой перехода проверяется в demo, но не задаёт структуру библиотечного API.

### Определение групп при записи

Recorder сохраняет действия и наблюдаемые состояния. Authoring может предложить группировку по областям наблюдения,
семантическому контексту и изменениям состава доступных целей. Это универсальные эвристики, а не распознавание
конкретного приложения. Предложения проверяет автор: он объединяет/разделяет группы и назначает явные условия входа,
переходы и зависимости. Каждый click или DOM mutation не считается границей; неоднозначные случаи требуют уточнения.
Tracking-атрибуты и hooks в целевой интерфейс не добавляются.

Похожее поле в другой группе не объединяется с прежним только по label. Если DOM не позволяет отличить контексты или
бизнес-сущности, сценарий требует уточнения либо отдельного интеграционного адаптера. Ядро не угадывает скрытое
состояние.

Реализован Scenario v4: группы независимых ожиданий, явные зависимости и переходы. Runtime v2/v3 сохраняет
последовательную семантику. Импорт не мигрирует порядок автоматически; новый черновик из записи v3 создаёт v4. В текущем
редакторе автор отмечает границы вручную и проверяет предлагаемую цель подтверждения; автоматических предложений по
кластеризации DOM пока нет.

## Подтверждение текстового ввода

Для администратора и ученика действует одно правило: события input обновляют внутренний черновик, а сравнение текстового
значения с ожиданием выполняется при blur — выходе из поля. Пауза при наборе не подтверждает ввод. Одно редактирование
до выхода даёт не более одного semantic input с итоговым значением; повторный выход без изменений не создаёт ещё одно
действие. Нативный change не должен дублировать blur или преждевременно засчитывать текст.

После начала нового редактирования ранее подтверждённое поле считается изменяемым: старое совпадение не позволяет
завершить тренировку. При этом каждый символ не порождает действие/подсказку об ошибке. На blur подтверждается
актуальное значение с учётом синхронной нормализации контрола; последующие программные изменения остаются отдельными
state updates, а не действиями ученика. Незавершённый IME-ввод не подтверждается.

Checkbox/radio/select подтверждаются отдельным событием изменения/выбора. Для combobox различаются текст поиска и
выбранная option: blur внутреннего input при переходе в popup сам по себе не доказывает выбор.

Submit по Enter без blur, удаление поля и выход из тренировки не должны молча подтверждать черновик. На первом этапе нет
автоматического зачёта в этих случаях: runtime сообщает о неподтверждённом вводе. Если понадобится подтверждение через
submit, оно вводится отдельной явной политикой и проверяется до обработки completion, без зачёта каждого Enter.

Реализовано: input/change обновляют черновик; только полученный blur разрешает semantic input. Таймер inputIdleMs
удалён. Клик, Enter, navigation и stop сами не подтверждают текст. Синхронная blur-нормализация включается в значение;
программная подмена между вводом и blur отменяет черновик с диагностикой. Stop/navigation/unmount сохраняют
неподтверждённый ввод только в наблюдаемых состояниях. Для IME требуется завершённая composition перед blur.

ElementRecorder.hasUncommittedInput и RuntimeSnapshot.uncommittedInput сообщают приложению о черновике. Он блокирует
completion, не создавая ошибок на каждый символ. В v4 редактирование снимает прежний зачёт до blur, а изменение
подтверждённого значения сервером делает ожидание невыполненным. Старые JSON с commit:idle/change остаются читаемыми;
новый recorder создаёт текстовые действия с commit:blur.

## Текущий Angular и обязательный подход к реализации

Обновление отложено пользователем. Реализация начинается на установленном Angular 19.2.25, TypeScript 5.8.3 и Taiga
UI 4. Не менять зависимости ради этого этапа. Использовать доступные API установленной версии и сохранять текущий
bootstrap.

- Для внешней админки и demo: standalone components/directives, `OnPush` для собственной UI-композиции,
  `input()`/`output()`, signal queries, встроенные `@if`/`@for` с устойчивым track. MF и формы создаются Angular
  templates, не через innerHTML/ручной DOM.
- Состояние библиотечного сеанса и policies — `signal`, производные значения — `computed`, наружу readonly signals.
  `effect` только для синхронизации с внешним API и с cleanup; не строить цепочки копирования производного состояния.
- Registry, EventHub и coordinator — Angular services с `inject()` и типизированными DI tokens конфигурации.
  Session-scoped providers на уровне training shell/маршрута; один EventHub на document в пределах этой интеграции.
  `providedIn: 'root'` сам по себе не обеспечивает singleton между независимыми Angular applications/MF.
- `DestroyRef` и `takeUntilDestroyed` для соответствующего lifecycle. Отключение области освобождает ресурсы сразу, не
  только при уничтожении всего Angular injector. Явные команды start/stop/enable/disable остаются необходимыми.
- RxJS для потоков событий, HTTP и отмены; `toSignal`/`toObservable` на границах с UI, без повторных subscriptions из
  getters/templates и без превращения каждого DOM event в обновление всей панели. XState остаётся источником состояния
  сценария, Angular facade предоставляет его snapshot; не дублировать машину второй системой signals.
- Формы внешней админки и demo — typed Reactive Forms и `HttpClient`; экспериментальные формы/API не вводить ради
  новизны. DOM-наблюдатель не читает FormGroup соседнего MF. Обновления формы, отражаемые в UI, явно уведомляют Angular.
- Цель — zoneless-compatible реализация. Проверять реальный bootstrap и Taiga, а не считать, что версия сама убрала
  ZoneJS. Не использовать `NgZone.onStable` как наблюдатель чужого MF, `setTimeout` для ожидания Angular render и ручной
  detectChanges как стандартный способ обновления UI.
- Для готовности собственного DOM — render callbacks (`afterNextRender`), `ElementRef`/queries и `DOCUMENT` через DI.
  Для чужого DOM — изолированный browser adapter с MutationObserver, capture listeners и sampling properties: lifecycle
  одного Angular MF не сообщает обо всех изменениях соседнего. Native API здесь обоснован задачей; механическая замена
  на Renderer2 не делает наблюдение надёжнее. Новые directives/hooks на чужие поля не добавляются.
- Чистые matching/scoring и wire validation остаются TypeScript-функциями; Angular управляет композиционной частью,
  зависимостями и ресурсами. Не превращать каждый алгоритм в service без необходимости.
- Проверки Angular services/components — TestBed с настоящим DI/lifecycle и целевым режимом change detection; Playwright
  — браузерная семантика portals, MF и forms. Тест не должен маскировать отсутствие уведомления Angular принудительным
  detectChanges после каждой мутации. Прежние чистые unit tests resolver сохраняются.

Это условия приёмки каждого этапа, а не отдельная последующая «ангуляризация» готового JavaScript решения. Архитектура
предыдущего spike описывает существующий прототип; этот раздел определяет подход к новой реализации.

Основания: [Angular DOM APIs](https://angular.dev/guide/components/dom-apis),
[signals](https://angular.dev/guide/signals), [zoneless](https://angular.dev/guide/zoneless),
[style guide](https://angular.dev/style-guide). Документация latest может описывать более новую версию: совместимость
каждого используемого API сверяется с установленной версией Angular.

## Читаемость кода и документация

Обязательные требования пользователя **к коду библиотеки** для каждого этапа. Demo остаётся тестовым приложением; его
компоненты не нужно снабжать такими описаниями в рамках этой задачи:

- Понятные предметные имена, одна ответственность компонента/сервиса, небольшие методы и явный поток данных. Не
  сокращать код за счёт вложенных тернарных выражений, неочевидных флагов и универсальных абстракций без потребности.
- Ownership, observation и matching остаются в библиотеке. Внешние приложения вызывают API и отображают результат.
- В начале модуля/над классом библиотеки — описание назначения, входов, алгоритма, побочных эффектов и cleanup на
  русском. Это относится также к Angular services/adapters; визуальных компонентов в библиотеке нет.
- Комментарии объясняют порядок действий и причины решений. Меняется алгоритм — обновляется описание в том же коммите.
- Корневой [ARCHITECTURE.md](../ARCHITECTURE.md) — точка входа: назначение библиотеки, Mermaid-схемы, основные модули и
  направление зависимостей. Отдельно обозначать реализованные и запланированные части.
- На review каждого этапа проверять соответствие описаний коду и схем текущей реализации. Линтер помогает со стилем, но
  понятность алгоритма не заменяется формальным ограничением количества строк.

## Роль demo и основной пользовательский сценарий

Demo — испытательный стенд библиотеки. Его формы не оптимизируем специально ради показателей и не переводим
принудительно на zoneless. Требования к эффективности и zoneless-совместимости относятся к библиотеке и её
Angular-интеграции без UI. Demo содержит обычные реалистичные перерисовки и фоновые события; совместимость режимов
change detection проверяется отдельной конфигурацией тестов. Исходный режим приложения сохраняется, если обновление
пользователя не изменило его.

Основной вход в процедуру — **отдельный MF поиска процедур**:

1. Изначально на странице есть `<microfrontend><procedure-search-mf>…</procedure-search-mf></microfrontend>`. Плеера в
   DOM ещё нет, хотя его логическая область уже может быть включена в политику наблюдения.
2. Пользователь вводит запрос в **Taiga UI 4 combobox с поиском**, видит подходящие процедуры и выбирает вариант мышью
   либо клавиатурой. Это именно редактируемый combobox, не обычный select с фиксированным списком.
3. После подтверждённого выбора **ниже поиска** появляется отдельный
   `<microfrontend><procedure-mf>…</procedure-mf></microfrontend>`. Выбранная процедура автоматически открывается:
   загрузка, затем первая форма. Дополнительное нажатие «Новая процедура» для этого пути не требуется.
4. Пользователь заполняет форму; backend постепенно присылает новые поля и этапы, как в существующем плеере.
5. Выбор другой процедуры заменяет экземпляр плеера и начинает новую процедуру. Просто изменение поискового запроса не
   запускает новую процедуру. Очистка подтверждённого выбора закрывает плеер и освобождает его ресурсы.

Demo связывает поиск и плеер обычной коммуникацией через shell (Angular output/input или штатный сервис demo).
Библиотека наблюдения не подписывается на эту внутреннюю связь и не получает selectedProcedure/HTTP payload. Такая
коммуникация моделирует само приложение, а не hook для обучения.

В fixture предусмотреть несколько процедур с различающимся названием и проверяемым результатом открытия, фильтрацию
результатов, пустую выдачу, загрузку/ошибку поиска и задержку открытия. Если поиск выполняется через тестовый HTTP
backend, поздний ответ предыдущего запроса не должен заменять актуальную выдачу; ответ предыдущей выбранной процедуры не
должен обновлять новый плеер. Реалистичный lifecycle здесь важнее оптимизации demo.

Для recorder различать ввод поискового текста и **подтверждённый выбор процедуры**. Ввод точного названия сам по себе не
является select. Programmatic value update, отсутствие результатов и отмена dropdown тоже не означают выбор.
Совместимость именно Taiga combobox с поиском проверяется отдельно: результаты прежних tests обычного Taiga Select не
дают её автоматически. При необходимости расширяется DOM adapter с доказанным owner и commit, без доступа к модели.

Контрольный сценарий обучения: начать запись до поиска → ввести запрос → выбрать процедуру → дождаться нового MF →
заполнить динамические поля → завершить → сохранить Scenario → повторить на маршруте ученика с изначально отсутствующим
плеером. Completion выбора проверяет появление ожидаемой формы, а не один click по option.

## Приоритет

Сначала надёжная принадлежность элемента микрофронту, ограничение работы выбранными областями и lifecycle. Существующий
semantic resolver сохраняется как защита от небольших изменений. Редкие обновления UI позволяют перепроверять сценарии
после релиза и явно перепривязывать сломанные цели. Пороги ради «найти любой ценой» не снижаем: неверное совпадение
опаснее понятного отказа.

Область — логический MF, экземпляр области — конкретный смонтированный root. Поле должно находиться внутри своей
области, а не в соседнем MF с таким же label. Селекторы существующих host-тегов допустимы для задания границ; они не
заменяют ElementDescriptor полей и не превращаются в новые маркеры интерфейса.

## Что уже есть и что нужно изменить

Сейчас ElementRecorder принимает один HTMLElement, слушает capture events на document, наблюдает мутации root и каждые
100 мс повторяет reconcile его controls/properties. Resolver тоже получает один root. ScenarioRuntime создаёт
собственные observer и timer. Панель обучения находится снаружи root. Portal owner ищется среди controls root по
существующим aria-controls/aria-owns.

События на document сами по себе не означают полный обход страницы на каждый клик. Главный выигрыш ожидается от
ограничения DOM scans, property polling и повторных resolve. Перенос всех listeners на host MF потеряет события его
dropdown/dialog в общем overlay-контейнере. Поэтому сначала измеряем работу, затем устраняем дублирование observation
между recorder/runtime, сохраняя intent/commit и generation semantics.

## Предлагаемые понятия

| Понятие            | Назначение                                                                                                       |
| ------------------ | ---------------------------------------------------------------------------------------------------------------- |
| AreaDefinition     | Стабильный логический key MF и правило нахождения его host по существующему DOM или разрешённому shell-контракту |
| AreaInstance       | Текущий root, идентификатор экземпляра и поколение mount; DOM-ссылка не сериализуется                            |
| AreaRegistry       | Найденные/отсутствующие/неоднозначные области, mount/unmount/replace, принадлежность узлов                       |
| AreaPolicy         | Независимые `observe: boolean` и `interaction: allowed / blocked`; blocking добавляется позднее                  |
| EventHub           | Один набор capture listeners на document; дешёвый dispatch в разрешённую область по composedPath                 |
| PortalOwnership    | Связь вынесенного popup с областью через доказанного owner, с инвалидированием при закрытии/remount              |
| ObservationSession | Наблюдение выбранного набора областей, порядок событий, очистка и ограниченные ресурсы                           |

Логические keys находятся в конфигурации training, не записываются в атрибуты target DOM. Порядок `<microfrontend>` не
является идентификатором. Два `<some-mf>` без различающего контекста означают ambiguous, а не выбор первого. Общая
обёртка `<microfrontend>` недостаточна: требуется тип дочернего host и, если нужно, существующий instance context.

Для вложенных областей ближайшая зарегистрированная область владеет событием/контролом. Отключённый дочерний MF не
должен автоматически попадать в наблюдение включённого родителя. Неоднозначные или пересекающиеся определения
обнаруживаются до старта; правила не зависят от порядка конфигурации.

generation существующего плеера изолируют поздние ответы. Эксперименты вне observation root: перестановка соседей,
скрытие/возврат и пересоздание плеера, второй экземпляр справочника. Справочник фильтруется и открывает карточку;

ownership будут добавлены с registry; второй справочник уже позволяет воспроизвести два одинаковых host. Настоящая

поиск/пустую выдачу, отсутствие автозапуска по точному тексту, mount/remount/clear, сохранение состояния соседей и
поздний ответ предыдущего плеера. Метрики selective observation этим прогоном не измерялись.

## Этап 2. Registry и принадлежность областям

**Изменения:** выделить `libs/training-observer/src/areas/` с определениями, registry и resolver границ. Конфигурация
demo сопоставляет логический key с существующим дочерним host-тегом. Поддержать ноль/один/несколько совпадений,
уникальный контекст для нескольких экземпляров, вложенные области и изменение политики.

Discovery отслеживает структуру известных shell-контейнеров. Если доступен только document, лёгкий childList observer
смотрит появление/исчезновение host, а не извлекает признаки всех controls страницы. Его собственная стоимость тоже
измеряется: отсутствие полного сканирования не означает отсутствие любых callbacks от соседних MF.

**Готово, когда:** перестановка не меняет логический key; remount меняет generation и очищает ссылки; похожее поле
другого MF никогда не становится кандидатом выбранной области; неоднозначный root даёт явную диагностику.

### Реализовано: registry и Angular facade

Модули библиотеки: areas/types.ts, registry.ts и area-registry.service.ts. Правило области — существующий hostTag и
необязательный ancestorTag с точными значениями существующих атрибутов; произвольные CSS/XPath не принимаются. Контекст
ограничен переданным scope. Интеграция владеет lifecycle scope и вызывает disconnect при его уничтожении;
появление/удаление MF внутри scope отслеживается автоматически. Portal за scope пока возвращает outside.

Registry хранит все определения, включая observe=false. root(key) возвращает однозначный физический host независимо от
политики; для допуска элемента нужен accepts(key, node), который проверяет ближайшего владельца и observe. При
ambiguous/conflict root отсутствует, ownership возвращает отказ. Дубли одного key запрещены в конфигурации. Изменение
observe повышает generation; removed/reinserted host тоже консервативно повышает generation, даже при сохранении того же
Element. Логический key не меняется. Поколение локально экземпляру registry; будущая observation session должна отличать
также сеансы. DOM-ссылки и поколения не добавляются в wire-контракт v2.

Discovery использует childList/subtree и attributeFilter только для атрибутов контекста. Каждая структурная мутация
может вызвать повторный поиск host; значения controls, accessible names и descriptors не вычисляются. Dirty-subtree
оптимизация пока не реализована. Перед синхронным root/owner/snapshots обрабатываются takeRecords, чтобы событие сразу
после замены host не использовало предыдущую границу.

AreaRegistryService — provider уровня маршрута, DOCUMENT/DestroyRef через DI, readonly signal snapshots. TestBed
проверяет автоматическое обновление, teardown и reconnect. В админке раздел «Границы микрофронтов» показывает
missing/resolved/ ambiguous/conflict, число hosts и generation; интеграция подключается через afterNextRender. Сама
библиотека UI не содержит.

После этапа 2 запись ещё наблюдала общий surface. Подключение accepts к recorder/resolver выполнено в этапе 3; политика
блокировки взаимодействий остаётся отдельным расширением.

Проверки: development build, ESLint, 131 unit-тест ядра (11 новых), 2 Angular TestBed-теста, 9 backend-тестов и 11
browser tests (registry, multi-MF и regression записи) прошли. HTTP backend-тест запускался с разрешением локальных
портов после отказа sandbox; ошибки приложения в нём не было. npm test теперь включает Angular TestBed suite.

Рабочие модули перенесены в libs/training-observer. Старое ядро и неиспользуемая страница pages/spike удалены. Пакет

## Этап 3. Выбор наблюдаемых MF и общий dispatch

**Изменения:** добавить в админку список областей и переключатели «Наблюдать». По умолчанию для полного сценария
включены поиск процедур и логическая область плеера, даже пока он не смонтирован. Отдельно доступен режим наблюдения
только за плеером. Сначала подключить registry к существующему recorder/resolver без изменения matching-эвристик.

Сформировать одну observation session с общим EventHub, глобальным порядком/уникальными ID действий и локальным
состоянием областей. Не запускать независимый document listener на каждый MF. Membership проверяется до чтения value,
вычисления accessible name и генерации descriptor. Navigation — событие сеанса, не копия от каждого MF.

MutationObserver/property sampling работают только в включённых областях. Pending input/selection принадлежат экземпляру
области; disable/unmount отменяет неподтверждённые ожидания с диагностикой, не создаёт отложенного «успешного» действия.
Завершённые действия сохраняются. Enable начинает новое поколение и baseline snapshot, не записывая прошлые изменения
как новые действия. Старые tokens не действуют после повторного enable.

Включение нескольких MF не должно нарушить последовательность input commit → click между областями. Для runtime
изменение набора наблюдения не означает пропуск шага: если его область выключена, показать паузу/недоступность.

**Готово, когда:** выбран один MF — значения и действия остальных не записываются; можно добавить второй MF без
перезапуска первого; нет двойных событий, потерянного порядка и принятия старого commit после переключения.

### Реализовано: селективная запись

RecorderOptions.areas подключает registry к одному recorder. Inventory и sampling берут только разрешённые roots;
membership проверяется до track/readValue/identity. Вложенные выключенные области исключены и из peers генератора
locator. Root observers подключаются к выбранным областям, общий property timer и журнал сохраняются при переключении.
Мутации внутри выключенного потомка всё ещё могут доставляться observer родителя: это не гарантия отсутствия callbacks.
Изменения registry отменяют pending intent/commit старого поколения; новая область получает baseline без фиктивного
input.

DocumentEventHub разделяет семь capture listeners на document в пределах экземпляра библиотеки. После последней отписки
они снимаются; события передаются синхронно, ошибки подписчика не прерывают доставку другим. Navigation остаётся одним
событием одного журнала. Portal lookup учитывает aria-controls/aria-owns конкурентов в scope, включая observe=false, до
чтения значения выбранного owner. Полный общий индекс portals остаётся в этапе 4.

RecordingSessionService владеет recorder через DI/DestroyRef и readonly signals; админка не управляет native ресурсами.
Переключатели «Наблюдать» работают до и во время записи. session.resolve использует сохранённый key цели и
ResolverOptions.accepts; поиск в другой MF или fallback на весь document при отсутствии области запрещён.

На момент поставки этапа 3 target → area находился только в памяти recorder. Экспорт Recording v2 был журналом действий;
он не сохраняет area identity. Импортированные записи без привязки не получают угадываемую область. Перенос области в
сценарий и подключение registry к learner реализованы ниже через wire v3. Свободный порядок и blur-only здесь не
менялись.

## Этап 4. Portals, контракты и свободный порядок прохождения

**Изменения:** вынести принадлежность popup в общий слой. Option за пределами host учитывается только при доказанном
owner выбранной области. В поиске конкурирующих владельцев учитывать и известные выключенные области, иначе отключение
одного MF может искусственно сделать owner «уникальным». Для этого достаточно индекса ownership-связей; значения
выключенных controls не читаются и semantic recording для них не включается.

Popup без доказанного owner не присваивать активному MF по фокусу, времени или положению. Крупный shared overlay
container нельзя целиком отдать одному MF. Проверить одновременные dropdown разных MF, переиспользование popup IDs,
удаление owner, закрытие popup и remount. Неподдержанные dialogs фиксируются отдельно от поддержанного ARIA dropdown.

В записи/сценарии нужна сохранённая логическая область каждого descriptor. Предлагается отдельная версия wire-контракта
для multi-area, с обновлением validation/import/export и runtime. Не добавлять новые поля в строгий v2 молча. Импорт
прежнего v2 требует явного сопоставления единственной области с выбранным MF; никаких автоматических привязок к
«первому» MF. Поколение и Element остаются только в памяти, не идентичностью будущего прохождения.

Resolver сначала находит однозначную область, затем элемент внутри неё. Поля следующего MF и completion должны ссылаться
на область явно. При потере/выключении нужной области runtime ожидает либо приостанавливается; таймаут, unknown и
ambiguity сохраняются. Remount разрешает повторный поиск по логическому key, но не переносит старый intent.

В этом этапе заменить модель единственного текущего шага активной группой с набором доступных ожиданий. Authoring
объединяет исправления одного поля в итоговое ожидание в пределах одной формы/ветки; повторные появления похожих полей в
разных состояниях не объединяются автоматически. При недостатке контекста администратор уточняет ожидания. Контракт явно
хранит условия доступности, обязательность и completion; хронология Recording не задаёт зависимости. Старый v2 нельзя
молча переинтерпретировать: импорт проходит через проверку автором и новый контракт. Intent tokens относятся к ожиданиям
и поколениям областей и активной группы, а не к единственному текущему шагу; поздние commits не должны закрывать новые
ожидания.

Проверки свободного порядка: администратор заполняет A → B → C, ученик C → A → B; другая последовательность записи даёт
те же требования внутри группы; перемешанный порядок между MF в одной группе; правильное → неправильное → правильное
значение; повторный click; одинаковые поля и ambiguity; поздние поля backend; optional/branch и итоговый completion.
Сценарий завершается по состоянию обязательных ожиданий и итоговому completion, не по достижению последнего записанного
события.

Дополнительные проверки групп: A/B/C на первом экране в разном порядке → подтверждённый переход → D/E на втором; справка
обязательна перед переходом, но не упорядочивает остальные поля; popup и ошибка валидации не переключают экран; append
сохраняет видимость старых полей без их автоматического включения в новую группу; поздний commit предыдущего экрана не
учитывается в новом; преждевременный «Далее» не засчитывается, даже если реальный плеер ушёл вперёд; одинаковые labels
на двух экранах, условные поля, ветки и unknown postcondition.

Независимость от demo проверяется разными fixtures: обычная форма с несколькими состояниями, вкладки/диалог внутри
одного DOM-root, несколько разрешённых DOM-областей. Для них используется один и тот же runtime без ветвлений по именам
компонентов, маршрутам или подписям кнопок. Конкретные MF поиска/плеера остаются одним из интеграционных тестов.

В этом этапе заменить ручной запуск ученика автоматическим: вход загружает сценарий и запускает runtime, выход
останавливает сеанс. Наблюдаемые области определяет конфигурация сценария/интеграции. Проверить первый action после
старта, ожидание MF, подсказки через внешний renderer, повторный вход и cleanup. Диагностика остаётся отдельным режимом
стенда; прохождение не требует её открытия.

**Готово, когда:** Recording → JSON → другой маршрут/документ → Scenario работает для двух MF с одинаковыми labels,
порталами и сменой экземпляров. Предыдущие сценарии v2 импортируются через проверяемое сопоставление области.

### Реализовано: перенос областей через wire v3

Recording и Scenario теперь имеют отдельный вариант version:3 с areas.definitions и полным сопоставлением targetId →
areaKey. Все descriptor имеют ровно одну область; неизвестные/повторные ссылки и поля отклоняются. Descriptor/Resolution
остаются v2. Номера поколений и DOM-ссылки не попадают в JSON.

Recorder с registry экспортирует v3. Выключение MF не удаляет уже записанные цели: экспорт объявляет их области
необходимыми для будущего сеанса. Это не команда изменить текущую observe policy. Черновик переносит привязки действий и
явно выбранную область completion. TargetResolver сверяет host/context с registry интеграции до поиска; затем ищет цель
в текущем экземпляре только своего MF. Conditions используют ту же границу, включая глобальное completion и ветки.
Отсутствующий MF не доказывает даже expected:false — результат unknown.

Learner demo подключает registry; область следующего действия может появиться после выбора процедуры. Появление плеера
сохраняет подтверждённый intent поиска; remount владельца самого действия инвалидирует intent. Вне выбранных областей
recorder ученика не читает значения. Импортированную запись v3 можно проверять без прежнего сеанса в памяти.

Чтение v2 сохранено. bindRecordingAreas/bindScenarioAreas требуют явной, полной таблицы сопоставления; не исправляют
семантику старых descriptors автоматически. Multi-MF demo отклоняет v2 с объяснением необходимости миграции.

Проверки: 158 core tests и 4 Angular TestBed tests; 16 browser tests записи, импорта, прохождения и границ MF. Новый
browser-тест начинает запись до выбора процедуры, затем проходит поиск → поздний плеер в другом документе. Development
build, сборка пакета, проверка consumer без workspace aliases и ESLint проходят.

На момент поставки wire v3 общий индекс portals, blur-only commits, свободный порядок ожиданий и автоматический запуск
ученика ещё не были реализованы. Blur-only добавлен следующим изменением ниже. Последовательную модель графа v3 не
следует считать выполнением этих требований.

### Реализовано: группы ожиданий, wire v4

Новые сценарии из записи v3 используют groups/expectations/transitions. Границы отмечает автор; внутри группы
последовательность записи не задаёт порядок прохождения. requires задаёт только явные зависимости; when различает false
и unknown. Пропущенное optional ожидание не удовлетворяет requires. Один подтверждённый click справки сохраняет
доказательство после её закрытия; ввод перепроверяется после blur и при изменении свойства сервером.

Переход получает разрешение до обработчика приложения, затем ждёт своего результата. Незавершённый ввод, невыполненные
задания и неоднозначные совпадения не разрешают переход. Поля следующих групп, даже видимые, не засчитываются заранее.
Поколения области/группы исключают старые commits. Ожидаемое значение input/select хранится отдельно от DOM completion,
в action.value.

Редактор предлагает границы вручную через «Группы и переходы» и выбор цели подтверждения. Сложные зависимости, условия и
ветки задаются в JSON; автоматической кластеризации пока нет. Повторные исправления одного поля сворачиваются только
внутри одной группы. Уже видимая цель перехода требует проверки автором: универсальный наблюдатель не узнает скрытый
бизнес-результат. Импорт v2/v3 сохраняет прежний последовательный интерпретатор.

Проверки: 197 core tests, 4 Angular TestBed tests, все 33 browser-сценария. После финальной правки редактора отдельно
повторён импорт записи → изменение границ → экспорт v4 → прохождение. Browser-проверки включают другой порядок полей в
изменённой раскладке, 422, потерю ответа, stop/restart, поиск и поздний mount; unit fixtures не зависят от Taiga или
demo-компонентов. Собраны demo и пакет, проверен внешний consumer новых v4-типов, ESLint проходит.

2. Измерение и оптимизация наблюдения (этап 5).

### Реализовано: общий индекс принадлежности dropdown

2026-09-13: `observation/portal-ownership.ts` разделяется всеми recorder одного document в пределах одного экземпляра
пакета. Runtime использует тот же механизм через принадлежащий ему recorder. Ссылки `aria-controls`/`aria-owns` и ID
индексируются по document, поэтому маленький root не скрывает конкурентов за своими границами. Observe policy
проверяется после выбора единственного владельца; значения ненаблюдаемых controls не читаются.

Повторные ID и конкурирующие владельцы дают отказ. Общий контейнер нескольких listbox нельзя присвоить одному control.
Перед intent/commit индекс забирает необработанные мутации, включая изменения в том же стеке. Обычное закрытие popup не
отменяет подтверждённый выбор; замена popup, повторное использование ID, remount того же узла и новый конкурент до
подтверждения отменяют pending selection. Lookup `aria-activedescendant` тоже отклоняет повторные ID.

Первый recorder подключает общий observer, последний освобождает observer и таблицы DOM-ссылок. Поколения удалений
хранятся в WeakMap. Сам индекс внутренний; новые требования к целевому приложению и wire-поля не добавлены. Произвольные
dialogs без доказанной связи, Shadow DOM и iframe не объявляются поддержанными.

Это общий ownership для поддержанного dropdown, а не универсальная принадлежность всего overlay. Индекс пока полностью
перестраивает таблицы после релевантных мутаций; стоимость и более точная invalidation относятся к этапу 5.
Автоматический запуск ученика и остальные обязательные части этапа 4 выполнены ранее. После завершения ownership
следующим был этап оптимизации; актуальный порядок изменён: **сначала редактирование событий и обратная связь (этап 6),
затем оставшаяся оптимизация (этап 5)**. Блокировка взаимодействий остаётся отдельной опцией.

Проверки: 210 core tests, 4 Angular tests, сборка пакета и внешний consumer, сборка demo и ESLint проходят. Из 35
browser-сценариев полный прогон прошли 34; один тест плеера получил ошибку Chromium `Network.getResponseBody`. Оба
варианта этого теста повторно прошли без изменения кода. Новые browser-проверки подтверждают отказ в зачёте выбора при
конкурирующей ссылке из выключенного MF и успешный свежий выбор после снятия конфликта — в записи и у ученика.
Unit-проверки покрывают маленький root, конкурента вне него без чтения value, независимые dropdown, повторные ID,
закрытие, remount тех же узлов, смену владельца в обработчике и освобождение общего observer.

## Этап 5. Измеряемая оптимизация

**Оставшаяся работа отложена до завершения этапа 6. Реализована первая часть — общий цикл recorder/runtime и повторное
использование inventory при sampling.** Runtime получает coalesced microtask после наблюдения recorder; отдельные
runtime observer и interval удалены. Произвольные изменения `.value` по-прежнему обнаруживаются среди всех tracked
controls и не становятся действиями. Мутация пересканирует затронутую область целиком: это безопасный промежуточный
вариант, учитывающий влияние labels, ARIA и контекста на соседние элементы. Remount и изменение политики пересобирают
выбранные области.

Воспроизводимый runner: `npm run benchmark:observation`. Сравнение с `98575d2`, методика и ограничения находятся в
[отчёте](./observation-benchmark/README.md). Browser tests получили отдельный backend на 4311 через Angular environment
replacement, чтобы не расходовать лимит сессий demo на 4310.

**Осталось в этапе 5:** точная invalidation dirty subtrees и identity с безопасным fallback, отдельные счётчики работы
discovery/ownership и расширенные измерения задержки принятия действия. Этот промежуточный результат не закрывает этап.

**Изменения:** добавить общий scheduler observation, чтобы recorder/runtime не делали независимые полные scans одного
root. После первичного inventory обновлять tracked controls по dirty subtrees; периодически читать properties из
актуального набора, потому что MutationObserver не видит произвольные `.value`/`.checked` изменения.

Не ограничивать sampling только текущим фокусом: backend может менять другие controls выбранной области. Кэшировать
identity до релевантных мутаций; инвалидировать label/ARIA/context dependencies и исключённые дочерние области. Shared
owner index имеет свою invalidation-политику. Полную пересборку оставить безопасным fallback при неопределённом наборе
изменений. Поддерживать лимиты и coalescing, но не выбрасывать semantic commits молча.

Сравнить прежний single-root подход и новый scheduler на одном и том же сценарии: один выбранный маленький MF, несколько
выбранных MF, шумящие соседи, большой плеер и частые remount. Размеры fixtures и seed зафиксировать до замеров.

**Метрики:** число listeners/observers/timers, scans и controls с прочитанными properties, вызовы features/resolve,
работа discovery/ownership, median/p95 обработки и задержки принятия действия, retention узлов после unmount. Стоимость
фонового discovery не смешивать со стоимостью полноценного наблюдения.

**Готово, когда:** рост числа controls в выключенных соседях не увеличивает число читаемых values и кандидатов resolver
выбранного MF; число document listeners постоянно; выключение освобождает локальные ресурсы; все прежние проверки
intent/commit, ambiguity, 422 и поздних ответов проходят. Численный выигрыш публикуется по результатам, заранее процент
ускорения не обещается. Жёсткий CPU-бюджет согласовать по реальному окружению.

## Этап 6. Редактирование событий и обратная связь в админке

Инструкция по текущим возможностям: [как пользоваться админкой](./admin-guide.md). Во время записи показываются
остановка и журнал, команды редактирования скрыты с объяснением. После остановки журнал расположен перед редактором.
«Экраны обучения и переходы» отделены от свёрнутого раздела «Группы вариантов — заготовки»; интерфейс явно сообщает, что
настройка авторских сообщений ещё не реализована. Подсказка не выдаётся за сообщение о результате действия.

Дополнение к MVP от 2026-09-13. **В работе: добавлены удаление действий и выбор составов групп вариантов.** Следующая
часть — привязка групп к заданиям, реакции вариантов и авторская обратная связь. Выполняется до оставшейся оптимизации
наблюдения.

### Удаление записанных событий

**Реализация:** на `/record` после остановки у каждого semantic action доступна кнопка «Удалить», над журналом —
«Отменить удаление». Рабочие версии хранятся отдельно от recorder; история отмены действует до новой записи или ухода со
страницы. Экспорт записи сохраняет текущую рабочую копию. ID/sequence оставшихся действий, descriptors и фоновые states
не перенумеровываются и не удаляются вместе с action.

После удаления/отмены уже подготовленный сценарий считается устаревшим; экспорт и запуск запрещены до пересборки.
Исчезнувшее последнее действие нужно выбрать заново или восстановить. Удалённую границу автор явно убирает из настроек
либо отменяет удаление. При пересборке `mergeScenarioDraft` сравнивает базовый черновик, авторскую версию и новый
черновик. Независимые правки сохраняются; для конфликтов автор может исправить задания, отменить удаление или выбрать
«Использовать новую запись для конфликтов». Этот выбор не отменяет проверку зависимостей и wire-контракта. Повторный
ввод сворачивается по оставшимся событиям; при удалении первого события сохраняется ID существующего ожидания. Сообщения
обратной связи пока не реализованы и в этом изменении не объявляются поддержанными.

При удалении границы номера групп могут сдвинуться: идентичность последующих групп восстанавливается по входящим
переходам, чтобы авторские заголовки и задания не перешли к другому экрану. Конфликты отображаются с названием задания и
смыслом поля; решение в пользу записи затрагивает только конфликтующие изменения. При изменении самого состава групп
автору всё равно нужно проверить результат пересборки.

**Проверки:** 220 core tests, 4 Angular tests, сборка пакета и внешний consumer, ESLint изменённых файлов. Новые browser
tests проверяют удаление → отмену → пересборку → прохождение, удаление конца и всех действий, конфликт значений,
удаление границы и исправление зависимости. После обновления поведения редактора прошли все 13 затронутых browser tests;
остальные 27 browser tests прошли в полном прогоне. Unit tests дополнительно проверяют неизменность исходной записи,
стабильность ID свернутого ввода и сохранность поздней группы после удаления раннего перехода.

В журнале админки можно удалить отдельное записанное semantic action: лишний клик, ввод, выбор или навигацию. Удалённое
действие исчезает из рабочей записи и не участвует в генерации сценария. Это редактирование автором, а не optional
задание или пропуск действия учеником. Низкоуровневые DOM events и фоновые snapshots не выдаются за учебные действия.

Редактировать рабочую копию, сохраняя возможность отменить удаление. Не менять стабильные ID оставшихся действий. После
удаления повторного ввода итоговое ожидаемое значение вычисляется по оставшимся действиям этой группы. Если удалено
последнее действие сценария, граница группы или действие, на которое ссылается зависимость, явно показать необходимость
исправления. Не переназначать переход или зависимость молча и не сохранять сценарий с висячими ссылками. Перегенерация
не должна незаметно терять уже отредактированные задания и обратную связь: сохранять их по стабильным ссылкам, а
конфликтующие изменения показывать автору.

**Готово, когда:** через UI можно удалить ошибочный клик и промежуточный ввод, отменить удаление, сохранить и заново
открыть сценарий. Удалённое действие не требуется при прохождении. Проверены удаление последнего действия, перехода,
ожидания с зависимостями и повторного ввода, а также сохранность авторских текстов после пересборки.

### Обратная связь для каждого действия

#### Группы вариантов и режим выбора элементов

**Частично реализовано: выбор и хранение состава групп; реакции и исполнение пока не реализованы.**

На `/record` доступна кнопка «Создать группу вариантов» вне активной записи. Angular-компонент
`projects/demo/src/authoring/element-group-picker.component.ts` получает root и registry, не знает устройство demo,
Taiga controls или названия микрофронтов. Верхний слой использует Popover API; без поддержки API режим не включается.
Клик добавляет или убирает control, «Готово» сохраняет состав, Escape/«Отмена» отменяют изменения. Панель можно
перенести влево или вправо, чтобы она не закрывала выбираемые элементы. Подсветка обновляется при scroll/resize.

Живые DOM-ссылки остаются только в открытом инструменте. Отдельный документ `training-element-groups` v1 хранит ID,
названия групп, descriptors и area keys в localStorage под ключом `training-authoring-element-groups-v1`. Это авторские
заготовки, **не расширение Scenario v4**: они пока не экспортируются с учебным сценарием и не проверяются runtime. При
повторном открытии цели разрешаются в своих областях; missing/ambiguous и изменившиеся цели требуют повторного выбора.
Повреждённый документ не перезаписывается автоматически. Отдельный `readElementDescriptor` ядра проверяет сохранённые
цели теми же правилами, что и цели recording/scenario.

Picker доступен только при остановленной записи; собственные клики и перенос фокуса не являются учебными действиями.
Слой перехватывает pointer/mouse активацию, клавиатура и фокус остаются в панели. При закрытии снимаются observer,
listeners и слой, восстанавливается доступный прежний фокус. Native controls не модифицируются. Глобальные capture
handlers приложения по-прежнему могут видеть события слоя — полной изоляции document/window не обещаем.

Текущая область поддержки: controls из переданного root с доказанным owner, в том числе нативные radio/checkbox, button
со вложенными span и Taiga combobox как цель. Состав можно собрать из разных контейнеров. Popup вне root, Shadow
DOM/iframe, произвольный canvas и controls без поддерживаемой семантики пока не выбираются. Слой не открывает dropdown
вместо автора; дальнейшую поддержку внешних popup нужно связать с доказанным ownership.

**Проверки этого изменения:** 221 core test, 4 Angular tests, сборка пакета и внешний consumer; полный прогон 46 browser
tests прошёл. После приведения CSS к правилам проекта повторно прошли 6 проверок picker: generic HTML controls и
сохранение после reload, keyboard/Escape, remount и исключение из записи, touch/scroll/resize и изменение подписи, Taiga
combobox без открытия dropdown, отказ от повреждённого документа. ESLint и Stylelint изменённых файлов проходят.

**Осталось:** ручные реакции вариантов и связь с активным заданием, предложения групп по DOM-семантике, контракт
обратной связи и его проверка в runtime. Сохранённые составы — входные данные для этой части; этап 6 ещё не завершён.

Требования полного механизма: в админке кнопка «Создать группу вариантов». Автор включает режим выбора, наводит
указатель на целевой интерфейс и видит подсветку элемента. Клик добавляет элемент в рабочую группу, повторный клик
убирает его. «Готово» сохраняет выбор; Escape или «Отмена» отменяют текущие изменения. Панель админки остаётся доступной
и не может стать учебной целью. Можно выбирать элементы из разных контейнеров разрешённых областей.

Для каждого варианта автор задаёт реакцию: ожидаемое действие, допустимое действие без ошибки или ошибочный вариант с
текстом обратной связи. Группа вариантов привязана к заданию активной группы сценария и не заменяет сам экран с его
независимыми ожиданиями. Учитывать зависимости и свободный порядок заполнения; несколько доступных правильных действий
не должны становиться ошибочными альтернативами друг друга. Противоречивые правила для одной цели при одновременно
активных заданиях показывать автору и требовать исправления.

Автоматическая группировка — только предложение автору на основе стандартной семантики DOM: нативная radio-группа,
`role="radiogroup"`, `fieldset`/`legend`, именованный `group` или `toolbar`. Расположение кнопок рядом не доказывает их
взаимоисключение. Автор подтверждает состав и смысл группы либо выбирает элементы вручную. Никаких специальных знаний о
кнопках, маршрутах, Taiga UI, процедурах или микрофронтах demo в алгоритме библиотеки нет. Для нестандартных controls
сохраняется возможность адаптеров; отсутствие надёжной семантики нельзя компенсировать угадыванием.

Негативная обратная связь допустима при однозначном совпадении с явно заданным ошибочным вариантом либо неверным
значением ожидаемого поля. Посторонние действия не считаются ошибкой, неоднозначный resolver означает проблему сценария.
Radio проверять после подтверждения выбора. Набор checkboxes проверять при явно заданном подтверждении или переходе,
чтобы промежуточный набор не порождал ошибки; немедленную реакцию на конкретный запрещённый вариант автор может задать
отдельно. Успех перехода по-прежнему требует выполнения его условий и подтверждённого результата.

**Изоляция выбора от приложения:** использовать принадлежащий админке прозрачный слой над выбираемой областью,
принимающий pointer events. Элемент под слоем определять DOM hit testing, исключая собственный UI; событие не пересылать
реальному контролу и не вызывать его `click()`. Подсветка и слой не являются tracking-маркерами целевого приложения.
Проверять вложенные icon/span и позволять уточнить выбираемый контрол, если цель неочевидна.

Одного `preventDefault()` на click реального контрола недостаточно: приложение может реагировать на pointerdown или
mousedown. При входе в режим приостанавливать обработку действий recorder/runtime до переноса фокуса, чтобы служебный
blur не подтверждал ввод и сам выбор не попадал в запись. Зафиксировать правила отмены незавершённого ввода/выбора; не
создавать commit из него при возобновлении. Перевести фокус в инструмент выбора, ограничить Tab его UI, исключить
активацию реальных controls через Enter/Space, touch и submit. Слой должен оставаться над выбранной областью при
scroll/resize и учитывать вынесенные popup. Выход, отмена, ошибка и уничтожение компонента снимают слой/подписки и
восстанавливают допустимый фокус и режим наблюдения без запоздалых commits.

Гарантию формулировать точно: реальные controls не получают целевые события выбора, но события слоя могут быть видны
глобальным capture listeners приложения. Полную изоляцию от произвольных document/window handlers в том же document
нельзя обещать; при необходимости такой гарантии нужна интеграция с shell. Фоновые HTTP-запросы и DOM-обновления не
останавливаются. Если выбранный элемент исчез или был перемонтирован, показать устаревший выбор и потребовать повторного
выбора; не подменять его автоматически другим похожим элементом.

Инструмент выбора и его lifecycle принадлежат Angular-админке. Headless-библиотека строит ElementDescriptor выбранных
целей и исполняет правила; wire-сценарий не хранит живые DOM-ссылки. Общие механизмы описания/разрешения элементов
переиспользуются без зависимости от реализации demo. Этот режим — обязательная часть этапа 6, а не отложенная политика
блокировки действий ученика из этапа 7.

**Готово, когда:** автор создаёт и отменяет группу без JSON, повторно открывает её и задаёт разные реакции вариантам.
Проверены radio, набор checkboxes, кнопки в разных контейнерах и вложенные icon/span на разных DOM-структурах, включая
интерфейс без Taiga UI. При выборе не вызываются обработчики реальных controls на pointerdown/mousedown/click, не
переключаются radio/checkboxes, не отправляется форма, не меняется маршрут и не добавляются semantic actions. Проверены
клавиатура/touch, scroll/resize, исчезновение цели, отмена и повторный вход; после выхода обычное взаимодействие
восстанавливается. Runtime проверен на допустимом действии, ошибочной альтернативе, исправлении, неоднозначной цели и
свободном порядке полей. Выявленные ограничения глобальных handlers явно документированы.

#### Сообщения и события runtime

В редакторе у каждого ожидаемого действия и действия перехода можно задать обратную связь: текст при успешном выполнении
и текст при несовпадении действия/значения с ожиданием. Сообщения необязательны. Они отличаются от подсказки: подсказка
помогает выполнить задание, обратная связь сообщает результат конкретной попытки. Редактор показывает, к какому действию
и результату относится каждый текст; настройки сохраняются при экспорте/импорте сценария.

Библиотека остаётся без UI и зависимостей от Taiga UI. Runtime отдаёт событие обратной связи с идентификаторами сеанса,
группы, ожидания/перехода и попытки, результатом проверки и авторским текстом. Точный контракт и миграцию версии
сценария определить при реализации; существующие строгие JSON-контракты нельзя расширять молча. Старые сценарии без
сообщений должны оставаться исполнимыми.

Для input обратная связь появляется после blur, для выбора — после подтверждения значения, для перехода — после проверки
его результата. Сообщение об ошибке относится к однозначно сопоставленной попытке; посторонний клик или неоднозначная
DOM-цель не должны превращаться в выдуманную ошибку ученика. Повторный polling, render и одинаковые snapshots не
порождают новые сообщения. Исправленная новая попытка может дать новое сообщение; запоздалое событие старого сеанса или
группы не показывается.

**Дальнейшее отображение:** Angular-интеграция зоны ученика подписывается на эти события и показывает **Taiga UI 4
Alerts**. Выбор внешнего вида, очередь и закрытие уведомлений принадлежат приложению. Авторские строки выводятся как
текст. Подписка освобождается при выходе из тренировки; библиотека сама alerts не открывает.

**Готово, когда:** администратор настраивает разные сообщения для двух действий без JSON; настройки переживают
сохранение/импорт и удаление соседних событий. Проверены неверный ввод → blur → исправление → blur, подтверждение
перехода, свободный порядок полей, отсутствие дублей и отсутствие сообщений из остановленного сеанса. Контракт готов для
последующего подключения Taiga UI Alerts.

## Этап 7. Необязательная политика блокировки взаимодействий

**Отдельное последующее расширение**, после проверки наблюдения и только при подтверждённой потребности. Настройки
observe и interaction независимы: разрешено наблюдать разрешённую область, не наблюдать разрешённую, либо блокировать
выбранную область. Training UI не блокируется.

Перед реализацией определить продуктовый смысл: запрещены только click-активации или любое взаимодействие, включая ввод
и Tab/focus. Не выдавать запрет мыши за полную блокировку формы. Для click-режима проверить pointer, keyboard
Enter/Space, submit/link activation и связанный portal; guard выполняется до semantic recorder. Заблокированная попытка
— отдельная диагностика, не выполненный шаг и не обычный записанный click.

Выбрать механизм по контракту: capture cancellation для ограниченной активации; для полной блокировки — проверить
временный inert/focus management на host и принадлежность вынесенных popup. Это управление взаимодействием, а не
tracking-маркер. Восстанавливать прежние значения/фокус и снимать блокировку при stop/unmount/ошибке; не затирать
изменения host-приложения. Не блокировать всю страницу из-за неизвестного owner popup.

Document listener, зарегистрированный раньше guard, уже мог выполнить побочный эффект. Программные вызовы и HTTP-запросы
клиента такая блокировка не защищает. Если нужна гарантия отсутствия бизнес-действия, потребуется поддержка
shell/приложения; DOM-only blocking не является границей безопасности.

**Готово, когда:** выбранный режим блокировки проверен мышью и клавиатурой, соседние MF продолжают работать,
заблокированная попытка не продвигает обучение, remount не оставляет «залипшую» блокировку и все изменения обратимы.

## Порядок проверки и поставки

Каждый этап — отдельное завершённое изменение с тестами и коммитом. Этапы 1–4 дают работающую multi-area demo. Далее
этап 6 добавляет удаление событий и авторскую обратную связь; после его функциональных проверок завершаем измерения и
оптимизацию этапа 5. Этап 7 остаётся отдельной опцией. Реализация настоящей federation-сборки сюда не входит.

Unit tests: registry/ownership и конфликты, политика вложенности, generations, cross-area ordering, отключение
наблюдения и migration контрактов. Browser tests: оба маршрута, реальные Taiga portals/формы, одинаковые подписи, late
mount/remount, шумящий сосед, смена observe во время input/selection и переход сценария между MF. Performance runner
измеряет работу, а не только время загрузки страницы. После каждого этапа обновлять этот документ фактами; не объявлять
completed до соответствующих проверок.

Первое изменение при начале реализации: общий demo shell, MF поиска с Taiga combobox, открываемый им MF плеера и
действующие соседние MF, без изменения resolver score и без политики блокировки. Это позволит проверять последующие
изменения в видимом пользователю интерфейсе.

### Дополнительные критерии для поиска → открытия плеера

- Поиск и плеер наблюдаются вместе: search input и select записаны один раз, затем записаны действия нового MF.
- Наблюдается только плеер: поиск работает, но его текст/действия не попадают в запись; поздний mount плеера обнаружен.
- Наблюдается только поиск: выбор записан, но поля открывшегося плеера не читаются и не записываются.
- Option в общем portal принадлежит MF поиска, даже если рядом открыт другой combobox с похожими options.
- Пустая выдача, ошибка и медленная загрузка не создают фиктивного select или завершения шага.
- Повторный поиск и выбор другой процедуры, очистка и быстрые A → B не дают старому ответу/commit продвинуть новый шаг.
- Новый документ ученика начинает с MF поиска без плеера; runtime ожидает разрешённую, но ещё не смонтированную область.
