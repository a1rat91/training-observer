# Автоматическое наблюдение за страницей

Третий этап: слой автоматического обновления поверх `DomSnapshotBuilder`.
Он поддерживает снимок light DOM одного документа. История действий и сравнение
с учебным сценарием в этот этап не входят.

## API

```ts
const observer = inject(TrainingObserver);

// После отрисовки DOM. Возвращает первый снимок синхронно, затем обновляет signal.
observer.start(root, {
    batchDelayMs: 50,
    propertyCheckIntervalMs: 500,
    maxNodes: 10_000,
    maxDepth: 100,
});

observer.snapshot();    // последний опубликованный снимок
observer.controls();    // вычисляемый список потенциальных контролов
observer.isObserving(); // работает ли сессия
observer.error();       // ошибка фонового обновления или null
observer.scanCount();   // число выполненных полных пересчётов
observer.revision();    // число опубликованных снимков

observer.stop();        // отменить наблюдение, сохранить последний снимок
observer.start(root);   // новый снимок и новая сессия
observer.clear();       // остановить и освободить последний снимок
```

Без `root` используется `DOCUMENT.body`. Область должна быть подключена к документу,
переданному через Angular DI. Ручной `capture()` остаётся доступным и не перенастраивает
текущую автоматическую сессию. Для изменения её области или параметров нужен `start()`.

Повторный `start()` сначала проверяет настройки и строит начальный снимок. Ошибка
этих проверок не останавливает уже работающую сессию. После успешной проверки старые
ресурсы освобождаются и создаётся ровно одна новая сессия.

В `DOM_OBSERVATION_OPTIONS` можно задать общие настройки. По умолчанию они включают
значения `DOM_SNAPSHOT_OPTIONS`, окно объединения 50 мс и сверку свойств каждые 500 мс.
Значение `propertyCheckIntervalMs: 0` отключает периодическую сверку. Обе задержки
должны быть целыми числами от 0 до 2147483647 мс. Большие интервалы практически
неполезны, но не переполняют браузерные таймеры.

## Источники обновлений

- `MutationObserver`: дочерние узлы, текст, все атрибуты с `subtree: true`.
- Делегированные события в capture-фазе: `input`, `change`, `reset`, `toggle`,
  `focusin`, `focusout`, `load`, `transitionend`, `animationend`.
- `resize` окна.
- Периодическая сверка native-состояния `input`, `textarea`, `select`, `option`.

Мутации слушаются на всём документе даже при ограниченной области снимка:
стиль предка, подпись вне области или внешний перекрывающий блок могут менять её
состояние. События ничего не отменяют и не останавливают; слушатели passive.
Это сбор состояния, а не перехват управления чужим интерфейсом.

Проверка свойств использует тот же `DomElementAnalyzer`, что и снимок. Она читает
текущие значения, checked/indeterminate/selected и другие native-признаки без
геометрического обхода. Сохраняется соответствие DOM-элемент → сериализованное
состояние. При изменении ставится задача пересборки; неизменная страница не
пересканируется каждые 500 мс. Password/file проходят через существующее исключение
значений, в том числе во временном кэше.

`MutationObserver` наблюдает дерево и атрибуты, но не произвольные JS-свойства.
Например, присваивание `input.value` у текстового поля может не породить мутацию
или событие. Поэтому сверка свойств — самостоятельный источник обновления.
См. [настройки MutationObserver](https://developer.mozilla.org/en-US/docs/Web/API/MutationObserver/observe).

## Прокрутка

Событие `scroll` само по себе не запускает пересчёт и не публикует новый снимок.
Положение прокрутки не рассматривается как учебный шаг. Если виртуальный список
или подгрузка данных при прокрутке меняют DOM, обновление запускается соответствующей
мутацией. Библиотека не вмешивается в обработчики прокрутки соседних приложений.

Taiga UI перемещает собственные ползунки через inline-стили. Поэтому одного
отказа от события `scroll` недостаточно: эти изменения приходят в `MutationObserver`.
Служебное поддерево `tui-scroll-controls` исключено из снимка и источников обновления
(мутации, события, сверка свойств). Это встроенное правило библиотеки, независимое
от пользовательского `ignoreSelector`. Контейнер `tui-scrollbar` и его содержимое
остаются под наблюдением. Другие изменения DOM при прокрутке по-прежнему учитываются.

После обычной прокрутки сохранённые координаты, `inViewport`, `hitTest` и
`pointerActionable` могут устареть. Они описывают момент последнего снимка.
Перед использованием геометрии (например, будущей подсветкой) можно явно вызвать
`capture(root)`. Отдельного API обновления только геометрии пока нет.

## Наведение

`mouseover`, `mouseenter`, `pointerover`, `pointerenter` и движение указателя
не являются источниками пересчёта. Само наведение не должно становиться учебным
шагом в будущем регистраторе действий (сейчас реализованы только снимки состояния).

Декоративный CSS hover может завершиться событием `transitionend`, например при
смене `background-color` кнопки Taiga UI. Переходы цветов текста, фона, границ и
теней отфильтрованы: они не меняют состояние и геометрию, представленные в снимке.
Фильтр действует и при уходе указателя.

Переходы `opacity`, `visibility`, размеров и положения, неизвестные свойства и
`animationend` продолжают обрабатываться: они могут изменить доступность контролов.
Если наведение добавляет меню, меняет атрибуты или текст, эти DOM-изменения тоже
отслеживаются. Это обновление контекста страницы, а не учебный шаг «навести мышь».
Поэтому правило не означает запрет любых пересчётов, совпавших с наведением.

## Объединение и публикация

Первое уведомление открывает фиксированное окно `batchDelayMs`. Остальные
уведомления в этом окне не создают новые таймеры и не отодвигают уже назначенный
пересчёт. Даже непрерывный поток событий периодически приводит к обновлению.
При 0 мс пересчёт всё равно откладывается до задачи таймера, а не выполняется
внутри обработчика ввода. Это также позволяет обработать native reset после
выполнения стандартного действия браузера.

На этом этапе каждый такой пересчёт строит полный снимок выбранной области.
Структура, состояния, геометрия и статистика сравниваются с последней публикацией;
время снимка и длительность вычисления из сравнения исключены. При отсутствии
разницы `snapshot` и `revision` не изменяются. Поэтому `capturedAt` — время последнего
опубликованного снимка, а не таймер активности. Ручной capture и первый снимок
каждого start публикуются явно, даже при одинаковом содержимом.

Слушатели, MutationObserver, таймеры и обход работают вне Angular zone.
Публикация и диагностика возвращаются в неё. Это не отдельный поток: синхронный
обход и сравнение JSON всё ещё занимают главный поток браузера.

## Исключение интерфейса наблюдателя

Собственный компонент помечается `data-training-observer-ignore` — на чужие
контролы ничего добавлять не нужно. Исключённые поддеревья не попадают в снимок,
периодическую сверку и обработку внутренних событий/мутаций. Это устраняет
обратную связь: обновление JSON инспектора не запускает новый снимок JSON.

Изменение самого элемента-границы проверяется, поскольку оно может включать или
выключать исключение. Для удалённых узлов учитывается родитель из MutationRecord:
текущий родитель узла уже может быть другим. Иначе перенос контрола внутрь
исключённой области ошибочно оставлял бы его в последнем снимке.

Селектор исключения не является изоляцией CSS или layout. Если собственный
интерфейс изменяет геометрию соседей, это может отразиться в следующем снимке,
вызванном внешним событием. Для встраивания предпочтительна область интерфейса,
не сдвигающая наблюдаемые контролы.

## Жизненный цикл

`stop()` отключает MutationObserver, снимает все обработчики, отменяет периодический
таймер и ожидающий пересчёт, очищает кэш ссылок на контролы. Поздняя доставка
уведомления не возобновляет остановленную сессию.
[disconnect() отбрасывает недоставленные уведомления](https://developer.mozilla.org/en-US/docs/Web/API/MutationObserver/disconnect).

`DestroyRef` выполняет ту же очистку и освобождает последний снимок. При удалении
компонента это срабатывает, если сервис предоставлен в его `providers`.
Экземпляр с `providedIn: 'root'` живёт до уничтожения приложения — само удаление
произвольного компонента его не уничтожает.

В parser создан отдельный `ObserverPanelComponent` с `providers: [TrainingObserver]`.
Он запускает наблюдение после рендера. Кнопка «Закрыть инспектор» уничтожает компонент
и его сервис; «Открыть инспектор» создаёт новый экземпляр. Это стенд жизненного цикла
будущего встраиваемого интерфейса.

Если сама наблюдаемая область удалена из документа, сессия останавливается,
сохраняет последний успешный снимок и выставляет `error`. Новый корень нельзя
надёжно угадать — его нужно передать в следующий `start()`.

## Проверенные сценарии

Браузерные тесты покрывают изменения текста и атрибутов, добавление/удаление узлов,
делегированный ввод без polling, изменения native-свойств без событий, пакетные
обновления, непрерывный поток изменений, viewport и внешние перекрытия,
исключённый интерфейс, остановку с ожидающей задачей, повторный start,
уничтожение через DestroyRef, удалённый корень и некорректные настройки.
Отдельно проверено отсутствие пересчёта при обычной прокрутке и сохранение обновлений
при изменении DOM виртуальным списком.

Для проверок освобождения ресурсов тестовый input считает чтения своего value.
Трассировка Playwright в этом наборе отключена: её DOM-снимки сами читают значения
полей. Замер отсутствия фоновых чтений начинается после намеренного изменения
поля, чтобы исключить синхронные чтения со стороны обёртки native setter.

## Текущие ограничения

- Полные пересчёты, а не обновление отдельных веток. Нужны замеры на больших страницах.
- Полный опрос native-контролов области; лимиты maxNodes/maxDepth ограничивают
  снимок, а не стоимость поиска полей при сверке.
- В скрытой вкладке браузер может задерживать таймеры. Интервалы не являются
  гарантией задержки в реальном времени.
- CSSOM-изменения без DOM-мутации, промежуточные кадры анимаций и произвольные
  изменения layout без отслеживаемых событий не покрыты полностью. Для непрерывной
  геометрии понадобится отдельный механизм, например ResizeObserver и выборочные проверки.
- iframe и Shadow DOM пока только обозначены границами; семантических адаптеров
  всех компонентов Taiga UI ещё нет.
- Обновления снимка не являются последовательностью действий пользователя:
  несколько событий объединяются, кратковременные состояния могут не сохраниться.
  Будущий регистратор действий должен слушать события отдельно.
