# Аудит понятности кода — 10 сентября 2026

Проверена библиотека `libs/training-observer`, публичные модели, конфигурация
проверок и структура браузерных тестов. База — коммит `2033c27` и текущие
незакоммиченные изменения InputNumber. Это статический аудит сопровождаемости;
приоритеты ниже обозначают порядок упрощения, а не серьёзность runtime-дефектов.
Исходники и тесты в рамках аудита не изменялись, проверки повторно не запускались.

Главная проблема — концентрация правил и неявных зависимостей внутри методов.
В библиотеке около 1450 строк реализации; объём сам по себе не требует новой
архитектуры. Больше всего усилий на понимание требуют сборка логического контрола
и жизненный цикл наблюдения.

1. **Высокий приоритет: правила Taiga выходят за границы адаптера.**

   `services/control-adapters.ts:60` распознаёт компоненты, но
   `services/control-snapshot-builder.ts:36` самостоятельно знает об option,
   filler, multi-textfield, cleaner и floating label. Даже `nativeKind`
   в `control-adapters.ts:42` проверяет `tuiselectlike`. Интерфейс адаптера
   поэтому не показывает всех правил поддержки контрола.

   Практический пример — InputNumber: помимо распознавания пришлось расширить
   списки типов для field host, подписи, значения и popup. Пропуск одной ветки
   не является ошибкой TypeScript, но даёт частично поддержанный контрол.

   Упрощение: собрать специфичные правила Taiga рядом с адаптером; явно назвать
   решения о самостоятельном контроле, служебном элементе и неподдержанном
   составном поле. Сначала достаточно функций. Реестр плагинов и класс на
   каждый вид input здесь не нужны. Приоритет Taiga перед native сохранить.

2. **Высокий приоритет: `ControlSnapshotBuilder.build` объединяет слишком много задач.**

   `services/control-snapshot-builder.ts:23` в одном методе индексирует граф,
   ищет кандидатов, исключает служебные узлы, собирает members, вычисляет label,
   состояние, контекст и popup. Вложенные `ancestors`, `text`, `collect` замыкают
   общие данные; чтобы изменить одну часть, приходится читать почти весь метод.

   Упрощение: оставить в build последовательность именованных этапов.
   Отдельно выделить чтение графа снимка, поиск кандидатов и сборку одного контрола.
   Подпись, контекст и проекцию состояния оформить небольшими чистыми функциями.
   Вспомогательные функции не должны читать живой DOM или получать собственное
   состояние между вызовами. Перенос всех этих функций в Angular-сервисы добавит
   лишние зависимости.

3. **Высокий приоритет: жизненный цикл сессии имеет скрытые контракты.**

   В `services/dom-observation-session.ts:35` callback `onChange` возвращает
   снимок; его вызывающая сторона фактически выполняет capture и публикацию.
   `refreshProperties` в строке 97 также обновляет scope и ссылки на порталы.
   Название метода не объясняет эти побочные эффекты, часть которых выполняется
   даже при выключенной сверке свойств.

   `start(snapshot, true)` в `microfrontend-observer.ts:170` означает, что
   источники событий находятся снаружи. Режим сочетается с необязательным scope,
   но допустимые сочетания не выражены контрактом. В createArea callbacks
   ссылаются на area, объявленную ниже; сейчас это работает благодаря порядку
   вызовов, однако порядок приходится восстанавливать при чтении.

   Упрощение: дать callback имя, отражающее capture; разделить принятие нового
   снимка и сверку свойств; явно назвать режим источников. Создание состояния
   области и запуск сессии сделать последовательными шагами. Сохранить
   освобождение ресурсов и поведение ошибок.

4. **Средний приоритет: повторяются операции над снимками.**

   В `training-observer.ts:122` и `microfrontend-observer.ts:180` полностью
   повторяется вычисление fingerprint. В control/choice builders повторяются
   получение элементов графа, чтение текста и поиск по HTML id. Session и Scope
   отдельно восстанавливают DOM-корни порталов из `relatedRootIds`.

   Упрощение: общая функция сравниваемого содержимого снимка и небольшой набор
   операций чтения графа. Разрешение ссылок в живом DOM оставить отдельно.
   Общий базовый класс для двух наблюдателей ради fingerprint не требуется.

   Важно: существующие способы поиска HTML id неодинаковы. Map в
   `control-snapshot-builder.ts:64` оставляет последнее совпадение, а
   `choice-snapshot-builder.ts:26` требует единственного. При извлечении общего
   кода нельзя незаметно выбрать одну семантику для обоих случаев. Изменение
   политики неоднозначности — отдельная задача с проверкой поведения.

5. **Средний приоритет: технические условия скрывают предметные правила.**

   Примеры: `choice-snapshot-builder.ts:14` и `:54` с вложенными ternary для
   выбора и статуса popup; `dom-observation-session.ts:76` с объединёнными
   условиями маршрутизации и исключения; `dom-observation-scope.ts:59` со
   всеми причинами обновления области в одном методе.

   Упрощение: ранние возвраты и именованные проверки причин — собственные узлы,
   внешние зависимости, границы, общие стили. Для статуса popup записать явные
   ветки native / closed / resolved-open / unresolved.
   Не объединять фильтры discovery, ownership и ignore в одну универсальную
   проверку: они отвечают на разные вопросы. Особенно сохранить различие
   добавленных и удалённых узлов: удалённый узел мог уже сменить родителя.

6. **Средний приоритет: обход DOM трудно просмотреть как последовательность этапов.**

   `services/dom-snapshot-builder.ts:22` содержит build с рекурсивным visit,
   общими счётчиками, геометрией, путями, ограничениями и обходом порталов.
   Замыкание здесь оправдано состоянием одного обхода, но одновременно скрывает
   его состав и инварианты.

   Упрощение: явно описать контекст одного capture; выделить сборку текстового
   узла, элемента и поиск связанных корней. Лимиты и счётчики должны оставаться
   общими для основного дерева и порталов. Не переносить контекст обхода в
   долгоживущие поля singleton-сервиса; кеш геометрии остаётся на один снимок.

7. **Низкий приоритет: стиль и проверки пока не закреплены инструментами.**

   В package.json нет команд lint/format; соответствующих конфигураций в
   проекте не найдено. Встречаются длинные строки, несколько свойств и условий
   на строке. Браузерные тесты повторяют чтение JSON инспектора и поиск контрола;
   отдельного набора unit-тестов чистой проекции сейчас нет.

   Упрощение: отдельно согласовать и автоматизировать форматирование, извлечь
   общие test helpers. Для выделяемых правил добавить небольшие тесты контрактов
   на снимках: приоритет адаптеров, границы members, отсутствие значения и
   неоднозначные ссылки. Реальные браузерные сценарии Taiga сохранить.
   Форматирование всего проекта не смешивать с изменением логики.

Что уже устроено понятно: отдельные DomGeometry и DomElementAnalyzer;
сериализуемые снимки; отсутствие чтения приватных Angular-компонентов;
разделение живого DOM и проекции ControlSnapshot; комментарии о причинах
исключений для scroll, radio и portal. Эти границы нужно сохранить.

Предлагаемый порядок работы:

1. Упростить ControlSnapshotBuilder и расположить правила Taiga рядом с адаптером.
   Первый результат — читаемый поток сборки контрола без изменения публичного JSON.
2. Сделать явным жизненный цикл сессии; вынести повторяющиеся операции снимков.
3. Разделить этапы обхода DOM и именовать правила инвалидации областей.
4. Отдельно закрепить форматирование и облегчить поддержку тестов.

На каждом шаге сохранять публичный API, значения, правила включения узлов,
границы микрофронтов и поведение batching. Обнаруженные изменения семантики
оформлять отдельно. Критерий успеха — правила можно найти и понять локально,
а основной сценарий читается последовательно; уменьшение числа строк не цель.
