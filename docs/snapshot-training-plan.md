# План обучения по состояниям — ветка lib

Дата: 14 сентября 2026. Основание: `lib`, исходный коммит `d514f22`.
Это план следующих изменений; функциональность обучения ниже ещё не реализована.
План ветки `new` и её регистратор действий сюда автоматически не переносятся.

## Решение и границы

Строим обучение поверх снимков состояния. Проверяем ожидаемые значения полей и переходы между
экранами. Журнал кликов для этого MVP не нужен. Пользователь подтвердил: ID экрана уже доступен
в DOM, атрибуте, элементе или URL. Точное место чтения ещё нужно получить на примере целевого UI.

Смена ID подтверждает **достижение экрана**, а не нажатие конкретной кнопки. Если несколько действий
ведут к одному экрану, для этого MVP они эквивалентны. Автопереход backend также наблюдается как
переход состояния; нельзя приписывать его ученику только по DOM. Изменение значения может быть
результатом ввода, автозаполнения или кода приложения. В основном режиме оцениваем состояние,
не утверждаем, что пользователь лично совершил конкретное действие.

Обязательные исходные ограничения сохраняются:

- Не менять целевой интерфейс и не добавлять в него tracking-атрибуты/hooks.
- Существующие атрибуты и связи разрешено читать. UI самой админки можно исключать из наблюдения.
- Библиотека не знает процедур, конкретных MF, маршрутов demo и текстов их кнопок.
- Angular-интеграция владеет ресурсами через DI/DestroyRef; сравнение снимков — чистые функции.
- Библиотека не рисует учебный UI. Админка редактирует сценарии, зона ученика показывает подсказки/alerts.
- Никаких LLM в runtime и Driver.js. Существующую подсветку `DomHighlighter` переиспользуем при необходимости.
- Оптимизацию выполняем после функционального MVP. Angular и зависимости сейчас не обновляем.

## Что действительно есть в lib

| Уже реализовано | Практический смысл |
| --- | --- |
| `TrainingObserver.start()` | По умолчанию снимает `document.body`; можно передать меньший root. Demo-инспектор по умолчанию наблюдает свой root, всю страницу включает отдельно. |
| `DomObservationSession` | MutationObserver, browser events, batching 50 мс и сверка native properties каждые 500 мс по умолчанию. `input/change/focusout` запускают пересканирование; click не слушается. |
| `snapshotFingerprint` | Сравнение сериализованного содержимого снимков без времени/длительности, чтобы не публиковать одинаковое состояние. Это ещё не семантический diff учебных полей. |
| `DomSnapshot` | DOM-граф, текст, свойства, видимость, геометрия, границы и признаки усечения. |
| `ControlSnapshot` | Нормализованные контролы, значения, подписи, locator hints, popup/selection со статусом unknown. |
| Native и Taiga adapters | Поддержка ряда форм, в том числе textbox/number/checkbox/radio/switch/select/combobox. В этой ветке Taiga UI **5.15.0**, а не 4 из прежнего demo. |
| `MicrofrontendObserver` | Отдельные снимки областей, но discovery сейчас жёстко опирается на `[data-mf]`. Для нового MVP это не обязательная зависимость. |
| `DomHighlighter` | Подсветка живых узлов текущего снимка. JSON-копия не сохраняет связи с DOM. |
| Demo и Playwright | Стенды контролов, MF и нагрузки, проверки снимков/адаптеров/lifecycle. Учебной записи, редактора сценария и runtime ученика здесь ещё нет. |

Источники: [observer](../libs/training-observer/src/lib/training-observer.ts),
[обновления](../libs/training-observer/src/lib/services/dom-observation-session.ts),
[fingerprint](../libs/training-observer/src/lib/services/snapshot-fingerprint.ts),
[модель контролов](../libs/training-observer/src/lib/models/control-snapshot.ts).

`n…`, `control:n…` и `mf…` — ID живых экземпляров в текущей сессии. Они меняются после remount
или открытия документа ученика. Структурный `path` также не является долговечным идентификатором.
Текущий fingerprint включает DOM и геометрию; его нельзя использовать как равенство учебных ответов.

## Целевая схема

```text
DOM + существующий источник ID экрана
    → TrainingObserver → DomSnapshot → ControlSnapshot[]
    → ScreenStateReader → состояние активного экрана + качество снимка
    → ControlMatcher + semantic diff
        → режим записи → журнал состояний → редактор → Scenario JSON
        → режим ученика + Scenario JSON → проверка ожиданий → feedback/status
```

Demo и приложение интеграции предоставляют root/правила выбора учебной области и способ чтения ID.
Сканирование всей страницы допустимо, но проверка ограничена выбранным экраном и его контролами.
Соседние приложения, меню и popup не становятся отдельными учебными экранами автоматически.
`[data-mf]` не делаем обязательным: достаточно конфигурации уже существующих DOM-границ.

## Этап 1. Состояние экрана и контракт интеграции

- Добавить конфигурируемый `ScreenIdentityReader`: чтение существующего атрибута/текста/URL в заданном
  контексте. Конкретные селекторы задаёт интеграция. Не зашивать `procedureId` или имя demo-компонента.
- Различать логический ключ экрана и экземпляр/посещение. Возврат A → B → A — новое посещение A,
  а remount A сам по себе не означает следующий учебный шаг. При нескольких плеерах учитывать область.
- Проецировать снимок в `ScreenState`: ключ, посещение, логические поля, качество, состояние
  `ready / loading / unavailable / ambiguous`. Ошибка чтения ID не должна выглядеть как уход с экрана.
- Не считать любой пустой DOM загрузкой или завершением: readiness задаётся наблюдаемыми признаками.
  Усечённый снимок, неизвестный owner popup и отсутствие обязательной цели блокируют оценку.
- Отделить публичный учебный документ от диагностического DOM-графа. Версионировать формат;
  правила capture/redaction/omit применяются до сохранения значений. Unknown не равен пустой строке/false.
- Зафиксировать, что существующие предзаполненные значения удовлетворяют state-based ожиданиям;
  доказательство личного ввода ученика — отдельный режим, которого этот MVP не обещает.

**Приёмка:** один и тот же reader работает на двух разных DOM-структурах через конфигурацию;
дубли ID, remount, загрузка и соседний MF не создают ложный переход. Unit tests добавляются сразу.

## Этап 2. Сопоставление полей и семантическое сравнение

- Построить долговечный `ControlDescriptor` на основе уже имеющихся locator hints:
  тип/role, label, существующие id/name/placeholder и смысловой контекст.
- Приоритет существующего стабильного ID внутри экрана, затем сочетаний семантических признаков.
  ID из генератора Angular не считать устойчивым без проверки. Значение и координаты не входят в identity.
- Проверять уникальность, однозначное соответствие один-к-одному и совместимость типа.
  При необходимости — детерминированная оценка сходства с порогом и отрывом от второго кандидата.
  CSS/path только дополнительные данные; `missing/ambiguous` не исправляются выбором первого элемента.
- Добавить semantic diff: поле появилось/исчезло, изменилось значение/состояние, сменился экран.
  Обёртки, классы, геометрия и внутренности Taiga не должны создавать изменения учебного ответа.
- Сравнивать текущие значения с ожиданиями сценария, а не только с предыдущим снимком. Diff — источник
  изменений; совпадение соседних снимков само по себе не подтверждает правильность.
- Сохранить raw-значения, явную нормализацию number/date и доказанную selection combobox.
  Поисковая строка или список показанных options не подтверждают выбор.

**Приёмка:** сохранённые descriptors работают в новом документе после wrappers/reorder/classes/remount;
одинаковые подписи и недостаток признаков дают отказ. Отчёт измеряет отдельно верные совпадения,
ложные совпадения, ambiguous и missing, без заранее обещанного процента восстановления.

## Этап 3. Запись состояний и понятное demo

- Вернуть структуру demo из `new`: `/` — инструкция, `/record` — админка, `/learn` — тренировка.
  Сохранить существующие стенды под разделом диагностики и обновить тестовые URL; не удалять покрытие контролов.
- Перенести пользовательский поток поиска → открытия динамической формы, сохранив архитектуру снимков `lib`.
  Формы получают экраны от тестового HTTP backend: append полей, замена формы, назад, загрузка и ошибка.
  ID — обычная часть DOM demo-приложения, читаемая конфигурацией, а не специально добавленный locator поля.
- Taiga UI сохраняет версию текущей ветки. Если целевому приложению нужна Taiga 4, её поддержку проверяем
  отдельными адаптерами/fixtures; работоспособность на Taiga 5 не доказывает совместимость с 4.
- Добавить журнал **состояний и переходов**, базовый снимок экрана, pause/resume/stop и сохранение.
  Не называть строки журнала «клик», если наблюдался только результат изменения состояния.
- Ввод остаётся черновиком до focusout. Использовать имеющийся источник focusout как границу подтверждения,
  сохраняя необходимый контекст до batch. Пауза по таймеру не заменяет blur; IME учитывается отдельно.
- На переходе сохранять последнее доказанное состояние уходящего экрана. Если DOM заменён до чтения,
  помечать ответ неполным. Не восстанавливать исчезнувшее значение из догадки или нового экрана.
- Stop завершает запись. Последний экран/переход становится кандидатом завершения; автор меняет его явно.
  Никакого обязательного повторного «признака завершения» без объяснения, что именно он проверяет.

**Приёмка:** через UI можно записать два экрана в произвольном порядке полей, вернуться назад, остановить,
получить JSON и увидеть значения. Тесты включают blur + немедленную замену DOM и A → B → C внутри одного batch.
Потерянный промежуточный экран не подменяется доказанным переходом; путь с недостающими данными требует уточнения.

## Этап 4. Редактор сценария по экранам

- Список экранов и их ожиданий вместо технического DOM-JSON. Тексты заданий/подсказки,
  ожидаемые значения, необязательные поля, явные зависимости, разрешённые ветки и итоговый экран/результат.
- Независимые видимые поля выполняются в любом порядке внутри активного экрана.
  Появление дополнительного поля на том же ID расширяет состав, а не автоматически создаёт другой экран.
- Удаление строки записи, исключение поля из проверки, отмена удаления. Пересборка сохраняет авторские правки;
  конфликт после удаления границы/ожидания показывается, экспорт устаревшего сценария запрещён.
- Текстовая обратная связь на совпадение/несовпадение подтверждённого поля и контрольной точки.
  Checkbox-набор оценивается целиком на настроенной наблюдаемой границе, без ошибок на промежуточные галочки.
- Ручной выбор полей набора через защищённый слой с паузой наблюдения; собственные клики выбора не активируют форму.
  Привязка для этого MVP относится к состояниям, а не к ошибочным кликам соседних кнопок.
- Версионированный JSON, строгая validation, понятные ошибки импорта, сохранение после reload.
  Документы из `new` не принимать молча: там иная семантика действий; импорт требует отдельной миграции.

**Приёмка:** сценарий настраивается без JSON; удаление и отмена, сообщения, условия, наборы и экспорт/import
сохраняют смысл. Автор видит, какие значения/переходы проверяются, и чего наблюдатель доказать не может.

## Этап 5. Прохождение и обратная связь

- Автоматический запуск после загрузки валидного сценария на `/learn`; собственная панель управления
  ученику не нужна. Angular-зона ученика показывает Taiga Alerts/подсказки по событиям headless runtime.
- Сопоставлять текущий экран и его поля со сценарием. Смена ID не обходит обязательные ожидания прошлого
  экрана: для перехода нужны ожидаемая ветка и подтверждённое состояние уходящего экрана.
- Правильное → неправильное значение снимает выполненность. Подтверждение input и сообщения — после blur;
  первоначальная оценка предзаполненного состояния сама по себе не рассылает alerts об успешном «действии».
- Checkbox-набор: проверять целиком на доступной границе (например, уход/переход экрана), используя его
  сохранённое состояние. Если нужна проверка по кнопке без видимого изменения, это отдельное расширение.
- Явно отличать ошибочный ответ, неожиданный экран, loading, missing/ambiguous и неполный снимок.
  Проблема наблюдения не является ошибкой ученика; повторные scans не дублируют сообщения.
- Возврат назад, новый экземпляр формы, остановка/уход, повторная тренировка и поздние обновления не
  продолжают старую попытку. Результат считается достигнутым по сценарию, не по длине записи.

**Приёмка:** запись → редактирование → новый документ ученика → другой порядок полей → ошибка → исправление
→ переход → завершение. Отдельно: автозаполнение, асинхронный переход без клика, неожиданный ID и невозможность
прочитать последнее состояние старого экрана. Все различия видны в диагностике, без ложного зачёта.

## Что снимки принципиально не доказывают

- Нажатие конкретной кнопки, если несколько действий приводят к одинаковому состоянию.
- Клик по справке/скачиванию/действию, которое не оставило наблюдаемого состояния.
- Неудачное нажатие «Далее», если экран остался тем же и не появилось различимого результата.
- Кто изменил значение: ученик, Angular-код, браузерное автозаполнение или backend.
- Значения/экраны, появившиеся и исчезнувшие между capture, и содержимое за пределами снимка/лимита.
- Однозначную идентичность двух неразличимых полей или разных состояний с одинаковым ID экрана.

Для таких задач позднее можно добавить узкий источник подтверждений: наблюдаемый результат, существующее
состояние приложения через DI либо конкретное browser event. Универсальную запись кликов сейчас не строим.
Если необходимо «сначала посмотреть справку», состояние справки должно быть наблюдаемым и сохранённым;
просто наличие той же кнопки в двух снимках не доказывает её использование.

## Порядок работы

Всего **7 этапов**: 5 функциональных, приёмка и затем оптимизация. Первый следующий коммит реализации —
чтение существующего ID экрана и `ScreenState`, без переноса регистратора `new`.
Каждый этап заканчивается видимым результатом/тестами, обновлением этого плана и отдельным коммитом.
Этот документ фиксирует план; исходники, маршруты и зависимости в текущем изменении не меняются.
