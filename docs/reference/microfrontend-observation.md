# Независимое наблюдение микрофронтов

Селектор области настраивается. По умолчанию поддерживаются маркеры `[data-microfrontend]` и прежний `[data-mf]`. Новый
маркер задаёт границу, а `data-microfrontend-name` — её имя:

```html
<div
  data-microfrontend
  data-microfrontend-name="profile"
>
  <input aria-label="Имя" />
  <div
    data-microfrontend
    data-microfrontend-name="address"
  >
    <input aria-label="Город" />
  </div>
</div>
```

Имя не является уникальным ключом. Оно читается из `data-microfrontend-name`, а при отсутствии этого атрибута — из
`data-mf`. Пустое имя допустимо; один `data-microfrontend-name` без маркера не регистрирует область. Если оба маркера
стоят на одном элементе, область регистрируется один раз. Изменение имени обновляет результат без смены ID экземпляра.
Прежняя разметка сохраняет поведение и может использоваться вместе с новой:

```html
<section data-mf="profile">
  <input aria-label="Имя" />
  <section data-mf="address"><input aria-label="Город" /></section>
</section>
<section data-mf="profile"><input aria-label="Другой профиль" /></section>
```

Здесь три независимо наблюдаемых экземпляра. Внутренности address отсутствуют в снимке profile. Один и тот же живой
DOM-элемент сохраняет ID в пределах экземпляра сервиса; замена новым элементом создаёт новый ID даже при прежнем имени.
ID не предназначен для сопоставления интерфейсов админа и ученика.

## API

```ts
import {inject} from '@angular/core';
import {MicrofrontendObserver} from '@training-observer/core';

const observer = inject(MicrofrontendObserver);
// После рендера. По умолчанию искать корни во всём document.body.
observer.start();
// Или ограничить обнаружение контейнером:
observer.start(container, {batchDelayMs: 50, propertyCheckIntervalMs: 500});

observer.areas(); // readonly signal со снимками всех зарегистрированных областей
observer.isObserving();
observer.refresh(id); // запланировать обновление одной области
observer.refresh(); // запланировать обновление всех областей
observer.stop(); // снять слушатели/таймеры, сохранить сериализованные результаты
observer.clear(); // также удалить результаты
```

Подключайте `providers: [provideDomObservation()]` во встраиваемом компоненте: его `DestroyRef` освободит ресурсы.
Автоматической root-регистрации больше нет. Каждая область получает отдельный дочерний injector с browser-сеансом; общие
источники событий остаются у фасада. Повторный start заменяет работающую сессию. Некорректные настройки проверяются до
остановки прежней сессии. После stop изменения областей не отслеживаются; следующий start заново обнаруживает текущие
корни.

Каждая запись содержит `id`, `name`, `parentId`, `snapshot`, `logicalControls`, `scanCount`, `revision`, `error`.
DOM-объекты в публичный результат не входят. Удаление корня или всех совпадающих маркеров удаляет запись из текущего
реестра. Ошибка обхода одной области останавливает её сессию и сохраняет ошибку, не останавливая остальные; для
повторного запуска после ошибки нужен start.

`boundarySelector` можно переопределить; по умолчанию он равен `[data-microfrontend], [data-mf]`. `ignoreSelector`
исключает и снимки, и обнаружение областей: вложенные корни внутри интерфейса наблюдателя не регистрируются. На соседние
компоненты библиотека ничего не записывает.

## Как направляются изменения

На весь реестр создаются один MutationObserver, один комплект делегированных обработчиков и один таймер сверки
native-свойств. Каждая область имеет собственное окно объединения событий и строит только свой снимок. Обычный
`TrainingObserver` по-прежнему доступен для прежнего режима снимка страницы.

| Изменение                                                  | Какие области обновляются                             |
| ---------------------------------------------------------- | ----------------------------------------------------- |
| Ввод, текст, атрибуты, добавление обычного контрола        | Владелец ближайшей границы микрофронта                |
| Содержимое вложенного микрофронта                          | Вложенная область                                     |
| Перенос обычного узла между областями                      | Прежний и новый владельцы                             |
| Добавление/удаление маркера на существующем контейнере     | Реестр и затронутый родитель                          |
| Внешний popup с явным aria-controls                        | Область ссылающегося контрола                         |
| Изменение внешней подписи aria-labelledby/aria-describedby | Области, ссылающиеся на подпись                       |
| Выбор native Radio в общей группе                          | Области вариантов с тем же непустым name и form owner |
| Reset формы, включая внешнюю через form=id                 | Области её native-полей                               |
| Атрибуты общих предков, стили stylesheet, resize окна      | Зависимые области, возможно несколько                 |
| Посторонний блок вне областей                              | Пересчёт снимков не запускается                       |
| Scroll и декоративные hover-переходы                       | Не запускают пересчёт сами по себе                    |

Реестр проверяет появление/исчезновение корней при структурных и атрибутных мутациях. Это поиск областей без
геометрического обхода, а не пересборка всех снимков. Обновления внутри исключённого инспектора отфильтрованы.

Первое открытие Taiga dropdown может добавить общие `<style>` в `<head>` и потому пересчитать все области. Последующие
открытия без новых общих стилей обновляют только владельца popup. Завершение загрузки внешнего stylesheet также
обновляет области: CSS может примениться позже мутации, добавившей `<link>`.

Для позднего появления popup запоминаются и ещё не разрешённые aria-controls открытых контролов. После вставки
подходящего корня обновится владелец. Поля в захваченном popup также проходят сверку native-свойств. Popup внутри
другого корня микрофронта не включается повторно во внешний снимок. Рекурсивные цепочки popup по-прежнему не обходятся;
ID ссылок должны быть уникальны в документе.

В коде `DomObservationScope.acceptsMutation` перечисляет причины обновления в явном порядке: изменение собственных
узлов, появление вложенной границы, атрибуты предков, общие стили, существующие зависимости и ещё не разрешённые ссылки
по id. Проверки вынесены в именованные методы. Для событий отдельно проверяются radio-партнёры и принадлежность полей
форме.

Правила ownership не заменяют фильтры ignore и декоративных изменений в сессии. Добавленные и удалённые поддеревья
проверяются с учётом внешнего контекста: они могут содержать корень области, зависимость, stylesheet или ожидаемый id.
Рефакторинг сохраняет прежние условия и не расширяет список причин пересчёта.

## Ограничение геометрии

Изменение одного микрофронта может сдвинуть соседний через layout, а внешний несвязанный overlay — перекрыть его. Ради
независимости такой косвенный эффект не запускает полный обход соседей. Их координаты и hit-test относятся к последнему
снимку; перед подсветкой используйте `refresh(id)` и дождитесь обновления счётчика. Семантика учебного действия не
должна зависеть от устаревшей геометрии.

Внешние associated labels через HTML for без aria-labelledby пока не внесены в таблицу зависимостей. CSSOM без
DOM-мутаций и изменения layout без событий по-прежнему требуют явного refresh. Это не гарантия знания всей видимой
страницы.

Обход каждой области пока полный. Сверка свойств может искать элементы внутри вложенных корней, но их состояния
проверяются только у владельца. Лимиты относятся к снимку одной области, а не к суммарной стоимости работы реестра.
Нагрузочные замеры для 10 разных областей и стресс-сценарии на 100/300 описаны в
[нагрузочной проверке](load-testing.md).

## Стенд

Запустить `npm start` и открыть `/controls?fixture=microfrontends` (ссылка «Несколько областей» в дополнительных
проверках контролов). Видны profile, вложенный address и employment с настоящим Taiga Select. Карточки показывают
отдельные счётчики, родителя и контролы. Кнопки добавляют второй profile, удаляют области, останавливают реестр и
обновляют снимки.

Асинхронный стенд вынесен на отдельную страницу `/microfrontends`, доступную через основной пункт навигации
**Микрофронты**. Три `div[data-microfrontend]` с отдельным именем появляются последовательно; данные и контролы
добавляются через вторую задержку. Панель показывает состояния `data-load-state` из снимков, принадлежность контролов и
счётчики. Можно заблокировать поля, добавить контрол, удалить или перемонтировать область. Все эти обновления проходят
через обычные источники наблюдения, без ручного refresh. Отмена загрузки и уход со страницы освобождают ожидающие
таймеры. Подробнее — [инструкция demo](../demo-guide.md#асинхронные-микрофронты).

## Области по произвольному селектору

```ts
observer.observe(['microfrontend > some-mf', 'employee-search']);
```

Селекторы задаёт интеграция; новые атрибуты целевого приложения не нужны. Обнаружение учитывает поздний монтаж,
удаление, вложенность и изменение атрибутов, влияющих на совпадение с селектором. Чужие события фильтруются по владению
областью; popup и внешние подписи учитываются по явным связям. Пустой селектор отвергается. Demo:
`/controls?fixture=selectors`.
