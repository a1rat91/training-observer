# Разбор buildDomTree.js и первый перенос в Angular

Исходник: [nanobrowser/buildDomTree.js](https://github.com/nanobrowser/nanobrowser/blob/master/chrome-extension/public/buildDomTree.js).
Прочитан целиком 9 сентября 2026 года: 1505 строк, SHA-256
`3bbbdc5077a9721efbc66e7490df9aa52008e3f0626434a2e4ba87018bb8c7e8`.
Ссылка указывает на изменяемую ветку; номера строк ниже относятся к прочитанной версии.
Код в нашей библиотеке написан заново; полного копирования файла и совместимости его API нет.

## Что делает исходник

Функция получает настройки, обходит `document.body`, описывает элементы и текст,
выбирает потенциальные действия и рисует пронумерованные рамки. Результат —
`rootId` и плоская таблица `map`: дочерние узлы представлены идентификаторами.
Это снимок в момент вызова, а не история действий и не постоянно актуальная модель.

### 1. Настройки и временная память — строки 1–116

`showHighlightElements` управляет видимостью слоя рамок, `focusHighlightIndex` —
выбором рамки для рисования. `viewportExpansion` расширяет область проверки;
значение `-1` отключает некоторые пространственные фильтры. `startId` и
`startHighlightIndex` задают начальные значения двух независимых счётчиков.
`debugMode` распаковывается, но дальше не используется.

Важная особенность API: объект значений по умолчанию работает только при отсутствии
аргумента целиком. Частичный объект не объединяется с defaults, поэтому пропущенные
поля становятся `undefined`.

Внутри каждого вызова создаются `WeakMap` для прямоугольников и computed styles,
таблица результатов, кэш XPath и набор посещённых элементов. Эти структуры не
обеспечивают узнавание узла при следующем вызове.

### 2. Подсветка — строки 125–363

Создаётся фиксированный слой поверх страницы с `pointer-events: none`.
На каждый непустой прямоугольник элемента приходится рамка; отдельная метка
показывает номер. Это полезно для многострочных ссылок, имеющих несколько боксов.
Для iframe добавляется смещение родительского фрейма. Цвет выбирается по номеру.

Каждая подсветка подписывается на `scroll` и `resize`, ограничивает частоту
пересчёта примерно одним вызовом за 16 мс и перемещает рамки. Если количество
прямоугольников уменьшается, лишние рамки скрываются; если увеличивается,
дополнительные рамки не создаются. Функции очистки складываются в глобальный массив,
но общий вызов очистки в этом файле закомментирован.

**Следствие для переноса:** построение снимка должно быть операцией чтения,
а подсветка — отдельным компонентом с общим жизненным циклом и очисткой подписок.
Иначе повторные снимки сами меняют наблюдаемую страницу и накапливают слушатели.

### 3. Структурный путь — строки 371–416

Для элемента вычисляется позиция среди соседей того же тега. Из сегментов
собирается XPath-подобный путь вверх по родителям. На границе Shadow DOM обход
прерывается; у непосредственного ребёнка shadow root путь может оказаться пустым,
поскольку проверка выполняется до добавления текущего сегмента.

Путь зависит от структуры и порядка соседей. Он подходит для диагностики,
но сам по себе не идентифицирует одно и то же поле у администратора и ученика.

### 4. Текст, допустимые теги и видимость — строки 424–532

Текст проверяется через `Range.getClientRects()`, затем через видимость родителя.
Режим `-1` пропускает проверку положения текста, но сохраняет проверку CSS.
`checkVisibility()` имеет fallback на computed styles.

Из обхода исключаются служебные поддеревья, включая `script`, `style`, `template`
и `svg`. Для обычного элемента видимость определяется размерами и CSS
`display`/`visibility`. Проверки элемента и текста различаются: например,
проверка элемента непосредственно не учитывает прозрачность предков.

**Следствие:** «имеет DOM-узел», «отрисован», «в пределах экрана» и «доступен для
взаимодействия» должны быть отдельными состояниями. Нулевая геометрия обёртки не
доказывает отсутствие видимых потомков: пример — `display: contents`.

### 5. Интерактивность — строки 541–782

Это набор эвристик: сначала CSS-курсор, затем HTML-теги, состояния
`disabled`/`readonly`/`inert`, редактируемость, классы и data-атрибуты,
ARIA-роли, доступные сведения об обработчиках, inline-обработчики.

Порядок проверок важен: ранний успех по курсору обходит более позднюю проверку
блокировки. Поэтому `disabled` и `cursor: pointer` могут дать противоречивую
классификацию. Некоторые признаки слишком широкие: курсор текста, `fieldset`,
`legend` или класс `item` не гарантируют отдельное пользовательское действие.

`getEventListeners` относится к инструментам разработчика; `getEventListenersForNode`
должен предоставляться внешним окружением. Обычный микрофронт не получает стандартный
API перечисления чужих `addEventListener`/Angular-обработчиков. Отсутствие признаков
также не доказывает отсутствие действия.

### 6. Проверка перекрытий и viewport — строки 790–933

Сначала ищется непустой прямоугольник в расширенном viewport. Затем для одного
из прямоугольников проверяются центр и две точки около углов через
`elementFromPoint`. Попадание в потомка считается попаданием в элемент.

У Shadow DOM есть отдельная проверка через его root. Для чужого документа
iframe проверка перекрытия фактически заменена успехом. Ошибки hit-test тоже
могут трактоваться оптимистично. Режим `-1` сразу даёт положительный результат
`isTopElement` и `isInExpandedViewport`: это режим охвата, а не доказательство
физической доступности элемента.

**Следствие:** несколько точек — полезное приближение, а не точная проверка всей
видимой площади. В нашем API результат непроверенной геометрии явно отличается
от успешного попадания.

### 7. Быстрый кандидат и самостоятельное действие — строки 966–1160

Быстрая проверка кандидата решает, нужно ли копировать атрибуты узла. Она смотрит
на теги и несколько признаков без дорогого анализа. Проверка `hasAttribute('aria-')`
проверяет буквальное имя, а не наличие любого `aria-*`.

Отдельный набор правил решает, является ли вложенный элемент самостоятельным
действием. Например, иконку внутри кнопки желательно не нумеровать второй раз,
а самостоятельный пункт меню — желательно. Учитываются теги, роли, редакторы,
тестовые атрибуты, обработчики и эвристика классов/контейнеров/видимых детей.
Это приблизительное устранение дубликатов, а не модель составного контрола Taiga UI.

### 8. Назначение номера действия — строки 1183–1225

Интерактивный элемент получает номер, если выше ещё нет подсвеченного действия
или элемент признан самостоятельным. Затем проверяется viewport, назначается
`highlightIndex` и вызывается рисование с учётом фокуса.

Видимость рамки и наличие номера — разные вещи: `showHighlightElements: false`
не отключает всю работу с подсветкой. Флаг о выделенном предке передаётся вниз,
но некоторые специальные ветки передают его иначе, чем обычные дети.

### 9. Сам обход — строки 1234–1495

Обход рекурсивный, с ограничением глубины 100 и `WeakSet` для повторных элементов.
Комментарии и прочие типы узлов пропускаются, собственный слой рамок исключается.
Для верхнего `body` создаётся упрощённый корневой объект, затем обрабатываются дети.
Непустые текстовые узлы сохраняются даже при отрицательном флаге видимости.

После фильтра тегов выполняется ранняя пространственная проверка. Она мягче,
чем кажется по названию: выход за viewport отсекает ветку при отсутствии размеров,
а fixed/sticky-элементы и shadow-host имеют исключения. Атрибуты копируются только
для кандидатов и нескольких специальных тегов. Затем вычисляются видимость,
перекрытие и интерактивность; контейнеры menu/menubar/listbox получают исключение
из проверки перекрытия.

После обхода детей пустые ссылки без адреса и геометрии отбрасываются.
Идентификатор элемента выдаётся при завершении обработки, после детей, а номер
подсветки — раньше. Таблица результатов индексируется ID узлов, не номерами рамок.

### 10. Особые ветки — строки 1405–1480

- **iframe:** добавляются вычисленные размеры; крошечные и далеко смещённые фреймы
  пропускаются; ограничивающий sandbox отмечается заранее; доступный документ
  обходится, ошибка доступа записывается в атрибуты. Это не обход same-origin policy.
- **Редакторы:** contenteditable/TinyMCE распознаются, форматированный текст
  обходится обычными дочерними узлами.
- **Shadow DOM:** читается открытый `shadowRoot`, затем light DOM. Это не полноценное
  flattened/composed tree со слотами; закрытые shadow roots не доступны.

Для вложенных iframe нужны отдельные контексты документов, viewport и координат.
Добавление смещения только ближайшего фрейма недостаточно для общего случая.

### 11. Завершение — строки 1497–1505

Запускается обход `document.body`, очищается временный кэш и возвращаются
корневой ID с таблицей узлов. Комментарий возле очистки говорит о начале,
но фактически очистка стоит после обхода.

### 12. Чего этот файл не даёт нашей задаче

В нём нет `MutationObserver`, записи последовательности событий, сравнения шагов,
стабилизации асинхронных изменений, устойчивого поиска между сессиями и адаптеров
Taiga UI. Атрибут `value` не заменяет текущее свойство `input.value`; то же относится
к `checked` и выбранным option. Перемещение рамок на scroll не обновляет снимок.

Наблюдатель сможет описывать доступную браузеру страницу. Внутренние Angular-модели,
закрытый Shadow DOM, чужие origin и элементы виртуального списка, которых ещё нет
в DOM, из такого обхода не становятся известны. Доработки соседних микрофронтов для
предложенной архитектуры не требуются.

## Что уже перенесено

| Сущность | Ответственность |
| --- | --- |
| `DomSnapshot`, `DomElementSnapshot`, `DomTextSnapshot` | Сериализуемая модель, связи родитель/дети, геометрия, состояние, ограничения |
| `DOM_SNAPSHOT_OPTIONS` | Настройки через Angular DI: глубина, число узлов, текст, слабые эвристики, исключённые области |
| `DomElementAnalyzer` | HTML/ARIA-признаки, базовая подпись и актуальные свойства native-контролов |
| `DomGeometry` | Временный кэш одного обхода, видимость, viewport и проверка перекрытий |
| `DomSnapshotBuilder` | Обход и сборка снимка, `DOCUMENT` через DI, ID через `WeakMap` |
| `TrainingObserver` | Публичный API `capture`, `clear`, readonly `snapshot` signal и computed `controls` |

Временный кэш — обычный внутренний объект, потому что принадлежит одному обходу,
а не injector. Angular-сервисы отвечают за конфигурацию и публичный жизненный цикл.
Наблюдаемые узлы не требуется превращать в Angular-компоненты или снабжать директивами.

`NgZone.runOutsideAngular` отделяет сбор данных от Angular zone, но не переносит
работу в другой поток: большой синхронный обход всё ещё может блокировать интерфейс.
Для больших страниц далее понадобится пакетная/инкрементальная обработка.

Снимок содержит disabled/hidden-контролы. `interactive` — потенциальный контрол;
`pointerActionable` — консервативный результат для текущего указателя, не гарантия
успешного бизнес-действия. `readonly` не приравнивается к `disabled`.
Подпись вычисляется приближённо, без полной реализации Accessible Name Computation.

ID сохраняется, пока живёт тот же DOM-объект и экземпляр builder. Если Angular
заменит узел новым или страница перезагрузится, такой идентичности недостаточно:
поиск одного контрола у разных пользователей будет отдельной задачей.

Снимок не меняет DOM. Данные копируются в обычные объекты, значения password/file
не попадают в `state.value` и атрибут `value`. Другие значения форм сохраняются
в памяти; это не универсальный механизм поиска персональных данных.
Ограничения обхода отмечаются флагом `truncated` и причинами, а не замалчиваются.

## Граница текущего шага и продолжение

Сейчас работает ручной снимок light DOM одного документа, включая DOM обычных
контролов Taiga UI. Это ещё не семантический адаптер всех компонентов Taiga UI:
вложенные labels и кнопки пока остаются самостоятельными узлами.
iframe и открытые shadow roots только отмечаются. SVG-поддеревья исключены.
Слоты, подсветка и автоматическое наблюдение не реализованы.

Следующий небольшой шаг — автоматическое обновление снимка: `MutationObserver`,
делегированные события `input`/`change`, объединение повторных сигналов и гарантированная
очистка через `DestroyRef`. Изменение DOM-свойств без события потребует отдельной
стратегии сверки. После этого — обход границ документов/Shadow DOM и адаптеры
Taiga UI, затем запись и сопоставление учебных шагов.
