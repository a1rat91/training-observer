# Benchmark восстановления ElementDescriptor v2

Этап 8. Этот эксперимент измеряет идентичность DOM-целей. Проверка правильности действий, значений и completion
выполняется отдельно тестами runtime; успешный resolve сам по себе не доказывает бизнес-успех.

## Воспроизведение и файлы

```sh
npm run benchmark:spike
```

Нужны зависимости проекта и установленный Google Chrome. Команда последовательно запускает тесты метрик, статическую
матрицу, два browser tests динамического плеера и публикацию отчётов. Статическая часть поднимает свой локальный сервер
на свободном порту. Для процедуры Playwright использует приложение на 4301 и backend на 4310, запуская их при
необходимости. Пользовательский сервер 4200 не перезапускается.

Временные bundle/JSON находятся в `dist/spike-benchmark`. Публикация происходит только после успешного выполнения всех
частей команды. Зафиксированные результаты:

- [Краткие таблицы](benchmark/RESULTS.md).
- [Полный JSON](benchmark/report.json): версии, hashes, пороги, генерация, каждый результат, locator attempts, причины
  отказов и пять лучших кандидатов resolver.
- [Поэлементный CSV](benchmark/results.csv) и [динамические переходы](benchmark/dynamic.csv).
- [Сводка для интерфейса](benchmark/summary.json).
- В приложении: `/spike/benchmark`, ссылки на скачивание JSON/CSV.

## Набор и границы эксперимента

28 **вариантов целей**, а не 28 независимых библиотечных widgets. Все поля и кнопки созданы реальным Angular с Taiga UI
4: text/email/tel/url/search, placeholder-only и aria-name, textarea, число, дата, select, checkbox, switch, radio,
readonly/disabled, ссылка, icon/button, одинаковые кнопки в fieldset и строках таблицы, две намеренно неразличимые
кнопки. Матрица и её oracle-selectors: `scripts/spike-benchmark/matrix.mjs`.

Это расширение отдельной JIT-формы исследования библиотек. Ручная демонстрация реальных динамических форм доступна на
`/spike/record` и `/spike/learn`; страница benchmark показывает сохранённые измерения, а не запускает тесты кликами.

Дескрипторы создаёт тот же `describe`, который использует ElementRecorder. Контракт не переписан специально под
benchmark. Генерация измеряется на живой Angular-форме. JSON сохраняется и читается с диска, документ записи
закрывается. Для каждого изменения создаётся новый документ с сериализованным Taiga DOM без Angular handlers. Так
измеряется устойчивость locators к структуре независимо от lifecycle; работа handlers, порталов и HTTP проверяется
отдельно.

Oracle — ElementHandle целевого узла в новом документе **до** мутации, включая перестановки. Он доступен только коду
эксперимента. Resolver получает исключительно сохранённый descriptor и DOM-root. Oracle-ключи, selectors, seed и
ожидаемый исход не передаются ему и не записываются в DOM. При удалении oracle остаётся disconnected. При подмене новый
узел намеренно представляет другую сущность, несмотря на совпадающий DOM.

## Изменения и отложенные случаи

Отдельные варианты: wrappers, перестановка блоков/строк, classes, несколько уровней вложенности, icon/span внутри
button, перенос блоков в новые containers и перегенерация id со связями label/ARIA. Два фиксированных сочетания
`combined-17`/`combined-83` меняют глубину и порядок. Seed здесь выбирает два заданных плана, это не случайная выборка.

Негативные и смысловые изменения: переименование кнопки, дублирование формы/контекстов, удаление целей, потеря
различающих legend/rowheader, CSS-ловушка, похожее название другой операции, идентичный DOM другой бизнес-сущности.
Перенос с сохранением семантического контекста относится к layout; потеря бизнес-контекста проверяется отдельно.

Пороги **0.9 / 0.12** и алгоритм resolver взяты из этапа 6 и зафиксированы до этого эксперимента. На результатах
benchmark они не подбирались. Первые 14 целей — развитие предыдущего исследования; следующие 14 — отложенные варианты.
Сводка содержит оба split. Это проверка новых примеров той же формы, а не независимая оценка на другом приложении. Число
прогонов одного DOM не выдаётся за число независимых бизнес-интерфейсов.

## Сравнение и метрики

Сравниваются resolver-v2, `@medv/finder` по умолчанию (CSS baseline), finder без id/classes, `dom-to-locator` и
`@mizchi/selector-generator`. Для всех используется один набор и те же mutated documents. Готовые generators возвращают
свой locator, исполняемый Playwright; дополнительные эвристики ремонта поверх них не добавлены. Это сравнение готовых
стратегий поиска, а не утверждение, что библиотеки обещают self-healing.

- **Correct**: единственное принятое совпадение с oracle для доступной различимой цели.
- **Wrong**: принят чужой узел **или** небезопасно принята цель, которая по протоколу должна быть отклонена. Например,
  `nth-child` может попасть в нужную из двух одинаковых кнопок по случайной позиции; это всё равно false accept. Поле
  `same` в JSON позволяет отделить физически чужой узел от небезопасного совпадения с oracle.
- **Ambiguous / broken**: явный отказ по неоднозначности / отсутствию надёжного результата.
- **Generation-error / query-error**: отдельные исходы, не скрытые под broken.
- **Recovery** = correct / eligible. **Precision** = correct / resolved. Отказы = (ambiguous + broken) / все проверки.
  Ошибки генерации и исполнения включаются в знаменатель eligible, но не в resolved.
- **False accepts**: принятые совпадения на негативных случаях. Знаменатель негативных случаев опубликован отдельно.

В dynamic CSV идентификатор имеет вид `internal:Курс` / `external:Стоимость`, чтобы различать ветки.

В каждом исходном наборе 25 eligible из 28: две неразличимые кнопки и disabled-поле требуют отказа. Readonly-поле
остаётся различимой целью поиска; возможность вводить в него значение — отдельная проверка runtime. Дубликаты, удаление
и потеря контекста уменьшают eligible согласно заранее заданному протоколу. Всего на метод: 476 проверок, 369 eligible и
107 негативных. Все 476 результатов остаются в JSON/CSV и сводке.

Время генерации и resolver измеряется внутри браузера через performance.now; публикация содержит median/p95 и размер
сериализованного descriptor в UTF-8. Для готовых locators query time включает Playwright round trip и проверку oracle —
**напрямую сравнивать эти задержки с in-page resolver нельзя**. Один замер на пару цель/изменение, без статистической
оценки разброса между машинами; значения не являются SLA. Поле `queriedControlCount` содержит число controls,
рассмотренных на входе resolver до visibility/scope filtering; список `candidates` — только top 5.

## Результаты и практический смысл

На структурных изменениях и двух комбинациях resolver восстановил **25/25 eligible целей в каждом варианте**; две
неразличимые кнопки и disabled-поле не приняты. Общая recovery — **368/369 (99.73%)**, precision принятия — **368/369
(99.73%)**. Это процент на данной матрице, не прогноз для произвольного приложения.

Один recoverable отказ — изменение «Продолжить» на «Продолжить оформление»: прежних независимых признаков недостаточно
для порога. Порог ради повышения результата не понижен. CSS-ловушка и операция «Продолжить удаление» не привели к выбору
чужой кнопки. Удалённые/дублированные цели и потерявшие различающий контекст отклонены.

**Один false accept из 107 негативных случаев** — замена сущности при полностью одинаковом наблюдаемом DOM. Роль,
название, атрибуты и контекст не изменились. Никакой DOM-only resolver не может доказать, что новая сущность — другая.
Для этого нужен уже существующий бизнес-идентификатор или разрешённая интеграция. Этот исход включён в wrong и
precision, а не исключён как «неудобный» пример.

## Живой динамический плеер

Два workflow записывают descriptor-снимки разных этапов в JSON, закрывают исходный документ, создают новую процедуру с
другим layout и сверяют найденный Element с oracle на каждом checkpoint. Это прямой benchmark общей функции describe;
полный поток semantic actions ElementRecorder проверяется существующими recording/runtime tests.

Проверяются: identity-форма; отсутствие будущего поля до append и во время удерживаемого HTTP-ответа; поиск после
append; открытый/закрытый портал (владелец select); поля после 422; review после replace; отсутствие прежней цели;
reset. Закрытие dropdown ожидается по исчезновению options: пересечение двух анимаций не принимается за установившийся
экран. Успешный отказ для отсутствующей цели учитывается как broken, а не как успешное восстановление.

Итог живого прогона: **29/29 доступных целей** найдены точно, для **12/12 отсутствующих** получен отказ, ложных
совпадений нет.

Не измерены этим benchmark: произвольные сторонние widgets, закрытый Shadow DOM/iframe, виртуализация с тысячами узлов,
локализация, масштабные изменения терминологии, частично совпадающие реальные бизнес-сущности. Shared DI, Angular model
и endpoint payload не используются для поиска. Финальные границы MVP — этап 9.

## Защита от ложных выводов

Unit tests метрик проверяют unsafe positional acceptance, раздельные знаменатели, ошибки генерации и CSV escaping.
Статический runner завершится с ошибкой при любом новом false accept resolver вне явно выделенной неразличимой подмены;
отчёт при этом сохранится для расследования. Динамические tests требуют точного Element для каждой доступной цели и
отказа для отсутствующей. Существующие unit tests resolver покрывают отрицания/числа в названиях, near ties, конфликты
role/type/attributes, CSS-ловушки и дубликаты. Runtime tests проверяют, что click не означает completion.
