# Этап 3: тестовый плеер процедур

Плеер доступен по [localhost:4200/spike/procedure](http://localhost:4200/spike/procedure), пункт меню **Spike → Плеер
процедур**. Исследование библиотек остаётся на `/spike/research`.

## Запуск и прохождение

```sh
npm start
```

Команда запускает Angular demo на 4200 и локальный Node HTTP backend на **127.0.0.1:4310**. Данные синтетические,
хранятся в памяти процесса и исчезают при его перезапуске. Это эмуляция backend с реальными HTTP-запросами; Angular
interceptor, подменяющий сеть таймером, не используется. Стенд рассчитан на локальную работу, не на размещение на
произвольном хостинге. Если Angular уже запущен отдельно, backend можно поднять командой `npm run procedure:server`.
Если backend уже отвечает на `/health`, `npm start` использует его повторно. При остановке команда закрывает только
процессы, которые запустила сама; уже работающий отдельно backend остаётся запущенным.

1. Нажмите «Новая процедура». Сервер вернёт первую схему формы.
2. Заполните ФИО, почту и выберите вид обучения. «Продолжить» отправляет форму серверу.
3. Внутренний курс: выберите курс и формат участия; наставник и комментарий необязательны.
4. Внешний курс: заполните организатора, стоимость и дату. Для стоимости свыше 100 000 ₽ сервер потребует обоснование
   минимум из 20 непробельных символов. Например, «Обучение необходимо для разработки внутренних приложений».
5. На подтверждении отметьте «Данные проверены» и отправьте заявку. Появятся «Заявка принята» и номер.

«Назад» возвращает принятые данные. Для изменения вида обучения вернитесь к данным сотрудника; переход в другую ветку
очищает данные прежней ветки на сервере. «Сбросить» отменяет ожидание и убирает текущую процедуру с экрана. «Новая
процедура» создаёт независимую серверную сессию. Отмена HTTP на клиенте не откатывает уже выполненную операцию старой
сессии, но её ответ не применяется к новой форме.

В настройках можно выбрать другое расположение и поведение сервера. Настройки действуют со следующей новой процедуры:

| Режим                          | Что происходит                                                                                                     |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| Обычный ответ                  | Создание — 200 мс; действия — 250 мс                                                                               |
| Медленный ответ                | Действия — 1500 мс                                                                                                 |
| Сбой перед сохранением         | Первый next возвращает 503 без перехода; «Повторить» повторяет исходный запрос                                     |
| Потеря ответа после сохранения | Первый next выполнен, но вместо успешного ответа возвращается тестовый 503; retry возвращает сохранённый результат |

Последний режим моделирует потерю успешного ответа посредством 503, а не реальный разрыв TCP. Отдельный browser test
удерживает уже полученный ответ до сброса и проверяет отмену старого ожидания.

## Устройство

- `scripts/procedure-server/service.mjs`: схемы, переходы, validation, revision и requestId. Успешные ответы и 422
  сохраняются по requestId; повтор того же payload возвращает их до проверки revision. Исправленная отправка получает
  новый requestId. Тот же ID с другим payload и устаревшая revision дают 409.
- `scripts/procedure-server/server.mjs`: HTTP endpoint с ограниченным размером JSON, локальным CORS и управляемой
  задержкой. Ограничение памяти — 1000 сессий, затем требуется перезапуск fixture.
- `projects/demo/src/pages/procedure/`: контракт плеера, Reactive Forms (`FormRecord`), рендерер Taiga UI **4.98.0**,
  HTTP-клиент, состояния загрузки/ошибки и отмена устаревших запросов.
- `scripts/start-demo.mjs`: совместный запуск двух процессов.

`append` сохраняет прежние FormControl и DOM-узлы, добавляя поля из полного серверного screen. Принятые исходные поля
становятся недоступны для редактирования. `replace` меняет поколение рендера, уничтожает старые контролы и строит новые.
Второй layout действительно добавляет контейнеры и вложенность, меняет порядок полей и содержимое кнопки. Schema keys
используются внутри рендера, не копируются в DOM как training IDs, data-* или name. У radio обычный value является
значением варианта формы. Метки и заголовки служат пользователю и доступности.

Select показывает label, а HTTP отправляет код (`Внутренний курс` → `internal`, `Angular` → `angular`). Число уходит
JSON number, дата TuiDay — `YYYY-MM-DD`, checkbox/switch — boolean. Эти данные доступны самому плееру; training-панель к
FormRecord, schema и HTTP bodies не подключена.

## Проверка и границы этапа

```sh
npm run test:procedure-api
npx playwright test tests/procedure.spec.ts tests/research.spec.ts
NX_DAEMON=false NX_ISOLATE_PLUGINS=false npx nx build demo --configuration=development
```

Тесты backend проверяют переходы, required/email/date/enum/number, серверное бизнес-правило, retry, revision,
сохранение/очистку принятых данных, неизменяемость исходных полей и реальный HTTP endpoint. Browser tests проверяют обе
ветки, два layout, DOM-идентичность до/после append и replace, wire values Number/Date/Select, 422, возврат, retry и
сброс после принятого сервером запроса. Отдельно сохраняются проверки исследовательской страницы.

Здесь построено целевое приложение эксперимента. Запись training-сценария на этом маршруте, semantic actions,
ElementDescriptor/Resolver и распознавание прохождения ученика выполняются следующими этапами. Полные P01–P22 из
спецификации пока не объявляются выполненными: на этапе 3 проверяется сторона плеера и backend, без training runtime.
Пример с конкурентной формой, неразличимые цели и матрица 20–30 элементов относятся к следующим экспериментам.
