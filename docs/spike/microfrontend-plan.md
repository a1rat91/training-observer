# План: области наблюдения на странице с несколькими микрофронтами

Дата: 2026-09-12. Статус: **план подготовлен; реализация не начата**. Это следующий цикл после завершённого
[spike](./PLAN.md), а не пересмотр его результатов.

Новые вводные: интерфейс меняется редко; страница содержит несколько микрофронтов, обычно
`<microfrontend><some-mf>content</some-mf></microfrontend>`. Нужно наблюдать один небольшой MF или выбранный набор,
подключать/отключать наблюдение, а позднее — при необходимости блокировать взаимодействие с отдельными MF. Driver.js не
используется. Формы demo остаются на Taiga UI 4. Новые tracking-атрибуты/hooks в целевые формы не добавляются.

## Приоритет

Сначала надёжная принадлежность элемента микрофронту, ограничение работы выбранными областями и lifecycle. Существующий
semantic resolver сохраняется как защита от небольших изменений. Редкие обновления UI позволяют перепроверять сценарии
после релиза и явно перепривязывать сломанные цели. Пороги ради «найти любой ценой» не снижаем: неверное совпадение
опаснее понятного отказа.

Область — логический MF, экземпляр области — конкретный смонтированный root. Поле должно находиться внутри своей
области, а не в соседнем MF с таким же label. Селекторы существующих host-тегов допустимы для задания границ; они не
заменяют ElementDescriptor полей и не превращаются в новые маркеры интерфейса.

## Что уже есть и что нужно изменить

Сейчас ElementRecorder принимает один HTMLElement, слушает capture events на document, наблюдает мутации root и каждые
100 мс повторяет reconcile его controls/properties. Resolver тоже получает один root. ScenarioRuntime создаёт
собственные observer и timer. Панель обучения находится снаружи root. Portal owner ищется среди controls root по
существующим aria-controls/aria-owns.

События на document сами по себе не означают полный обход страницы на каждый клик. Главный выигрыш ожидается от
ограничения DOM scans, property polling и повторных resolve. Перенос всех listeners на host MF потеряет события его
dropdown/dialog в общем overlay-контейнере. Поэтому сначала измеряем работу, затем устраняем дублирование observation
между recorder/runtime, сохраняя intent/commit и generation semantics.

## Предлагаемые понятия

| Понятие            | Назначение                                                                                                       |
| ------------------ | ---------------------------------------------------------------------------------------------------------------- |
| AreaDefinition     | Стабильный логический key MF и правило нахождения его host по существующему DOM или разрешённому shell-контракту |
| AreaInstance       | Текущий root, идентификатор экземпляра и поколение mount; DOM-ссылка не сериализуется                            |
| AreaRegistry       | Найденные/отсутствующие/неоднозначные области, mount/unmount/replace, принадлежность узлов                       |
| AreaPolicy         | Независимые `observe: boolean` и `interaction: allowed / blocked`; blocking добавляется позднее                  |
| EventHub           | Один набор capture listeners на document; дешёвый dispatch в разрешённую область по composedPath                 |
| PortalOwnership    | Связь вынесенного popup с областью через доказанного owner, с инвалидированием при закрытии/remount              |
| ObservationSession | Наблюдение выбранного набора областей, порядок событий, очистка и ограниченные ресурсы                           |

Логические keys находятся в конфигурации training, не записываются в атрибуты target DOM. Порядок `<microfrontend>` не
является идентификатором. Два `<some-mf>` без различающего контекста означают ambiguous, а не выбор первого. Общая
обёртка `<microfrontend>` недостаточна: требуется тип дочернего host и, если нужно, существующий instance context.

Для вложенных областей ближайшая зарегистрированная область владеет событием/контролом. Отключённый дочерний MF не
должен автоматически попадать в наблюдение включённого родителя. Неоднозначные или пересекающиеся определения
обнаруживаются до старта; правила не зависят от порядка конфигурации.

## Этап 1. Demo shell с несколькими MF

**Изменения:** добавить общий shell для `/spike/record` и `/spike/learn`, сохранив разные маршруты и формы плеера.
Эмулировать обычную DOM-композицию, без отдельного bundler/federation deployment на этом этапе:

```html
<microfrontend><procedure-mf>динамический плеер</procedure-mf></microfrontend>
<microfrontend><directory-mf>поиск сотрудника и карточки</directory-mf></microfrontend>
<microfrontend><notifications-mf>уведомления и обновляемый счётчик</notifications-mf></microfrontend>
<microfrontend><training-mf>панель записи или прохождения</training-mf></microfrontend>
```

Host-компоненты и обёртки — структура эмулируемого приложения, не tracking hooks. Каждый MF содержит действующие
контролы Taiga UI 4. В соседних MF намеренно повторить подписи «Поиск», «Продолжить», «Комментарий». Training MF всегда
исключён из целевых областей и доступен пользователю.

Добавить тестовые действия shell: перестановка MF, unmount/remount, замена root, фоновое обновление соседнего MF,
поздний mount и дублирование одного типа MF. Настройки эксперимента находятся вне наблюдаемой области.

**Готово, когда:** все MF реально работают на обоих маршрутах; можно пересоздать один MF, не пересоздавая остальные;
плеер продолжает получать динамические поля от HTTP backend. Честно обозначено, что это DOM/lifecycle эмуляция MFE.

## Этап 2. Registry и принадлежность областям

**Изменения:** выделить `libs/element-spike/src/areas/` с определениями, registry и resolver границ. Конфигурация demo
сопоставляет логический key с существующим дочерним host-тегом. Поддержать ноль/один/несколько совпадений, уникальный
контекст для нескольких экземпляров, вложенные области и изменение политики.

Discovery отслеживает структуру известных shell-контейнеров. Если доступен только document, лёгкий childList observer
смотрит появление/исчезновение host, а не извлекает признаки всех controls страницы. Его собственная стоимость тоже
измеряется: отсутствие полного сканирования не означает отсутствие любых callbacks от соседних MF.

**Готово, когда:** перестановка не меняет логический key; remount меняет generation и очищает ссылки; похожее поле
другого MF никогда не становится кандидатом выбранной области; неоднозначный root даёт явную диагностику.

## Этап 3. Выбор наблюдаемых MF и общий dispatch

**Изменения:** добавить в training-панель список областей и переключатели «Наблюдать». По умолчанию включён только
плеер. Сначала подключить registry к существующему recorder/resolver без изменения matching-эвристик.

Сформировать одну observation session с общим EventHub, глобальным порядком/уникальными ID действий и локальным
состоянием областей. Не запускать независимый document listener на каждый MF. Membership проверяется до чтения value,
вычисления accessible name и генерации descriptor. Navigation — событие сеанса, не копия от каждого MF.

MutationObserver/property sampling работают только в включённых областях. Pending input/selection принадлежат экземпляру
области; disable/unmount отменяет неподтверждённые ожидания с диагностикой, не создаёт отложенного «успешного» действия.
Завершённые действия сохраняются. Enable начинает новое поколение и baseline snapshot, не записывая прошлые изменения
как новые действия. Старые tokens не действуют после повторного enable.

Включение нескольких MF не должно нарушить последовательность input commit → click между областями. Для runtime
изменение набора наблюдения не означает пропуск шага: если его область выключена, показать паузу/недоступность.

**Готово, когда:** выбран один MF — значения и действия остальных не записываются; можно добавить второй MF без
перезапуска первого; нет двойных событий, потерянного порядка и принятия старого commit после переключения.

## Этап 4. Portals, контракты и прохождение между MF

**Изменения:** вынести принадлежность popup в общий слой. Option за пределами host учитывается только при доказанном
owner выбранной области. В поиске конкурирующих владельцев учитывать и известные выключенные области, иначе отключение
одного MF может искусственно сделать owner «уникальным». Для этого достаточно индекса ownership-связей; значения
выключенных controls не читаются и semantic recording для них не включается.

Popup без доказанного owner не присваивать активному MF по фокусу, времени или положению. Крупный shared overlay
container нельзя целиком отдать одному MF. Проверить одновременные dropdown разных MF, переиспользование popup IDs,
удаление owner, закрытие popup и remount. Неподдержанные dialogs фиксируются отдельно от поддержанного ARIA dropdown.

В записи/сценарии нужна сохранённая логическая область каждого descriptor. Предлагается отдельная версия wire-контракта
для multi-area, с обновлением validation/import/export и runtime. Не добавлять новые поля в строгий v2 молча. Импорт
прежнего v2 требует явного сопоставления единственной области с выбранным MF; никаких автоматических привязок к
«первому» MF. Поколение и Element остаются только в памяти, не идентичностью будущего прохождения.

Resolver сначала находит однозначную область, затем элемент внутри неё. Поля следующего MF и completion должны ссылаться
на область явно. При потере/выключении нужной области runtime ожидает либо приостанавливается; таймаут, unknown и
ambiguity сохраняются. Remount разрешает повторный поиск по логическому key, но не переносит старый intent.

**Готово, когда:** Recording → JSON → другой маршрут/документ → Scenario работает для двух MF с одинаковыми labels,
порталами и сменой экземпляров. Предыдущие сценарии v2 импортируются через проверяемое сопоставление области.

## Этап 5. Измеряемая оптимизация

**Изменения:** добавить общий scheduler observation, чтобы recorder/runtime не делали независимые полные scans одного
root. После первичного inventory обновлять tracked controls по dirty subtrees; периодически читать properties из
актуального набора, потому что MutationObserver не видит произвольные `.value`/`.checked` изменения.

Не ограничивать sampling только текущим фокусом: backend может менять другие controls выбранной области. Кэшировать
identity до релевантных мутаций; инвалидировать label/ARIA/context dependencies и исключённые дочерние области. Shared
owner index имеет свою invalidation-политику. Полную пересборку оставить безопасным fallback при неопределённом наборе
изменений. Поддерживать лимиты и coalescing, но не выбрасывать semantic commits молча.

Сравнить прежний single-root подход и новый scheduler на одном и том же сценарии: один выбранный маленький MF, несколько
выбранных MF, шумящие соседи, большой плеер и частые remount. Размеры fixtures и seed зафиксировать до замеров.

**Метрики:** число listeners/observers/timers, scans и controls с прочитанными properties, вызовы features/resolve,
работа discovery/ownership, median/p95 обработки и задержки принятия действия, retention узлов после unmount. Стоимость
фонового discovery не смешивать со стоимостью полноценного наблюдения.

**Готово, когда:** рост числа controls в выключенных соседях не увеличивает число читаемых values и кандидатов resolver
выбранного MF; число document listeners постоянно; выключение освобождает локальные ресурсы; все прежние проверки
intent/commit, ambiguity, 422 и поздних ответов проходят. Численный выигрыш публикуется по результатам, заранее процент
ускорения не обещается. Жёсткий CPU-бюджет согласовать по реальному окружению.

## Этап 6. Необязательная политика блокировки взаимодействий

**Отдельное последующее расширение**, после проверки наблюдения и только при подтверждённой потребности. Настройки
observe и interaction независимы: разрешено наблюдать разрешённую область, не наблюдать разрешённую, либо блокировать
выбранную область. Training UI не блокируется.

Перед реализацией определить продуктовый смысл: запрещены только click-активации или любое взаимодействие, включая ввод
и Tab/focus. Не выдавать запрет мыши за полную блокировку формы. Для click-режима проверить pointer, keyboard
Enter/Space, submit/link activation и связанный portal; guard выполняется до semantic recorder. Заблокированная попытка
— отдельная диагностика, не выполненный шаг и не обычный записанный click.

Выбрать механизм по контракту: capture cancellation для ограниченной активации; для полной блокировки — проверить
временный inert/focus management на host и принадлежность вынесенных popup. Это управление взаимодействием, а не
tracking-маркер. Восстанавливать прежние значения/фокус и снимать блокировку при stop/unmount/ошибке; не затирать
изменения host-приложения. Не блокировать всю страницу из-за неизвестного owner popup.

Document listener, зарегистрированный раньше guard, уже мог выполнить побочный эффект. Программные вызовы и HTTP-запросы
клиента такая блокировка не защищает. Если нужна гарантия отсутствия бизнес-действия, потребуется поддержка
shell/приложения; DOM-only blocking не является границей безопасности.

**Готово, когда:** выбранный режим блокировки проверен мышью и клавиатурой, соседние MF продолжают работать,
заблокированная попытка не продвигает обучение, remount не оставляет «залипшую» блокировку и все изменения обратимы.

## Порядок проверки и поставки

Каждый этап — отдельное завершённое изменение с тестами и коммитом. Этапы 1–4 дают работающую multi-area demo; этап 5
измеряет и оптимизирует; этап 6 остаётся отдельной опцией. Реализация настоящей federation-сборки сюда не входит.

Unit tests: registry/ownership и конфликты, политика вложенности, generations, cross-area ordering, отключение
наблюдения и migration контрактов. Browser tests: оба маршрута, реальные Taiga portals/формы, одинаковые подписи, late
mount/remount, шумящий сосед, смена observe во время input/selection и переход сценария между MF. Performance runner
измеряет работу, а не только время загрузки страницы. После каждого этапа обновлять этот документ фактами; не объявлять
completed до соответствующих проверок.

Первое изменение при начале реализации: общий demo shell и три действующих целевых MF, без изменения resolver score и
без политики блокировки. Это позволит проверять последующие изменения в видимом пользователю интерфейсе.
