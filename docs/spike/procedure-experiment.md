# Эксперимент: обучение поверх динамического плеера процедур

Этап 1 из [плана spike](./PLAN.md). Спецификация эксперимента, не отчёт о работающей реализации. Дата: 2026-09-11. Все
данные и правила ниже — синтетический воспроизводимый fixture, а не предположения о реальной бизнес-логике целевого
приложения.

## 1. Проверяемый вопрос

Сможет ли training записать прохождение процедуры администратором, а затем распознать действия ученика, если backend
постепенно присылает поля, Angular пересоздаёт контролы, а структура страницы и задержки отличаются?

Успех — корректно найденная цель и выполненное условие шага. Отдельно измеряем ложные совпадения, неоднозначность и
невозможность поиска. Нажатие «Продолжить», получение HTTP 200 и видимое завершение процедуры — три разных наблюдения.

## 2. Техническая граница и Taiga UI 4

Плеер — обычное Angular-приложение, которое строит Reactive Forms по schema backend. Training — отдельный Angular
microfrontend в том же document. В эксперименте backend эмулирует локальный HTTP-сервис; плеер отправляет реальные
HTTP-запросы. Playwright может управлять ответами для fault injection. Один таймер без HTTP не заменяет этот стенд.

**Все поля и кнопки форм плеера, а также формы training-панели — Taiga UI 4.** Установлены `@taiga-ui/core`,
`@taiga-ui/kit`, `@taiga-ui/cdk` версии **4.98.0**; основные зависимости в package.json используют диапазон `^4.98.0`.
Это текущая база эксперимента, major-версию не обновляем. При замерах фиксируем фактически установленную версию из
lockfile. Старые упоминания Taiga UI 5 в README не соответствуют этой установке.

| Тип schema     | Компонент/директива установленной v4                    | Что проверяем                                          |
| -------------- | ------------------------------------------------------- | ------------------------------------------------------ |
| text, email    | `TuiTextfield`: `tui-textfield` + `input[tuiTextfield]` | Ввод, blur, label, clear                               |
| select         | `TuiSelect`, `input[tuiSelect]`, `TuiDataListWrapper`   | Открытие, выбор мышью/клавиатурой, закрытие dropdown   |
| number         | `TuiInputNumber`, `input[tuiInputNumber]`               | Маска, форматированное отображение, значение           |
| date           | `TuiInputDate`, `input[tuiInputDate]`                   | Ввод даты и выбор в календаре                          |
| textarea       | `TuiTextarea`, `textarea[tuiTextarea]`                  | Многострочный ввод, composition, blur                  |
| radio          | `TuiRadio`, `input[tuiRadio]`                           | Выбор в группе через label/клавиатуру                  |
| checkbox       | `TuiCheckbox`, `input[tuiCheckbox]`                     | checked и повторное переключение                       |
| switch         | `TuiSwitch`, `input[tuiSwitch]`                         | Значение, не зависящее от визуального оформления       |
| действия формы | `TuiButton`, `button[tuiButton]`                        | Click/keyboard activation, loading/disabled, icon/span |

API сверено с `.d.ts` установленной 4.98.0. Обёртки, импортируемые наборы и фактическое поведение dropdown нужно
проверить сборкой и браузерным тестом на этапе 3. Native input внутри Taiga-компонента нормален; голый HTML-select
вместо Taiga Select — нет. Старый черновой target со смесью native-контролов требуется переработать перед подключением.

Плеер может иметь нормальные пользовательские заголовки, labels и accessibility-связи. Нельзя добавлять или исправлять
их специально для успеха training. Негативные fixture намеренно теряют часть этих признаков. Если Taiga генерирует ID
для label/dropdown, можно прочитать текущую связь, но нельзя считать значение этого ID стабильным между сессиями.

| Участник                 | Доступ                                                             |
| ------------------------ | ------------------------------------------------------------------ |
| Плеер                    | HTTP schema, field keys, FormGroup, procedure ID, revision         |
| Training, базовый режим  | DOM/browser events, текущий URL, видимые labels/values/state       |
| Тестовый runner / oracle | Backend fixtures, запросы/ответы, сценарий мутаций, ожидаемая цель |

Training не читает schema, HTTP bodies, Angular debug API, FormGroup и внутренние ключи плеера. Ключи нужны обычному
рендереру, но не копируются в data-*/id/name ради локаторов. Никаких test-only global objects, экспортирующих oracle в
training. Если далее исследуем уже shared DI, его результат будет отдельным режимом, а не улучшением метрики DOM-only.

## 3. Процедура «Заявка на обучение»

Одна процедура, две ветки: «Внутренний курс» и «Внешний курс». Все её экраны работают на одном URL `/spike/procedure`,
поэтому route не различает этапы процедуры.

| Состояние плеера | Видимый экран / поля                                                                                                   | Действие и следующий результат                                       |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| idle             | Кнопка «Новая процедура»                                                                                               | POST create → identity                                               |
| identity         | Форма «Данные сотрудника»: ФИО, Рабочая почта, Вид обучения                                                            | «Продолжить» → загрузка → details-internal или details-external      |
| details-internal | Прежняя форма остаётся; backend добавляет секцию «Внутренний курс»: Курс, Формат участия, Нужен наставник, Комментарий | «Продолжить» → загрузка → review; «Назад» → identity                 |
| details-external | Прежняя форма остаётся; добавлена секция «Внешний курс»: Организатор, Стоимость, Дата начала, Обоснование              | «Продолжить» → validation error либо review; «Назад» → identity      |
| review           | Полная замена формы: «Подтверждение заявки», сводка, checkbox «Данные проверены»                                       | «Продолжить» → загрузка → completed; «Назад» → details текущей ветки |
| completed        | Экран «Заявка принята», номер заявки, кнопка «Новая процедура»                                                         | Новое независимое прохождение                                        |

`pending` — состояние поверх текущего экрана: видимая загрузка, отправка недоступна, данные ещё не считаются принятыми.
Validation error оставляет поля и введённые значения, показывает сообщение рядом с полем. Transport error показывает «Не
удалось получить следующий шаг» и «Повторить». Ни одна ошибка не переводит процедуру вперёд.

В деталях исходные поля видимы, но readonly; «Назад» делает их снова доступными для редактирования. Возврат сохраняет
принятые значения. Смена вида обучения и повторная отправка очищают данные прежней ветки на backend и заменяют состав
дополнительных полей. В review сводка является текстом, а не скрытой копией исходных интерактивных контролов.

## 4. HTTP-контракт тестового backend

Контракт обслуживает плеер. Ни одно поле этого протокола не является training hook. В качестве данных формы принимаются
JSON string / number / boolean / null; select отправляет код выбранного варианта, дата — `YYYY-MM-DD`. Плеер преобразует
Taiga-модели в протокол. Training видит пользовательское отображение, а не код enum или объект даты.

| Запрос                               | Ответ / назначение                                    |
| ------------------------------------ | ----------------------------------------------------- |
| `POST /api/procedures`               | 201: новая процедура, revision 1, identity schema     |
| `POST /api/procedures/:id/actions`   | 200: next/back, новая revision, schema или completion |
| Тот же action с невалидными данными  | 422: field errors; revision и этап не меняются        |
| Action с устаревшей expectedRevision | 409: конфликт; переход не выполнен                    |
| Инъекция сбоя до выполнения action   | 503: можно повторить тот же запрос                    |

`requestId` — ключ идемпотентности в рамках процедуры. Повтор того же ID и payload возвращает сохранённый ответ, а не
выполняет следующий переход. Тот же ID с другим payload — 409. После 422 исправленная отправка имеет новый requestId.
После потери ответа/503 кнопка «Повторить» сохраняет requestId исходной попытки. Проверка уже выполненного requestId
происходит до проверки revision, иначе корректный retry сломается.

Каждый успешный next/back увеличивает revision на 1. В response `screen` всегда содержит полную актуальную schema.
`render` определяет, как применить её к живому UI: `append` сохраняет существующие контролы и добавляет новые, `replace`
пересоздаёт экран. Таким образом, ответ не зависит от истории неявных DOM-patches.

Создание процедуры — пример ответа 201:

```json
{
  "procedureId": "p-admin-001",
  "revision": 1,
  "state": "identity",
  "render": "replace",
  "screen": {
    "title": "Данные сотрудника",
    "sections": [
      {
        "key": "identity",
        "title": "Данные сотрудника",
        "fields": [
          {"key": "employee", "kind": "text", "label": "ФИО", "required": true},
          {"key": "email", "kind": "email", "label": "Рабочая почта", "required": true},
          {
            "key": "trainingKind",
            "kind": "select",
            "label": "Вид обучения",
            "required": true,
            "options": [
              {"value": "internal", "label": "Внутренний курс"},
              {"value": "external", "label": "Внешний курс"}
            ]
          }
        ]
      }
    ],
    "actions": [{"action": "next", "label": "Продолжить"}]
  },
  "values": {}
}
```

Переход к внешнему курсу — request:

```json
{
  "requestId": "request-001",
  "expectedRevision": 1,
  "action": "next",
  "values": {"employee": "Анна Смирнова", "email": "anna@example.test", "trainingKind": "external"}
}
```

В ответе revision 2 / details-external / append `screen.sections` содержит исходную секцию (её поля readonly) и
следующую секцию. Ниже показана именно добавляемая секция, а не полный response:

```json
{
  "key": "external-details",
  "title": "Внешний курс",
  "fields": [
    {"key": "provider", "kind": "text", "label": "Организатор", "required": true},
    {"key": "cost", "kind": "number", "label": "Стоимость", "required": true, "min": 1},
    {"key": "startDate", "kind": "date", "label": "Дата начала", "required": true},
    {"key": "justification", "kind": "textarea", "label": "Обоснование", "required": false}
  ]
}
```

Для internal backend вместо неё возвращает `internal-details`: `course` — select «Курс» с вариантами Angular /
TypeScript; `attendance` — radio «Формат участия» с вариантами Онлайн / Очно; `mentor` — switch «Нужен наставник»,
default false; `comment` — необязательная textarea «Комментарий». Курс и формат обязательны.

Правило серверной валидации: для external `cost > 100000` требует обоснование минимум из 20 непробельных символов.
Базовая required/email/date-валидация выполняется и в плеере, и на backend. Дополнительное бизнес-правило известно
только backend: локально корректная форма действительно отправляет запрос и получает 422.

```json
{
  "procedureId": "p-admin-001",
  "revision": 2,
  "state": "details-external",
  "error": {
    "code": "VALIDATION_FAILED",
    "fieldErrors": [
      {"key": "justification", "message": "Для стоимости свыше 100 000 ₽ укажите обоснование не короче 20 символов"}
    ]
  }
}
```

Успешный next из details возвращает revision 3 / review / replace: сводку принятых данных, checkbox `confirmed` «Данные
проверены» и next/back. Next требует true. Итоговый ответ 200 после подтверждения:

```json
{
  "procedureId": "p-admin-001",
  "revision": 4,
  "state": "completed",
  "render": "replace",
  "completion": {"title": "Заявка принята", "applicationNumber": "EDU-0001"}
}
```

Новая сессия ученика получает другой procedureId и номер заявки. Эти значения не входят в ожидаемый
descriptor/completion predicate. Backend время фиксировано для fixture; пример даты `2027-02-15` не должен зависеть от
системного «сегодня» тестовой машины.

## 5. Что считается действием и завершением training-шага

| Ситуация                  | Запись                                                                             | Условие принятия шага                                                              |
| ------------------------- | ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Печать в text/textarea    | Один input на завершённую серию ввода; composition не порождает промежуточные шаги | Правильная цель и ожидаемое значение после commit                                  |
| Taiga number/date         | Ввод/выбор и наблюдаемое отображение; отдельно результат нормализации              | Сравнение по явно заданному правилу, а не Angular model                            |
| Select: открыть и выбрать | Открытие — click, выбор — select; исходные DOM events остаются диагностикой        | Выбранный label подтверждён в связанном контроле; закрытия popup недостаточно      |
| Checkbox/radio/switch     | Изменение значения, без двойного зачёта click + change                             | Наблюдаемое checked/value соответствует ожидаемому                                 |
| «Продолжить»              | Click по найденной цели                                                            | Действие совпало, но переход ожидает следующий экран/набор полей без ошибки        |
| Backend добавил поля      | DOM/state observation, не действие ученика                                         | Можно начать ждать новую цель, не создавать фиктивный input/select                 |
| Отображён completed       | State observation                                                                  | До отправки этого результата не было; после неё появилась видимая «Заявка принята» |

Для чисел нормализатор заранее фиксирует ru-RU пробелы-разделители и десятичную запятую; для даты — отображаемый формат
DD.MM.YYYY → YYYY-MM-DD. Неизвестный/незавершённый формат не угадываем. Programmatic присвоение default не считается
input пользователя.

У Taiga dropdown выбор может закрыть/удалить option раньше асинхронной обработки. Нужны признаки цели, снятые до
удаления, и связь с владельцем dropdown. Нельзя назначать «последний активный input» владельцем без проверяемых
оснований. Если DOM-связь не восстанавливается надёжно, фиксируем unsupported/ambiguous и исследуем адаптер позже.

Появление «Заявка принята» доказывает только наблюдаемый результат UI. Оно не доказывает транзакцию или
бизнес-идентичность на сервере в произвольном целевом приложении. Test oracle проверяет backend отдельно; training не
получает этот дополнительный источник истины.

## 6. Запись и повторное прохождение

Основная последовательность для external:

1. Администратор включает запись и запускает процедуру.
2. Вводит «Анна Смирнова», `anna@example.test`, выбирает «Внешний курс».
3. Нажимает «Продолжить», ждёт секцию «Внешний курс» из HTTP-ответа.
4. Вводит «Учебный центр», стоимость 150000, дату 15.02.2027; обоснование оставляет пустым.
5. Нажимает «Продолжить», видит серверную ошибку; training не засчитывает переход.
6. Вводит «Обучение необходимо для разработки внутренних Angular-приложений».
7. Повторно нажимает «Продолжить», ждёт пересозданную форму «Подтверждение заявки».
8. Отмечает «Данные проверены», нажимает «Продолжить», ждёт «Заявка принята».
9. Останавливает запись, сохраняет JSON. В сценарии ошибочная попытка из п. 5 является диагностикой/демонстрацией
   валидации, а не обязательным действием каждого ученика.

Для internal записывается второй путь: Курс = Angular, Формат участия = Онлайн, Нужен наставник = true; Комментарий
можно пропустить. Полноценный редактор branching не требуется на этом этапе: ожидаемые пути задаёт fixture, семантика
runtime уточняется на этапе 4. Raw recording и отредактированный training-сценарий — разные артефакты.

Ученик начинает в новом browser context с новым документом, загружает сохранённый JSON сценария. Процедура та же, layout
другой. Никаких Element references, WeakMap-ключей или session IDs администратора в resolver. Правильная цель
определяется oracle отдельно.

Ученик может сразу указать корректное обоснование и не повторять ошибку администратора. Проверяются обе ветки,
optional-комментарий и ошибочное действие по соседнему контролу.

## 7. Контролируемая динамика

| Профиль              | Конфигурация fixture                                                             | Ожидание                                                               |
| -------------------- | -------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| A — запись           | Ответы через 150 мс; базовый layout                                              | Эталонные descriptor/action JSON                                       |
| B — повтор           | Ответы через 900 мс; wrappers, reorder, другие classes, icon/span, новые DOM IDs | Та же семантика и найденная цель после появления                       |
| C — replace          | При переходе пересозданы и ранее видимые контролы; все значения сохраняются      | Старая ссылка detached; resolver ищет новый узел                       |
| D — задержка         | Ответ через 1800 мс; deadline ожидания 3000 мс                                   | waiting → ready, без раннего broken                                    |
| E — timeout          | Ответ позже 3000 мс                                                              | Явный timeout; поздний ответ не продвигает training автоматически      |
| F — ошибка           | Один 503 до commit, затем повтор с тем же requestId                              | Один принятый переход, отсутствие двойного next                        |
| G — потерянный ответ | Backend принял next, ответ потерян, затем retry                                  | Повтор возвращает тот же результат/revision                            |
| H — конфликт         | Ответ предыдущей попытки приходит после back/reset                               | Плеер не применяет устаревший ответ, training отменяет старое ожидание |

Задержки — фиксированные параметры тестового сервера, а не замеры production. Не ждать завершения всей сетевой
активности страницы: readiness определяется текущей целью/условием шага. Короткое окно стабильности DOM проверяется
отдельно от readiness.

Плеер принимает ответ только для актуального экземпляра процедуры и активного запроса; back/reset отменяют ожидание и
помечают прежнюю попытку неактуальной. Это обычная логика плеера. Training отдельно отменяет свои watchers при смене
сценария/шага, не читая requestId плеера. Abort HTTP не гарантирует отмену уже выполненной серверной операции.

Варианты layout задаются fixture плеера, не training. Переносы меняют контейнеры и вложенность, а не только CSS display.
Для части целей сохраняется обычный semantic context; в негативных вариантах он удаляется. Повторяющаяся «Продолжить»
есть на каждом экране; дополнительная форма «Черновик другой заявки» с такой же кнопкой создаёт конкурента. В отдельном
негативном случае у двух форм одинаковы и кнопки, и весь доступный контекст.

## 8. Приёмочная матрица будущих тестов

Это спецификации проверок; сейчас они ещё не реализованы и не выполнены.

| ID  | Проверка                                       | Что обязательно проверить в oracle / training                                                            |
| --- | ---------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| P01 | A → запись → JSON → B                          | Те же бизнес-цели найдены в новом document; oracle не передавался resolver                               |
| P02 | Append после первого next                      | До HTTP-ответа поля нет; после ответа есть; старые поля/значения сохранены                               |
| P03 | Replace после второго next                     | Старые узлы disconnected; новая цель найдена без reuse старой ссылки                                     |
| P04 | Внешняя ветка с 422                            | Ошибка видна, revision не выросла; training остаётся на переходе                                         |
| P05 | Внутренняя ветка                               | Внешние поля отсутствуют; default switch не записан как действие; пользовательское переключение записано |
| P06 | Ввод + IME + blur                              | Финальное значение не потеряно, composition не создал лишние шаги                                        |
| P07 | Taiga Select мышь / клавиатура                 | Корректный владелец, выбранное значение подтверждено; нет двойного select                                |
| P08 | Dropdown вне form + мгновенное закрытие        | Записана исчезающая цель; область наблюдения включает popup, исключает training UI                       |
| P09 | Number/date: маска и commit                    | Ожидаемое значение нормализовано явно; промежуточная маска не завершает шаг                              |
| P10 | Checkbox через label / radio клавиатурой       | Одно изменение значения; нет фиктивного двойного click/change                                            |
| P11 | Задержки D/E                                   | waiting не равен broken; timeout и отмена не засчитывают поздний результат                               |
| P12 | 503 / потеря ответа / двойной click            | Один backend transition; число сырых событий не равно числу завершённых шагов                            |
| P13 | Back, смена ветки, next                        | Прежние branch fields удалены; stale watcher не продвигает новую ветку                                   |
| P14 | Reset до ответа                                | Новый procedureId/DOM; старый response и watcher не изменяют новый сценарий                              |
| P15 | Две различимые кнопки «Продолжить»             | Неверная форма не принимается; правильная определяется доступным контекстом                              |
| P16 | Две неразличимые кнопки                        | ambiguous с кандидатами; никакого выбора первой/ближайшей                                                |
| P17 | Удалена цель, её CSS занят другим контролом    | Нет false positive; waiting/timeout/broken по жизненному циклу шага                                      |
| P18 | Состояние поменялось без input/change          | Наблюдаемое состояние обновлено отдельно; не приписано действие ученику                                  |
| P19 | Optional-комментарий, корректный ввод сразу    | Пропуск optional разрешён; ошибочную попытку администратора повторять не нужно                           |
| P20 | Финальная отправка с ошибкой / успехом         | До видимого результата нет completion; success UI и backend success проверены раздельно                  |
| P21 | Stop/start/unmount training                    | Нет оставшихся listeners/таймеров, повторной записи или подсветки старой цели                            |
| P22 | Смена сущности без изменения видимых признаков | Не заявлять различение бизнес-идентичности по DOM; оформить границу метода                               |

## 9. Артефакты и следующий этап

На этапе 3 по этой спецификации появятся плеер, тестовый HTTP backend и независимые smoke tests. На этапах 5–7 будут
записанные JSON, browser tests recorder/resolver и прохождения A/B. Матрица 20–30 элементов и количественный benchmark
остаются этапом 8; процедура не заменяет этот отдельный тест устойчивости.

Здесь завершена только спецификация этапа 1. Следующий этап по плану — короткие воспроизводимые browser probes библиотек
и исследование с решением по зависимостям.
