# Сценарий и прохождение — этап 7

Маршруты: `/spike/record` — запись и подготовка; `/spike/learn` — новое прохождение с тем же компонентом плеера.
`/spike/procedure` остаётся плеером без training UI. Это композиция Angular-компонентов в demo, не production packaging
микрофронтендов. Training не получает FormRecord, ключи серверной схемы, HTTP payload и внутреннее состояние плеера.

## Как пройти полный цикл

1. На странице записи нажать «Начать запись» и «Новая процедура». Выполнить успешный workflow до результата.
2. Нажать «Остановить запись», затем «Выбрать признак завершения» и щёлкнуть по заголовку «Заявка принята» в плеере.
   Выбирается существующий доступный DOM-элемент; tracking-атрибуты не добавляются. В режиме выбора только выбранный
   клик перехватывается, чтобы он не выполнил действие приложения.
3. Нажать «Создать черновик сценария». Проверить JSON: задания `instruction`, подсказки `hint`, ожидаемые значения,
   `optional`, `branches`, `nextStepId`, completion шагов и всего сценария. Визуального graph editor пока нет.
4. Нажать «Сохранить и открыть прохождение». Проверенный JSON сохраняется в localStorage этого origin под ключом
   `training-spike-scenario-v2`; learner открывается отдельным маршрутом. Можно открыть `/spike/learn` в другой вкладке
   того же браузера или вставить JSON вручную. Это локальная передача, не публикация сценария на сервер.
5. В плеере ученика выбрать другое расположение/поведение сервера **до** запуска. Нажать «Начать обучение» и следовать
   заданиям справа. «Подсказка» показывает только заранее сохранённый текст. «Начать заново» создаёт новый runtime;
   первую новую процедуру пользователь начинает кнопкой плеера по заданию.

Запись и Scenario — разные документы v2. Скачивание записи осталось доступным. Исходная запись не считается сценарием
сама по себе: черновику необходим явный признак результата и проверка администратором.

## Семантика черновика

`draftScenario` создаёт линейную последовательность. Input/select получают condition на записанное значение; если есть
normalized, используется оно. Click ожидает видимость цели следующего действия; последний click ожидает выбранный
признак результата. Navigation получает явный pathname. Пропущенные/скрытые значения и запись с диагностикой не
преобразуются автоматически: программа не выдумывает ожидаемые значения.

**Completion кликов требует проверки автором.** Следующая цель может уже существовать до клика, а выбранный заголовок —
быть видимым всегда. Такие условия не доказывают выполненную бизнес-операцию. Нельзя считать черновик автоматически
верным или выбирать общий заголовок приложения как признак успешного результата. Для demo заголовок «Заявка принята»
действительно появляется только из успешного HTTP-ответа; generic runtime этого знания о backend не имеет.

Один черновик описывает записанную ветку. Объединение веток, optional и сложные completion задаются в JSON вручную.
Валидатор проверяет структуру, ссылки и типы, но не доказывает бизнес-корректность написанного сценария.

## Runtime

`libs/element-spike/src/runtime/` использует XState 5 для состояний: `waiting`, `ready`, `confirming`, `ambiguous`,
`broken`, `timedOut`, `finalizing`, `completed`, `stopped`.

- При входе в шаг resolver заново ищет цель. Пока backend её не прислал, состояние `waiting`, а не окончательный
  `broken`. Неоднозначность не разрешается DOM-порядком. Структурно неподдержанная цель/identity conflict
  диагностируются.
- Before-handler callback recorder проверяет identity и пригодность элемента. Каждый input burst/выбор хранит
  неперсистируемый token текущего поколения шага. Commit возвращает **тот же token**, даже если узел удалён
  обработчиком. Элемент, token и Event не попадают в Scenario JSON. При skip, retry и переходе поколение меняется:
  поздний commit старого шага не засчитывается даже для того же DOM-узла в новом шаге.
- Предыдущие input/selection подтверждаются до привязки следующего намерения. Это сохраняет порядок при быстром переходе
  от Taiga dropdown к «Продолжить».
- Только совпавшее действие активирует completion. Предварительно заполненное поле или программное изменение свойства не
  заменяют действие ученика. Некорректное committed value не активирует шаг и вызывает сообщение о несоответствии.
- Для input/select committed value служит evidence текущего шага, в том числе если поле сразу исчезло. Оно не является
  общей историей значений для будущих шагов. Другие value conditions читаются из текущего DOM. Raw/normalized
  сравниваются явно; секреты остаются redacted и не могут удовлетворить raw-value условие.
- `MutationObserver` и property polling по 100 мс повторяют проверку completion и цели. Training-панель находится вне
  наблюдаемого root. Target references после мутации не переиспользуются для resolver.
- Нажатие «Продолжить» активирует ожидание результата. При 422 или transport error следующий контрол отсутствует — шаг
  не продвигается. «Повторить» может завершить ту же ожидающую операцию после появления нужного DOM. Runtime не читает
  ни status HTTP, ни requestId; их проверяет отдельный протокол плеера.
- Условия имеют три результата: true/false/unknown. Неизвестное значение не считается false ради выбора default branch.
  Несколько true branches означают ambiguity, наличие unknown не позволяет принять решение, одна true и остальные false
  выбирают ветку, все false используют nextStepId.
- Optional пропускается только явной кнопкой и переходит на nextStepId. Автоматического пропуска отсутствующего поля
  нет.
- Конец графа переводит в `finalizing`. `completed` возможен только после отдельного глобального completion.
- Timeout ограничивает ожидание поля/результата, но не время размышления над доступным заданием. После timeout нужно
  явно повторить ожидание. Stop/unmount отключают observers/listeners/timers; restart создаёт независимый runtime.

Для conditions resolver получает отдельные опции: можно прочитать disabled/readOnly значение и найти статические
heading/region/status. Для действий по умолчанию требуются интерактивные доступные цели; readOnly input не принимается
как готовый к вводу. Расширение observable pool не заставляет recorder записывать клики по всем заголовкам.

Соответствие `/spike/record` → `/spike/learn` задаётся явной направленной парой. Проверка pathname не выключается
глобально. Другой URL без пары не считается тем же экраном. Query/hash пока не входят в navigation v2.

## Проверки и границы

Unit tests проверяют ожидание append, pre-removal click/input, отсутствие прогресса от одного state, wrong values,
независимое глобальное completion, duplicates, timeout/retry, stop и поздние мутации, optional и старый commit на том же
элементе, branch ambiguity, disabled conditions, authoring и гонку dropdown → следующий click.

Browser tests записывают процедуру через UI, выбирают результат, сериализуют Scenario, **закрывают документ записи** и
проходят сценарий в новой вкладке. Проверяются оба workflow, другой layout, slow response, lost response/retry,
ошибочное ожидаемое значение и серверная 422 с исправлением. Отдельный тест задерживает настоящий HTTP-ответ,
останавливает и запускает новый runtime, затем доставляет старый ответ: прогресс нового прохождения остаётся нулевым.
JSON — единственная передаваемая training-информация.

```sh
npm run test:spike
npx playwright test tests/learning.spec.ts tests/recording.spec.ts tests/procedure.spec.ts tests/research.spec.ts
NX_DAEMON=false NX_ISOLATE_PLUGINS=false npx nx build demo --configuration=development
```

Ограничения остаются: DOM не доказывает скрытый серверный бизнес-успех; неизвестные custom controls требуют проверяемого
adapter; polling может пропустить краткий переход. Runtime наследует лимиты recorder на объём наблюдения; при его
остановке показывает ошибку и требует нового запуска. Захват до обработчика доказан для обычных обработчиков плеера, но
чужой document-capture listener, сработавший раньше observer, может уже изменить DOM — без интеграции универсальной
гарантии порядка нет. Полноценные persistence/публикация/MFE packaging/graph editor не реализованы.

Это интеграционный spike. Полный benchmark 20–30 целей и калибровка resolver относятся к этапу 8.

Результат проверки 2026-09-11: **120 unit tests и 20 browser tests прошли**, TypeScript, ESLint и Angular development
build прошли. Визуально проверена панель ученика на живой форме Taiga UI. Процент восстановления на benchmark пока не
измерен и из этих проверок не выводится.
