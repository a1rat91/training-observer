# Training Observer: план технического spike

Статус: **пошаговое выполнение; этапы 1–2 завершены, следующий — этап 3**. Обновлено: 2026-09-11.

## Цель

Экспериментально установить, насколько надёжно можно записывать действия администратора и распознавать действия ученика
поверх существующего Angular-приложения без изменений его интерфейса ради отслеживания. Главная проверка — **плеер
процедур с динамическими формами**: пользователь заполняет поля, backend присылает следующие, состав и структура DOM
меняются в процессе.

Результат spike — работающий проверяемый эксперимент, сравнительные измерения и границы применимости. Production-система
обучения, полноценный редактор сценариев и инфраструктура публикации в этот объём не входят.

## Зафиксированные ограничения

- Не менять целевое приложение ради training: никаких data-* атрибутов, специальных hooks, директив, тестовых
  идентификаторов и других добавленных маркеров.
- Автоматические служебные изменения DOM библиотекой подсветки (например, классы Driver.js) допустимы. Запрещены
  маркеры/локаторы, добавленные специально для распознавания целей; служебные классы подсветки не используются в
  ElementDescriptor или similarity.
- Training UI — отдельный Angular microfrontend сбоку, работающий в том же document.
- Некоторые уже существующие Angular DI dependencies могут быть shared. Их доступность нужно проверить; не предполагать
  заранее доступ к модели формы или состоянию процедуры.
- Все поля и кнопки форм плеера и training UI используют **Taiga UI 4**. Текущая установленная версия основных пакетов —
  **4.98.0**. Проверяем реальные компоненты и их dropdown по
  [документации v4](https://taiga-ui.dev/v4/getting-started/). Старый черновик с голыми HTML-контролами перед
  подключением нужно переработать.
- DOM, классы, вложенность, порядок и контейнеры нестабильны. DOM-узлы могут пересоздаваться.
- Runtime детерминированный, без LLM; платные DAP не используем.
- CSS/XPath не могут быть единственным доказательством идентичности.
- При недостаточных признаках или близких кандидатах — диагностируемый отказ, а не угадывание.
- Серьёзность recorder оцениваем корректностью работы с динамикой, событиями и состояниями, а не наличием или
  отсутствием rrweb. Набора простых click/input listeners недостаточно как доказательства жизнеспособности решения.

## Как двигаемся

Один этап — один ограниченный результат с проверкой. Статус обновляется в этом файле. Не начинать одновременно UI,
recorder, resolver и сценарный движок. После этапа фиксировать: что сделано, как проверено, какие вопросы остались.
Непроверенный код не считать завершённым этапом. Проценты восстановления публиковать только после реального
воспроизводимого запуска.

## Этап 1. Зафиксировать эксперимент с плеером процедур

**Статус:** завершён — [спецификация эксперимента](./procedure-experiment.md).

Проверено: установленная Taiga UI 4.98.0 и API выбранных контролов; согласованность переходов, revision/retry/back,
границы DOM-only наблюдения; синтаксис JSON-примеров. Результат: две ветки процедуры, append/replace,
validation/transport errors, прохождения администратора/ученика и 22 приёмочные проверки. Плеер и эти тесты ещё не
реализованы.

Определить небольшой, но реалистичный workflow и HTTP-контракт тестового backend:

1. Начало процедуры: поля сотрудника и выбор типа заявки.
2. Отправка данных, состояние ожидания, ответ backend с дополнительными полями.
3. Новые поля добавляются в текущую форму; часть прежних сохраняется.
4. Следующий ответ полностью заменяет экран новой формой.
5. Значение предыдущего поля выбирает одну из двух веток процедуры.
6. Backend может вернуть ошибку валидации; шаг не считается успешно завершённым.
7. Финальный ответ показывает подтверждённый результат процедуры.

Для прохождения учеником подготовить вариант той же процедуры: другие задержки, wrappers, порядок полей, классы,
пересоздание контролов и повторяющиеся кнопки «Продолжить». Нужны также возврат к предыдущему экрану и повтор запроса.

**Результат:** `procedure-experiment.md` — состояния, payload-примеры, последовательности администратора/ученика,
ожидаемые наблюдения и негативные случаи.

**Критерий готовности:** каждое событие имеет понятный смысл; отдельно определены действие, изменение отображаемого
состояния и успешное выполнение операции. Не предполагается, что training знает содержимое backend-ответов или
внутренний ID процедуры.

## Этап 2. Завершить исследование и выбрать минимальные зависимости

**Статус:** завершён — [исследование](./research.md), [полный JSON-отчёт](./library-probes.json).

Проверено: 14 целей × 9 DOM-вариантов × 4 generator configurations = 504 comparisons; живой Taiga Select с rrweb,
Driver.js highlight/rebind/cleanup и XState guards/cancellation. Выбраны dom-accessibility-api, проверяемый finder
fallback, адаптация dom-to-locator для authoring, rrweb для диагностики записи, XState и Driver.js для соответствующих
слоёв. Это не измерение собственного resolver и не полный benchmark устойчивости.

Ниже исходные вопросы исследования; итоговые решения и ограничения — в research.md.

| Кандидат                   | Что проверить                                                                  | Предварительная гипотеза, ещё не итог                                                        |
| -------------------------- | ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| Playwright generator       | Генерация role/name/label/context, uniqueness, positional fallback             | Использовать идеи; не тащить Node/browser automation в runtime                               |
| dom-to-locator             | Browser API, несколько candidates, ограничения/размер, поведение после мутаций | Возможен адаптер генерации; locator string не равен runtime resolver                         |
| @mizchi/selector-generator | API, комплектность extraction, версии/лицензия, те же fixture cases            | Сравнить с dom-to-locator, не включать оба без причины                                       |
| @medv/finder               | CSS uniqueness и ложные совпадения после reorder                               | Только fallback с независимой проверкой identity                                             |
| dom-accessibility-api      | Accessible name, implicit role, labels, расхождения с браузером                | Использовать вместо самодельного полного AccName                                             |
| Healenium                  | Сохранение признаков, ранжирование, recovery threshold, инфраструктура         | Заимствовать подход; Java/Selenium backend не подходит для browser runtime                   |
| rrweb                      | Snapshot/replay, события, mirror IDs, стоимость, masking                       | Подключать, если помогает анализу записи; сам по себе не решает identity между прохождениями |
| XState                     | Guards, branches, optional steps, ожидание/ошибки, отмена                      | Кандидат для сценарного runtime MVP после проверки ядра                                      |
| Driver.js                  | Highlight живого Element, interaction, dropdown, scroll, cleanup               | Кандидат для подсказок; не resolver и не критерий завершения шага                            |

**Результат:** `research.md` с первичными ссылками, точными версиями/лицензиями, результатами коротких browser probes и
решением use / adapt / defer / reject.

**Критерий готовности:** выбор обоснован проверками. Отдельно обозначено, что только прочитано в документации, а что
действительно испытано.

## Этап 4. Уточнить модель данных и контракт наблюдения

**Статус:** есть непроверенный черновик модели.

Спроектировать сериализуемые и версионируемые:

- `ElementDescriptor`: несколько locator candidates, role, accessibleName, text, label, placeholder, допустимые
  attributes, semantic ancestor/context, CSS fallback, fingerprint.
- `SemanticAction`: click/input/select/navigation, цель, порядок, время и политика значений.
- `ObservedState`: состояние контрола отдельно от его identity.
- `Resolution`: resolved / ambiguous / broken с evidence и кандидатами.
- Ожидание шага: ещё не появился / готов / неоднозначен / сломан / истёк timeout / отменён.

Значение поля и позиция в DOM не должны автоматически становиться identity. Разделить уникальность сейчас и устойчивость
между прохождениями. Определить политику для repeated labels, контекста строки/секции и конфликтующих признаков.

**Результат:** `contracts.md` и минимальные TypeScript-типы, после ревизии черновика.

**Критерий готовности:** JSON round-trip, отсутствие DOM references в сохранённом сценарии, понятные границы DOM-only и
необязательного адаптера уже shared DI.

## Этап 5. Реализовать и проверить ElementRecorder

**Статус:** черновик; не проверен на workflow.

- Capture-phase / composedPath: находить интерактивный контрол при клике на icon/span.
- Сохранять необходимые признаки до удаления или изменения элемента обработчиком приложения.
- Input bursts, change/blur, IME composition, checkbox/radio, native select, Taiga dropdown.
- Различать намерение пользователя и подтверждённое изменение state.
- Наблюдать DOM-мутации: появление полей, замену узлов, dropdown вне формы.
- Не превращать каждый MutationRecord в semantic action.
- Отдельно обработать изменения DOM properties, которые не видит MutationObserver.
- Проверить навигацию, быстрые последовательности и порядок событий при async-ответах.
- Исключать собственный training UI по владению DOM-root, без маркеров в основном приложении.
- Start/stop/dispose, отсутствие дублирования listeners и утечек.
- Значения секретов не сохранять; политика остальных значений явная.

**Результат:** recorder + unit tests + запись реальной процедуры в браузере.

**Критерий готовности:** ожидаемая последовательность совпадает с записью; повторная отрисовка/ответ backend не создают
фиктивных действий пользователя. Все пропуски и неподдержанные custom controls явно диагностируются.

## Этап 6. Реализовать и проверить ElementResolver

**Статус:** есть черновик; пороги предварительные.

1. Проверить scope/экран и пригодность элемента.
2. Попробовать semantic locators с проверкой uniqueness.
3. Перейти к другим сохранённым candidates, затем CSS fallback.
4. Проверять identity даже при единственном совпадении locator.
5. При поломке locators построить пул кандидатов и deterministic similarity ranking.
6. Учесть коррелированные признаки: label/name/text не три независимых доказательства.
7. Проверить абсолютный порог, разрыв между двумя лучшими и конфликты признаков.
8. Возвращать evidence и отказ при недостаточной уверенности; DOM order не разрешает tie.

**Результат:** resolver + unit tests на позитивные и опасные негативные случаи.

**Критерий готовности:** CSS, который начал указывать на другой элемент, не принимается без проверки. Удалённая цель не
заменяется ближайшим похожим контролом. Порог — score, а не заявленная вероятность правильного совпадения.

## Этап 7. Проверить связку на динамической процедуре

**Статус:** не начат.

- Запись администратора → сериализация → новый документ/новое прохождение ученика.
- Runtime видит текущий шаг и ожидает поле, которое backend ещё не прислал.
- После append/replace заново находит цель, не использует старый Element reference.
- Разные задержки, повтор запросов, validation error и обе ветки процедуры.
- Смена ветки/шага отменяет старые ожидания; поздний ответ не завершает новый шаг.
- Dropdown портален и может исчезать сразу после выбора.
- «Продолжить» нажато ≠ операция выполнена. Completion проверяется отдельно.
- Если один DOM не позволяет доказать бизнес-успех, явно фиксируется ограничение, а не имитируется гарантированное
  определение результата.

**Результат:** интеграционные browser tests и демонстрация двух прохождений.

**Критерий готовности:** нет преждевременного продвижения, ложного broken во время нормального ожидания и зачёта
ошибочного действия. Timeout и ambiguity видны пользователю.

Мутации отдельно и в комбинации:

- wrappers;
- reorder;
- смена classes;
- изменение вложенности;
- icon/span внутри button;
- перенос в другой container;
- полное пересоздание узлов и новая загрузка документа;
- изменение подписи, дубликаты, удалённая цель, потеря контекста, ловушка старого CSS.

ради красивого процента. Отдельная таблица для динамических переходов процедуры.

**Результат:** benchmark runner, полный JSON/CSV отчёт и краткая таблица результатов.

**Критерий готовности:** команда воспроизводится; отчёт соответствует фактическому запуску; есть поэлементные результаты
и тесты против silent false positives.

## Этап 9. Сформулировать MVP и границы применимости

**Статус:** не начат.

Предлагаемые границы модулей для проверки результатами spike:

`Host DOM/events → observation + adapters → recorder / resolver → scenario runtime → training UI`

В MVP сценарий содержит текст задания, заранее заданные подсказки, ожидаемые значения, optional steps, branches и
completion conditions. В spike достаточно определить модель и показать ограниченный runtime для экспериментальной
процедуры. Полноценный редактор и все варианты сценарной семантики не строить до результатов измерений.

Оценить XState для execution/guards/cancellation и Driver.js для highlight по уже найденному Element. Независимо решать
вопросы packaging microfrontend, shared DI и persistence. Сравнить чистый DOM режим и возможное использование уже
доступных shared dependencies; не выдавать улучшенный интеграционный результат за DOM-only.

Отдельно описать случаи без надёжного восстановления:

- одинаковые элементы без различимых labels, attributes или semantic context;
- смена текста/контекста/доступных признаков до неразличимости;
- прежнее обозначение теперь принадлежит другой бизнес-сущности;
- виртуализированный элемент не существует в DOM, либо строка переиспользована;
- повторяющиеся экраны процедуры без наблюдаемого признака текущего состояния;
- серверный успех не отражён в доступном DOM/browser state;
- custom controls с закрытым внутренним состоянием, canvas/closed shadow DOM;
- cross-origin iframe и недоступные события/состояния;
- локализация или динамическое содержимое уничтожают сохранённые признаки.
