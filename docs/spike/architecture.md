# Итоговая архитектура MVP

Статус: решение этапа 9, 2026-09-11. **Conditional go: ограниченный пилот на плеере процедур.** Универсальный DAP без
интеграции и без отказов не подтверждён. Все девять этапов технического spike завершены; production-система и реальный
deployment микрофронтендов не являются его результатом.

## Основания решения

[Benchmark](./benchmark.md) содержит 2380 сравнений: 28 вариантов Taiga UI 4 целей × 17 изменений × 5 методов. Для
resolver выполнено 476 проверок: 368 correct, 1 wrong, 58 ambiguous, 49 broken. Recovery — 368/369 eligible (99.73%);
precision — 368/369 принятых результатов (99.73%). Неразличимые и недоступные цели не исключены из отчёта. Структурные
изменения сохранили 25/25 различимых доступных целей в каждом варианте. Отложенные 14 вариантов дали 193/193 eligible,
но это дополнительные примеры той же формы, не проверка другого приложения.

Единственный false accept — новая бизнес-сущность с полностью одинаковым наблюдаемым DOM. Один recoverable отказ —
переименованная кнопка. Пороги 0.9/0.12 оставлены без подгонки; score не является вероятностью. Нельзя переносить 99.73%
на произвольный интерфейс или считать этот результат основанием для автоматической аттестации сотрудников.

На живом HTTP-плеере в новом документе: 29/29 доступных целей найдены, 12/12 отсутствующих отклонены, false accepts — 0.
[Runtime tests](./scenario-runtime.md) отдельно проверяют неверные значения, 422, задержки, retry, поздний ответ после
restart, optional/branching и независимое completion. Качество поиска и правильность сценария — разные проверки.

## Границы модулей

| Модуль                  | Вход и ответственность                                               | Что существует в spike                                                |
| ----------------------- | -------------------------------------------------------------------- | --------------------------------------------------------------------- |
| Contracts               | Версионированные Recording/Scenario/Resolution, строгая валидация    | `libs/element-spike/src/contracts/`, v2                               |
| DOM identity            | Role, accessible name, labels, context, допустимые attributes        | `src/dom/identity.ts`, без Angular/Taiga imports                      |
| Observation / recorder  | User intent + DOM/property state → подтверждённые semantic actions   | `src/recording/`; свойство value наблюдается отдельно от событий      |
| Resolver                | Descriptor + текущий root → Element либо ambiguous/broken с evidence | `src/resolution/`, свежий поиск и проверка конфликтов                 |
| Authoring               | Recording → редактируемый Scenario с явным результатом               | `src/runtime/authoring.ts`, линейный черновик и JSON editor           |
| Scenario runtime        | Текущий шаг, ожидаемое действие, условия, ветки, ожидание и отмена   | `src/runtime/`, XState + собственная логика условий/поколений         |
| Training UI             | Запись, редактирование, задания, заранее заданные подсказки          | `/spike/record`, `/spike/learn`; композиция компонентов demo          |
| Persistence / MFE shell | Версии сценариев, публикация, mount/unmount, права и progress        | Не реализовано; localStorage/sessionStorage служат локальной передаче |

Пути `src/…` в таблице относятся к `libs/element-spike`. Старые файлы непосредственно в корне этой библиотеки и
`projects/demo/src/pages/spike` — ранние черновики, не основа нового пакета. Перед выделением production-пакетов
перенести только принятые модули v2 и их тесты.

## Работа с динамическими формами

Запись должна наблюдать намерение пользователя и подтверждение результата контрола. Одних click/input/change
недостаточно: Taiga Select меняет value без native input/change. Recorder использует capture events, composedPath,
MutationObserver и опрос DOM properties. Программное изменение value создаёт state, но не действие ученика. Portal
option связывается с единственным owner через существующий ARIA-контракт; элемент вне root не становится частью
процедуры только потому, что по нему кликнули.

На входе в шаг runtime заново разрешает descriptor. Если поля ещё нет, он ожидает мутацию/состояние в пределах таймаута.
После подходящего действия проверяется отдельное completion. В примере «Продолжить» недостаточно: появление следующего
поля подтверждает видимый переход; 422 или transport error не продвигают шаг. Смысл HTTP-ответа generic runtime не
читает.

Capture callback фиксирует поколение шага до обработчика. Commit input/selection возвращает исходный token, включая
случай удаления узла обработчиком. Skip/retry/смена шага инвалидируют старый token. Stop/unmount отключают
listeners/observers/timers; restart создаёт новый runtime. Это не отменяет запросы плеера: DOM-only слой не владеет ими.
Ранний чужой document-capture listener всё ещё может изменить DOM до нашего наблюдения.

Условия дают true/false/unknown. Несколько подходящих веток — ambiguity; неизвестная ветка не превращается в false ради
default-перехода. Optional пропускается явно. Конец графа не завершает обучение без глобального completion. Committed
value относится только к текущему шагу; скрытые значения прошлых форм не восстанавливаются из истории автоматически.
[Подробная семантика](./scenario-runtime.md).

## Поиск и управляемый отказ

Descriptor хранит несколько типизированных locators и fingerprint из наблюдаемых признаков. Приоритет semantic locators
не отменяет проверку identity: даже единственный CSS-результат может быть чужим. Resolver проверяет совместимость
роли/типа, name/href, бизнес-контекст и разрыв между двумя лучшими кандидатами. Имена, label и text считаются
коррелированным свидетельством, а не тремя независимыми доказательствами.

Если сохранённые locators не дают проверенного уникального результата, допустим deterministic similarity matching внутри
разрешённого контекста. Изменение бизнес-контекста не считается обычным переносом layout. При недостаточных признаках
runtime показывает отказ и останавливает зависимый переход. Администратор исправляет привязку в новой версии сценария;
runtime не переписывает descriptor автоматически по найденной догадке.

В текущей реализации resolver вычисляет признаки пула даже при работающем semantic locator, чтобы обнаружить
конкурирующие цели. Поэтому semantic-first здесь означает приоритет принятия locator, а не обещание быстрого
short-circuit. Оптимизация через общий индекс/dirty sets — отдельная работа после профилирования большого плеера.

## Решение по библиотекам

Версии ниже — проверенные версии проекта, не рекомендация обновиться до latest. Полные исходные probes и лицензии:
[исследование](./research.md), [версии и hashes benchmark](./benchmark/report.json).

| Решение                           | Библиотека                                                   | Причина и статус                                                                                                 |
| --------------------------------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| Оставить в ядре                   | dom-accessibility-api 0.7.1                                  | Общий расчёт accessible name/role вместо собственной реализации AccName                                          |
| Оставить fallback                 | @medv/finder 4.0.2                                           | CSS без id/classes, обязательно с повторной проверкой identity; не единственный идентификатор                    |
| Оставить runtime                  | XState 5.32.6                                                | Явные фазы и lifecycle; смысл действий, условия и идентичность реализует наш код                                 |
| Использовать для тестов           | Playwright 1.62.1                                            | Реальный браузер, oracle сравнивает Element, исполняет locators библиотек                                        |
| Оставить comparators              | dom-to-locator 1.0.0, @mizchi/selector-generator 1.50.0-next | Хорошее восстановление layout, но unsafe positional/substring acceptance; в рабочем recorder v2 не интегрированы |
| Оставить опциональную диагностику | rrweb 2.1.4                                                  | Replay помогает расследованию; mirror ID не годится для следующего прохождения, snapshots не являются действиями |
| Исключить                         | Driver.js                                                    | По решению пользователя удалён из зависимостей и demo; подсказки текстовые                                       |
| Только идеи                       | Healenium                                                    | Ranking, история признаков, threshold, отчёт о repair; Java/Selenium-стек здесь не запускался                    |

Это уточняет предварительное решение этапа 2: адаптация dom-to-locator для authoring **не обязательна для MVP**. Текущий
типизированный descriptor уже прошёл benchmark. Добавлять генератор следует только при подтверждённой пользе на реальном
контроле, преобразуя поддержанные стратегии в наш контракт, без eval строк и позиционной автоматической привязки.
[Публичный API dom-to-locator](https://github.com/gajus/dom-to-locator) возвращает Playwright locators; это не готовый
browser runtime нашего Scenario.

XState подходит для lifecycle: invoked actor останавливается при выходе из родительского состояния.
[Документация actors](https://stately.ai/docs/actors). В spike XState хранит фазы, а наблюдение и generation tokens
управляются классом ScenarioRuntime; они ещё не оформлены как отдельные invoked actors. При таком рефакторинге нужно
сохранить существующие cancellation tests. Платный редактор Stately для исполнения не требуется.

Подсказки показываются заранее заданным текстом в боковой панели. Driver.js исключён по решению пользователя; подсветка
и альтернативная библиотека overlay в MVP не планируются. Исторические probes остаются в отчёте этапа 2.

[Healenium Web](https://github.com/healenium/healenium-web) рассчитан на Selenium-based tests. Мы не переносим его
runtime и не включаем AI/XPath repair. В исполняемом пути проекта нет LLM и платного DAP; external models не нужны для
генерации условий, подсказок или выбора кандидата.

## Packaging отдельного Angular MFE

Предлагаемый первый production-контракт — shell монтирует training UI рядом с плеером в том же document. Ему нужны
training mount point, существующий root плеера, документ сценария и явное соответствие маршрутов записи/прохождения. Это
API оболочки обучения, не hooks полей. Если shell не может передать существующий root, training должен найти его по уже
доступному уникальному контексту; неоднозначный root означает отказ от старта. Добавлять атрибуты целевым полям ради
этой задачи нельзя.

Общее ядро остаётся TypeScript/DOM без Angular DI. Angular-обвязка выполняет наблюдение вне своей зоны, обновляет панель
по snapshot и гарантирует dispose на смене маршрута/root. Новый root после remount получает новый сеанс наблюдения.
Training UI не включается в выборку контролов плеера. Стили панели ограничены её контейнером; совместимость Taiga
overlay/root, global styles и версий Angular нужно проверить на настоящей оболочке.

Spike не выбирает за целевое приложение Module Federation, Native Federation или другой loader: его текущая схема не
известна. Сначала использовать существующий способ загрузки MFE. Сам факт shared npm dependency не гарантирует общий
Angular injector или экземпляр сервиса. Требуется проверка token identity, injector hierarchy и lifecycle в целевой
сборке. Установка отдельного MFE и нагрузка такого размещения ещё не проверены.

## DOM-only и режим с shared dependency

| Режим                            | Источник истины                                  | Требования                                                                                 |
| -------------------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| DOM-only, реализован             | Доступный DOM, свойства и browser events         | Наблюдаемые identity, значение и completion; допустим явный отказ                          |
| Shared adapter, только предложен | Уже доступный публичный сервис/observable плеера | Явно согласованные версии API, capability и lifecycle; отдельные tests и маркировка режима |

Полезные возможности интеграции: procedure instance ID, текущая revision/стадия, business field ID, semantic value
custom widget и подтверждённый результат операции. Они помогают только если уже есть доступный контракт и доказано
соответствие поля DOM business ID. Знание schema field ID само по себе не объясняет, какому из двух одинаковых input он
соответствует. Приватное Angular-состояние, ng-reflect/debug APIs и перехват HTTP не становятся контрактом MVP.

`ObservationMode` уже различает режимы, но shared adapter runtime сейчас отклоняется как неподдержанный. API adapters
ещё не реализован. Для будущей интеграции предусмотреть проверку возможностей перед стартом; отсутствие необходимого
сервиса не должно молча понижать точность до DOM-only. Сохранённые сценарии и отчёты должны указывать режим и версию
adapter. Интеграционные показатели измеряются отдельно.

## Authoring и persistence MVP

Запись — журнал, сценарий — задания и проверяемые условия. Подготовка из Recording требует явного признака результата;
черновик линейный и отражает только записанную ветку. Его click-completion по видимости следующей цели необходимо
проверить: цель могла существовать до клика. Повторные input commits не обязательно должны становиться отдельными
учебными заданиями. В MVP нужен редактор, где автор может объединять/удалять такие действия, менять ожидаемые значения,
добавлять optional/ветки и отдельно проверять глобальное завершение. Это предложение, не описание готового UI.

Для пилота зафиксировать envelope вокруг Scenario v2: immutable revision, статус draft/published, набор совместимых
версий приложения/adapter, автор и результат контрольного прохождения. Не добавлять эти поля в строгий Scenario v2 без
изменения wire-контракта. Сценарий ученика привязывается к опубликованной версии; редактирование создаёт новую.
Состояние прогресса хранится отдельно от Scenario и от DOM-ссылок. Resume требует проверки текущего состояния плеера, а
не слепого восстановления номера шага.

LocalStorage и sessionStorage в demo — транспорт между маршрутами одного origin, не persistence службы обучения. Перед
пилотом определить серверное хранение сценариев/progress и доступ автора/ученика, какие записанные значения можно
сохранять, срок хранения и удаление. Секреты не превращать в expected values; rrweb snapshots включать отдельно для
диагностики с проверкой содержимого. Raw значения учебной записи не должны автоматически становиться шаблоном для
реальных персональных данных другого сотрудника.

## Следующие работы после spike

Это новый backlog MVP, не незавершённые этапы технического исследования.

| Порядок | Работа                                                   | Критерий выхода                                                                                                    |
| ------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 1       | Пилот на одном реальном workflow и его реальных controls | Согласована матрица наблюдаемости и негативные случаи; точно известен источник completion                          |
| 2       | Встраивание через существующий MFE shell                 | Запись и прохождение в отдельных маршрутах; root/remount/portal/dispose проверены без маркеров в плеере            |
| 3       | Недостающие adapters и облегчение observation            | Browser fixtures для каждого контрола; измерены нагрузки типичной и большой формы, нет незаметной потери действий  |
| 4       | Редактор шагов и проверка автором                        | Сценарий можно подготовить без ручного JSON, все ветки имеют контрольное прохождение, неоднозначные привязки видны |
| 5       | Версии, публикация, progress и политика данных           | Новая версия не меняет активное прохождение; импорт/rollback/resume и доступ проверены                             |
| 6       | Доступность панели                                       | Задания, подсказки и ошибки доступны с клавиатуры и screen reader; панель не перехватывает ввод плеера             |

Критерии допуска **предлагаются для пилота**, не объявляются выполненными: ноль false accepts на согласованном наборе
наблюдаемых негативных случаев; точный Element и completion во всех обязательных шагах выбранного workflow; явные отказы
при неизвестном состоянии; сохранение поздних-event/reset тестов; измеренный бюджет CPU/памяти на реальной оболочке. Не
наблюдаемые DOM-only шаги либо получают интеграцию, либо исключаются из автоматического зачёта. Если бизнес требует
безошибочного скрытого подтверждения при запрете такой интеграции, решение для этого workflow — **no-go**, независимо от
процента benchmark. [Полный список ограничений](./limitations.md).
