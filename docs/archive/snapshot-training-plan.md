Это план развития и история этапов. Актуальная структура пакетов описана в [ARCHITECTURE.md](../../ARCHITECTURE.md).

## Уточнение размера demo

По последнему решению первый экран `/record` содержит только один Input, один Select и один ComboBox.
Большую форму проверяем отдельными тестовыми fixtures, а не на основном экране demo.
Остальные экраны и навигация сохранены.

## Обязательный пользовательский цикл и текущее состояние

Администратор начинает запись, заполняет поля и переходит между экранами, завершает запись,
редактирует ожидания/сообщения и сохраняет сценарий. Ученик открывает отдельную страницу тренировки:
наблюдение запускается автоматически и сравнивает его подтверждённые значения и переходы с этим сценарием.
Внутри одного экрана независимые поля можно заполнять в любом порядке.

**Сейчас есть запись в админке:** старт/завершение, журнал подтверждений полей и посещений экранов,
сохранение завершённого документа после reload и JSON для копирования. `confirmedControls` остаётся
источником последних blur-подтверждений; `StateRecorder` строит из них отдельный журнал.
Из полной записи теперь можно создать и отредактировать ожидания, сохранить сценарий и запустить `/learn`.
Базовая проверка значений/переходов и Taiga Alerts подключены; расширения этапов 2–5 ещё остаются.

В ветке `lib` запись действий означает подтверждённые изменения полей и наблюдаемые переходы экранов.
Input, Select и ComboBox подтверждаются после blur. Конкретные клики, не оставляющие наблюдаемого
результата, эта модель не записывает. Тренировка оценивает записанные ожидания, а не воспроизводит клики.

## Решение и границы

Строим обучение поверх снимков состояния. Проверяем ожидаемые значения полей и переходы между
экранами. Журнал кликов для этого MVP не нужен. Пользователь подтвердил: ID экрана уже доступен
в DOM, атрибуте, элементе или URL. Точное место чтения ещё нужно получить на примере целевого UI.

Смена ID подтверждает **достижение экрана**, а не нажатие конкретной кнопки. Если несколько действий
ведут к одному экрану, для этого MVP они эквивалентны. Автопереход backend также наблюдается как
переход состояния; нельзя приписывать его ученику только по DOM. Изменение значения может быть
результатом ввода, автозаполнения или кода приложения. В основном режиме оцениваем состояние,
не утверждаем, что пользователь лично совершил конкретное действие.

Обязательные исходные ограничения сохраняются:

- Не менять целевой интерфейс и не добавлять в него tracking-атрибуты/hooks.
- Существующие атрибуты и связи разрешено читать. UI самой админки можно исключать из наблюдения.
- Библиотека не знает процедур, конкретных MF, маршрутов demo и текстов их кнопок.
- Angular-интеграция владеет ресурсами через DI/DestroyRef; сравнение снимков — чистые функции.
- Библиотека не рисует учебный UI. Админка редактирует сценарии, зона ученика показывает подсказки/alerts.
- Никаких LLM в runtime и Driver.js. Существующую подсветку `DomHighlighter` переиспользуем при необходимости.
- Оптимизацию выполняем после функционального MVP. Angular и зависимости сейчас не обновляем.

## Что действительно есть в lib

| Уже реализовано | Практический смысл |
| --- | --- |
| `TrainingObserver.start()` | По умолчанию снимает `document.body`; можно передать меньший root. Demo-инспектор по умолчанию наблюдает свой root, всю страницу включает отдельно. |
| `DomObservationSession` | MutationObserver, browser events, batching 50 мс и сверка native properties каждые 500 мс по умолчанию. `input/change/focusout` запускают пересканирование; click не слушается. |
| `snapshotFingerprint` | Сравнение сериализованного содержимого снимков без времени/длительности, чтобы не публиковать одинаковое состояние. Это ещё не семантический diff учебных полей. |
| `DomSnapshot` | DOM-граф, текст, свойства, видимость, геометрия, границы и признаки усечения. |
| `ControlSnapshot` | Нормализованные контролы, значения, подписи, locator hints, popup/selection со статусом unknown. |
| Native и Taiga adapters | Поддержка ряда форм, в том числе textbox/number/checkbox/radio/switch/select/combobox. В этой ветке Taiga UI **5.15.0**, а не 4 из прежнего demo. |
| `MicrofrontendObserver` | Отдельные снимки областей, но discovery сейчас жёстко опирается на `[data-mf]`. Для нового MVP это не обязательная зависимость. |
| `DomHighlighter` | Подсветка живых узлов текущего снимка. JSON-копия не сохраняет связи с DOM. |
| Demo и Playwright | Стенды контролов, MF и нагрузки, проверки снимков/адаптеров/lifecycle. Базовый цикл записи, редактора и runtime ученика теперь включён в проверки. |

Источники: [observer](../../libs/training-observer/src/lib/training-observer.ts),
[обновления](../../libs/training-observer/src/lib/services/dom-observation-session.ts),
[fingerprint](../../libs/training-observer/src/lib/services/snapshot-fingerprint.ts),
[модель контролов](../../libs/training-observer/src/lib/models/control-snapshot.ts).

`n…`, `control:n…` и `mf…` — ID живых экземпляров в текущей сессии. Они меняются после remount
или открытия документа ученика. Структурный `path` также не является долговечным идентификатором.
Текущий fingerprint включает DOM и геометрию; его нельзя использовать как равенство учебных ответов.

## Целевая схема

```text
DOM + существующий источник ID экрана
    → TrainingObserver → DomSnapshot → ControlSnapshot[]
    → ScreenStateReader → состояние активного экрана + качество снимка
    → ControlMatcher + semantic diff
        → режим записи → журнал состояний → редактор → Scenario JSON
        → режим ученика + Scenario JSON → проверка ожиданий → feedback/status
```

Demo и приложение интеграции предоставляют root/правила выбора учебной области и способ чтения ID.
Сканирование всей страницы допустимо, но проверка ограничена выбранным экраном и его контролами.
Соседние приложения, меню и popup не становятся отдельными учебными экранами автоматически.
`[data-mf]` не делаем обязательным: достаточно конфигурации уже существующих DOM-границ.

## Этап 1. Состояние экрана и контракт интеграции

**В работе.** Реализованы `readScreenState` (существующий атрибут или прямой текст корня),
статусы чтения, ограничение полей поддеревом экрана и `ScreenVisitTracker`.
Проверены разные конфигурации DOM, дубли, remount, loading, усечение и возвраты.
В demo `/record` уже есть компактная форма, три экрана заполнения, результат, неправильная ветка
и карточки подтверждённых значений из снимка всей страницы. Базовая запись этапа 3 теперь подключена.

**Следующий шаг:** завершить контракт интеграции: отдельный источник ID (включая URL),
политика качества для границ обхода/неизвестных значений и публичный сохраняемый учебный формат
с правилами исключения значений. Затем — сопоставление полей и semantic diff (этап 2).
Текущий `ready` означает, что прочитан единственный корень с ID; это ещё не разрешение
засчитать все ответы. Ошибка HTTP в demo сохраняет предыдущий экран и не создаёт посещение.

Проверка этого среза: production-сборка библиотеки и demo, 8 unit-тестов, полный прогон
86 браузерных тестов (включая 4 новых) прошли. Новые browser cases проверяют реальные Taiga
значения, возвраты, неправильную ветку, remount, неоднозначность, загрузку и повтор после HTTP-ошибки.

- Добавить конфигурируемый `ScreenIdentityReader`: чтение существующего атрибута/текста/URL в заданном
  контексте. Конкретные селекторы задаёт интеграция. Не зашивать `procedureId` или имя demo-компонента.
- Различать логический ключ экрана и экземпляр/посещение. Возврат A → B → A — новое посещение A,
  а remount A сам по себе не означает следующий учебный шаг. При нескольких плеерах учитывать область.
- Проецировать снимок в `ScreenState`: ключ, посещение, логические поля, качество, состояние
  `ready / loading / unavailable / ambiguous`. Ошибка чтения ID не должна выглядеть как уход с экрана.
- Не считать любой пустой DOM загрузкой или завершением: readiness задаётся наблюдаемыми признаками.
  Усечённый снимок, неизвестный owner popup и отсутствие обязательной цели блокируют оценку.
- Отделить публичный учебный документ от диагностического DOM-графа. Версионировать формат;
  правила capture/redaction/omit применяются до сохранения значений. Unknown не равен пустой строке/false.
- Зафиксировать, что существующие предзаполненные значения удовлетворяют state-based ожиданиям;
  доказательство личного ввода ученика — отдельный режим, которого этот MVP не обещает.

**Приёмка:** один и тот же reader работает на двух разных DOM-структурах через конфигурацию;
дубли ID, remount, загрузка и соседний MF не создают ложный переход. Unit tests добавляются сразу.

**Уточнение подтверждения:** для Input/Number/Select/ComboBox добавлен отдельный `confirmedControls`
после выхода фокуса. Карточки используют его; сырые снимки продолжают обновляться.
Базовые сравнение ожиданий и runtime подключены; расширенная проверка долговечной identity ещё впереди.

## Этап 2. Сопоставление полей и семантическое сравнение

**Первый срез:** `matchControl` с порогом/отрывом, semantic hints без значений/геометрии,
отказ при неоднозначности и конфликте один-к-одному. Unit tests проверяют новые сессионные ID,
переименование подписи при стабильном ID, дубли и несовместимые типы. Полная матрица DOM-мутаций
и отдельный semantic diff ещё не выполнены; проценты восстановления не заявляем.

- Построить долговечный `ControlDescriptor` на основе уже имеющихся locator hints:
  тип/role, label, существующие id/name/placeholder и смысловой контекст.
- Приоритет существующего стабильного ID внутри экрана, затем сочетаний семантических признаков.
  ID из генератора Angular не считать устойчивым без проверки. Значение и координаты не входят в identity.
- Проверять уникальность, однозначное соответствие один-к-одному и совместимость типа.
  При необходимости — детерминированная оценка сходства с порогом и отрывом от второго кандидата.
  CSS/path только дополнительные данные; `missing/ambiguous` не исправляются выбором первого элемента.
- Добавить semantic diff: поле появилось/исчезло, изменилось значение/состояние, сменился экран.
  Обёртки, классы, геометрия и внутренности Taiga не должны создавать изменения учебного ответа.
- Сравнивать текущие значения с ожиданиями сценария, а не только с предыдущим снимком. Diff — источник
  изменений; совпадение соседних снимков само по себе не подтверждает правильность.
- Сохранить raw-значения, явную нормализацию number/date и доказанную selection combobox.
  Поисковая строка или список показанных options не подтверждают выбор.

**Приёмка:** сохранённые descriptors работают в новом документе после wrappers/reorder/classes/remount;
одинаковые подписи и недостаток признаков дают отказ. Отчёт измеряет отдельно верные совпадения,
ложные совпадения, ambiguous и missing, без заранее обещанного процента восстановления.

## Этап 3. Запись состояний и понятное demo

**Частично реализован:** `StateRecorder`, версионированный `StateRecording`/parser, начало/завершение,
журнал, сохранение в браузере и три страницы demo. Диагностика MF/нагрузки перенесена в fixtures
страницы контролов, её тесты сохранены. На `/learn` подключена базовая проверка по отдельно сохранённому сценарию.

**Остаётся:** первый выбор Taiga ComboBox без DOM-доказательства (явный пропуск, не догадка по тексту), базовые состояния и политики предзаполненных полей, pause/resume с честными разрывами,
IME/быстрые переходы, запись последнего доказанного состояния при всех вариантах remount.
Перед подключением ученика нужны оставшиеся контракты этапа 1 и долговечное сопоставление этапа 2.
Базовая запись не закрывает эти этапы и не доказывает восстановление поля между документами.

Проверка среза записи: production-сборка и 16 unit-тестов прошли. В полном browser-прогоне
88 тестов прошли; дополнительное ожидание доказанного выбора закрытого ComboBox оказалось неверным
для текущего DOM-контракта. Тест уточнён на явный пропуск вместо ложного подтверждения;
оба теста записи после уточнения прошли. Регрессии MF проверены по новым URL внутри `/controls`.

- Прибраться в demo: оставить ровно три страницы в маршрутах и меню:
  `/controls` — контролы и их диагностика, `/record` — запись и редактирование администратором,
  `/learn` — прохождение учеником. `/` перенаправляет на `/record`; отдельная страница инструкции не нужна.
  Краткая инструкция находится на странице записи.
- Удалить лишние страницы `/microfrontends` и `/load`, их маршруты, пункты меню и неиспользуемый demo-код.
  Нужные проверки MF/нагрузки перенести в тестовые fixtures или сценарии страницы контролов;
  сохранить покрытие библиотеки, обновить маршрутные тесты и документацию. Чистка относится к этапу 3,
  а не к отложенной оптимизации. Не добавлять страницу ученика с неработающими кнопками:
  до этапа 5 она честно сообщает о недоступности прохождения.
- Перенести пользовательский поток поиска → открытия динамической формы, сохранив архитектуру снимков `lib`.
  Формы получают экраны от тестового HTTP backend: append полей, замена формы, назад, загрузка и ошибка.
  ID — обычная часть DOM demo-приложения, читаемая конфигурацией, а не специально добавленный locator поля.
- Основной пример — одна полноценная процедура минимум с тремя экранами, а не коллекция отдельных игрушечных страниц.
  На первом экране — один Input, один Select и один ComboBox; на последующих — дополнительные поля и изменение
  состава формы. В тестовом покрытии обязательны combobox с поиском, select, именованная группа полей, группа checkboxes, группа radio
  buttons и inputs разных типов. Использовать Taiga UI; сделать подписи, легенды и выбранные значения видимыми.
  Для групп использовать обычную семантику формы (`fieldset/legend`, ARIA-связи), без tracking-маркеров.
- Внизу каждого экрана формы один ряд кнопок: **«Далее»**, **«Назад»**, **«Неправильный переход»**.
  «Назад» на первом экране disabled; на последующих возвращает предыдущий экран с сохранёнными ответами.
  «Далее» открывает следующий экран, а на последнем — итоговый результат процедуры. Кнопка неправильного перехода
  действительно открывает другой экран с отдельным ID, не предусмотренный правильной веткой сценария.
  С этого экрана можно вернуться к исходному с сохранением ответов. Ошибка определяется по ожидаемому и фактическому
  ID, а не по тексту кнопки и не по hardcoded знанию demo. Изменение DOM и загрузка должны быть наблюдаемыми.
- Рядом с формой показать **карточки распознанных элементов активного экрана**, построенные из снимка библиотеки.
  Это основной визуальный разбор страницы; JSON и DOM-дерево остаются в сворачиваемой диагностике.
  Карточки уже в этом этапе показывают тип, подпись, текущее значение и качество распознавания. Редактирование
  ожиданий и обратной связи подключается в этапе 4; до этого не показывать неработающие поля настроек.
- Taiga UI сохраняет версию текущей ветки. Если целевому приложению нужна Taiga 4, её поддержку проверяем
  отдельными адаптерами/fixtures; работоспособность на Taiga 5 не доказывает совместимость с 4.
- Добавить журнал **состояний и переходов**, базовый снимок экрана, pause/resume/stop и сохранение.
  Не называть строки журнала «клик», если наблюдался только результат изменения состояния.
  На странице явно показывать статус записи, записанные подтверждения полей по экранам и переходы.
  Сохранять запись после stop и reload; из неё строить сценарий для `/learn`, без повторного ручного
  ввода всех ожидаемых значений. Само наблюдение до «Начать запись» не пополняет журнал.
- Ввод остаётся черновиком до focusout. Использовать имеющийся источник focusout как границу подтверждения,
  сохраняя необходимый контекст до batch. Пауза по таймеру не заменяет blur; IME учитывается отдельно.
- На переходе сохранять последнее доказанное состояние уходящего экрана. Если DOM заменён до чтения,
  помечать ответ неполным. Не восстанавливать исчезнувшее значение из догадки или нового экрана.
- Stop завершает запись. Последний экран/переход становится кандидатом завершения; автор меняет его явно.
  Никакого обязательного повторного «признака завершения» без объяснения, что именно он проверяет.

**Приёмка:** через UI можно пройти и записать компактную форму и минимум три экрана в произвольном порядке полей,
вернуться назад с сохранением значений, выполнить неправильный переход, остановить запись и получить JSON.
На первом экране «Назад» не активируется, остальные кнопки имеют реальные результаты. Карточки отражают поля из DOM,
включая добавленные backend, а не заранее перечисленный список demo. Тесты включают blur + немедленную замену DOM
и A → B → C внутри одного batch.
Потерянный промежуточный экран не подменяется доказанным переходом; путь с недостающими данными требует уточнения.

## Этап 4. Редактор сценария по экранам

**Первый срез реализован:** компиляция полной записи, последнее значение поля на экране,
редактирование ожиданий/заданий/сообщений перехода и поля, исключение поля, сохранение/reload.
Группы, произвольное ветвление, удаление/undo событий и отдельный импорт через UI ещё впереди.
Закрытый ComboBox без доказательства выбора по-прежнему блокирует компиляцию неполной записи.

Добавлена память доказанного выбора: если выбранный вариант уже попал в снимок открытого связанного
списка, его можно подтвердить после закрытия и blur. Ввод, изменение значения/связи/контрола и
неполное наблюдение сбрасывают доказательство. Raw snapshots не дополняются историей.
Исследование реального первого выбора Taiga показало отсутствие `aria-selected` перед закрытием;
`ng-reflect-model` не используем. Первый выбор без доказательства остаётся отдельной задачей
контракта интеграции; нельзя автоматически считать совпавший текст выбранным вариантом.

Проверка памяти выбора: production-сборка, 28 unit-тестов и полный прогон 94 браузерных тестов прошли.
Добавлены позитивная запись ранее наблюдавшегося выбора после закрытия списка и отрицательная проверка
повторного ввода; исходный неподтверждённый первый выбор остаётся явным пропуском.


- Список экранов и их ожиданий вместо технического DOM-JSON. Тексты заданий/подсказки,
  ожидаемые значения, необязательные поля, явные зависимости, разрешённые ветки и итоговый экран/результат.
- Превратить карточки распознанных элементов в редактор ожиданий. Карточка, например **«Select · Вид заявки»**,
  должна явно разделять **«Сейчас в форме»**, **«Ожидаемое значение»** и **«Сообщение при другом значении»**.
  Можно принять наблюдаемое значение как ожидаемое, задать другое или исключить элемент из проверки.
  Значение формы обновляется из снимков; авторское ожидание и сообщение не перезаписываются новым scan.
- Редактор соответствует типу контрола: текст для input, типизированное значение для number,
  подтверждённый вариант для select/combobox, boolean для checkbox и один вариант для radio-группы.
  Нельзя выдавать видимую часть dropdown за полный список вариантов или поисковый текст за выбранное значение.
  Неизвестное/недоступное значение явно обозначается и не превращается в пустое ожидаемое значение автоматически.
- Именованные группы показывать контейнером с дочерними карточками; radio-группу — одной карточкой выбора,
  checkbox-группу — карточкой набора с состоянием каждого участника. Понадобится общая проекция групп поверх
  `ControlSnapshot`: группировать по подтверждённым DOM-связям, а не по соседству или именам полей demo.
  Без доказанной связи оставлять отдельные карточки и позволять автору объединить их вручную.
  Вложенность карточек не создаёт дублирующих ожиданий на одни и те же поля.
- Для native radio учитывать общий `name` и владельца формы; одинаковый `name` в разных формах не объединяет
  варианты. Для кнопок карточка показывает название и доступность, а ожидаемый результат задаётся переходом
  экрана: поле «правильное value» к кнопке не применяется. Служебные DOM-узлы внутри Taiga не становятся карточками.
- Карточка показывает принадлежность экрану/группе, состояния disabled/readonly и причину missing/ambiguous.
  Выбор карточки позволяет подсветить соответствующий элемент существующим `DomHighlighter`; при remount
  привязка пересчитывается, устаревшая DOM-ссылка не используется. Карточки принадлежат Angular-админке, не библиотеке.
- Независимые видимые поля выполняются в любом порядке внутри активного экрана.
  Появление дополнительного поля на том же ID расширяет состав, а не автоматически создаёт другой экран.
- Удаление строки записи, исключение поля из проверки, отмена удаления. Пересборка сохраняет авторские правки;
  конфликт после удаления границы/ожидания показывается, экспорт устаревшего сценария запрещён.
- Текстовая обратная связь на совпадение/несовпадение подтверждённого поля и контрольной точки.
  Checkbox-набор оценивается целиком на настроенной наблюдаемой границе, без ошибок на промежуточные галочки.
- Ручной выбор полей набора через защищённый слой с паузой наблюдения; собственные клики выбора не активируют форму.
  Привязка для этого MVP относится к состояниям, а не к ошибочным кликам соседних кнопок.
- Версионированный JSON, строгая validation, понятные ошибки импорта, сохранение после reload.
  Документы из `new` не принимать молча: там иная семантика действий; импорт требует отдельной миграции.

**Приёмка:** сценарий настраивается без JSON; удаление и отмена, сообщения, условия, наборы и экспорт/import
сохраняют смысл. Автор видит, какие значения/переходы проверяются, и чего наблюдатель доказать не может.
В карточке select задаётся правильный вариант и сообщение для другого значения; radio- и checkbox-группы
редактируются без технических ID. Новые снимки меняют текущее значение, сохраняя настройки карточки.

## Этап 5. Прохождение и обратная связь

**Первый срез реализован:** автоматический старт, порядок полей свободный внутри экрана,
проверка после blur, запрет обхода ожиданий переходом, исправления, дедупликация ошибок и Taiga Alerts.
Установленная Taiga UI 5 предоставляет `TuiNotificationService`, наследующий `TuiAlertService`;
он используется в Angular-интеграции. Runtime библиотеки публикует только данные.

Проверка этого среза: production-сборка, 22 unit-теста и полный прогон 92 браузерных тестов прошли.
Новый browser-путь: запись → редактирование сообщения → публикация → ошибка после blur → исправление
→ завершение → новая попытка после reload. Отдельно проверены неправильная ветка и отказ публикации
неполной записи. Гарантии восстановления на всех типах мутаций и числовой benchmark ещё не заявляются.

- Автоматический запуск после загрузки валидного сценария на `/learn`; собственная панель управления
  ученику не нужна. Angular-зона ученика показывает Taiga Alerts/подсказки по событиям headless runtime.
- Ошибка подтверждённого значения или неправильный переход вызывает **Taiga UI Alert** с сообщением
  из настройки поля/перехода. Вызов `TuiAlertService` принадлежит Angular-интеграции ученика;
  библиотека только публикует результат проверки. Не показывать ошибку во время ввода до blur
  или повторно при каждом scan. Loading/unknown/ambiguous не выдавать за неправильный ответ.
- Сопоставлять текущий экран и его поля со сценарием. Смена ID не обходит обязательные ожидания прошлого
  экрана: для перехода нужны ожидаемая ветка и подтверждённое состояние уходящего экрана.
- Правильное → неправильное значение снимает выполненность. Подтверждение input и сообщения — после blur;
  первоначальная оценка предзаполненного состояния сама по себе не рассылает alerts об успешном «действии».
- Checkbox-набор: проверять целиком на доступной границе (например, уход/переход экрана), используя его
  сохранённое состояние. Если нужна проверка по кнопке без видимого изменения, это отдельное расширение.
- Явно отличать ошибочный ответ, неожиданный экран, loading, missing/ambiguous и неполный снимок.
  Проблема наблюдения не является ошибкой ученика; повторные scans не дублируют сообщения.
- На demo отдельно проверить кнопку «Неправильный переход»: неожиданный ID не засчитывает ожидаемый переход,
  показывает настроенное сообщение о переходе и допускает возврат для продолжения правильной ветки.
  Сообщение поля при другом value берётся из его карточки. Для input оно возникает после blur,
  для select/combobox — после blur с доказанным выбором, для radio — при доказанном выборе, для checkbox-набора — на заданной границе проверки.
- Возврат назад, новый экземпляр формы, остановка/уход, повторная тренировка и поздние обновления не
  продолжают старую попытку. Результат считается достигнутым по сценарию, не по длине записи.

**Приёмка:** запись → редактирование → новый документ ученика → другой порядок полей → ошибка → исправление
→ переход → завершение. Отдельно: автозаполнение, асинхронный переход без клика, неожиданный ID и невозможность
прочитать последнее состояние старого экрана. Все различия видны в диагностике, без ложного зачёта.

## Что снимки принципиально не доказывают

- Нажатие конкретной кнопки, если несколько действий приводят к одинаковому состоянию.
- Клик по справке/скачиванию/действию, которое не оставило наблюдаемого состояния.
- Неудачное нажатие «Далее», если экран остался тем же и не появилось различимого результата.
- Кто изменил значение: ученик, Angular-код, браузерное автозаполнение или backend.
- Значения/экраны, появившиеся и исчезнувшие между capture, и содержимое за пределами снимка/лимита.
- Однозначную идентичность двух неразличимых полей или разных состояний с одинаковым ID экрана.

Для таких задач позднее можно добавить узкий источник подтверждений: наблюдаемый результат, существующее
состояние приложения через DI либо конкретное browser event. Универсальную запись кликов сейчас не строим.
Если необходимо «сначала посмотреть справку», состояние справки должно быть наблюдаемым и сохранённым;
просто наличие той же кнопки в двух снимках не доказывает её использование.

Всего **7 этапов**: 5 функциональных, приёмка и затем оптимизация. Первый этап начат:
чтение существующего ID экрана и `ScreenState`, без переноса регистратора `new`.
Каждый этап заканчивается видимым результатом/тестами, обновлением этого плана и отдельным коммитом.
Базовый путь запись → редактор → прохождение реализован; расширенная приёмка и оставшиеся части этапов ещё впереди. Оптимизация остаётся последней.

## Обновление: удаление и отмена в админке

Реализованы удаление строк после завершения записи, отмена в рамках текущей страницы,
сохранение изменённого журнала, пересборка ожиданий с сохранением авторских правок черновика.
Потеря границы экрана блокирует публикацию; общий пропуск наблюдения нельзя скрыть удалением.
Опубликованная тренировка меняется только при явном сохранении. Связь с исходной записью

1. Завершить контракт наблюдения: источник ID из URL/DOM, правила сохранения чувствительных

2. Укрепить сопоставление и semantic diff: новые документы, динамические поля, матрица DOM-мутаций,

3. Доработать редактор: карточки ожиданий, группы и безопасный выбор их состава,

4. Расширить прохождение: оценка наборов на границе, зависимости и допустимые ветки,

## ComboBox: сравнение текста после blur

По согласованному правилу ComboBox записывается и проверяется по видимому тексту после выхода
фокуса. Выбор из списка и ручной ввод одинакового текста равнозначны для тренировки.
Пока фокус внутри поля, новое значение не засчитывается и сообщение об ошибке не появляется.
Карточка показывает подтверждённый текст; отсутствие `aria-selected` больше не создаёт пропуск записи.

Диагностический `choice.selection` по-прежнему описывает только доказанный выбор и может быть unknown.
Учебный формат сохраняет текст как массив из одной строки (пустое поле — пустой массив), как и ранее
сохранённые подписи вариантов. Это не доказательство выбора конкретной опции или её backend ID.
Предыдущие замечания о блокировке первого выбора ComboBox относятся к старому правилу; для текущего
MVP дополнительный источник подтверждения выбора не требуется. Старые строки «не удалось прочитать»
не исправляются автоматически: нужно заново записать значение либо явно удалить ненужную строку.

Проверка нового правила: 34 unit-теста, 12 целевых браузерных тестов и production-сборка прошли.

## Исправление уведомлений при входе на экран

Начальное состояние checkbox/radio больше не вызывает ошибку ученика. Новые поля и remount
получают исходное состояние без уведомлений; повторные снимки не рассылают ошибки.
Последующие изменения проверяются, а обязательные неверные значения по-прежнему блокируют переход.

Проверено: 36 unit-тестов, 4 браузерных сценария тренировки и production-сборка прошли.

## Уже заполненные ответы при входе

Runtime сразу оценивает начальные значения распознанных полей на экране, включая числовую сумму,
Input, Select и ComboBox. Совпавшие значения засчитываются без фокуса и blur. Несовпавшие остаются
невыполненными без уведомлений. Это также действует после возврата с неправильного экрана,
когда приложение создало новые DOM-элементы и восстановило ответы.

Для каждого экземпляра поля сохраняется его первое прочитанное состояние. Последующие изменения
Input/Number/Select/ComboBox заменяют это исходное значение только после blur. Неоднозначные цели,
скрытые значения и неизвестный выбор Select не превращаются в правильные ответы. Новый шаг сбрасывает
исходные состояния предыдущего. Поздно появившееся поле получает своё начальное состояние при распознавании.
Это правило прохождения; журнал администратора по-прежнему записывает подтверждения после blur.

## Начальная картина checkbox и radio в записи

При начале записи, входе на новый экран и появлении нового checkbox/radio регистратор сразу
сохраняет его состояние, включая `false`. Последующие изменения добавляются в журнал;
компилятор оставляет последнее значение каждого поля в рамках посещения экрана. Каждый radio-вариант
сейчас представляет отдельное boolean-ожидание: выбранный — true, остальные — false.
Повторный снимок без изменения значения и изменение только disabled не добавляют строк.

Ученик должен воспроизвести итоговую картину. Поле с ожидаемым false обязательно должно оставаться
выключенным; переключение на true вызывает ошибку. Исключение поля из проверки — отдельная настройка,
false не означает «не проверять». Старые записи автоматически не дополняются отсутствовавшими полями.
