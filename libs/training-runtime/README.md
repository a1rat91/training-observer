# Runtime: Angular-сеанс тренировки и проверка сценария

`@training-observer/runtime` предоставляет `TrainingSession` для Angular и алгоритмы проверки готового сценария. Сеанс
управляет попыткой и наблюдением через общий `ObservationConnection` из core. `ScenarioRuntime` получает наблюдаемые
состояния и возвращает прогресс и новые сообщения; сам движок не читает DOM. Пакет не записывает сценарии, не читает
storage и не показывает Taiga Alerts. UI-интеграция demo — `projects/demo/src/app/pages/learn`.

Переходы сравниваются по общему `ScreenState.key`. Имена DOM-тегов и атрибутов приложения, включая `block-id`,
интерпретируют адаптеры приложения; движок прохождения их не читает.

## Структура

| Модуль                        | Ответственность                                                         |
| ----------------------------- | ----------------------------------------------------------------------- |
| `scenario-runtime.ts`         | координация готовности, переходов и результата                          |
| `field-evaluator.ts`          | сопоставление обязательных полей, выбор исходного/blur значения, оценка |
| `feedback-tracker.ts`         | память обратной связи и подавление повторов                             |
| `control-matcher.ts`          | детерминированный поиск цели по descriptor                              |
| `training-progress.ts`        | выходная модель обновления                                              |
| `training-session.service.ts` | Angular-владелец попытки и доставка наблюдаемых кадров                  |
| `provide-training-session.ts` | регистрация Angular-сеанса                                              |

Публичны TrainingSession, provideTrainingSession, ScenarioRuntime, TrainingProgress и matchControl/ControlMatch.
Внутренние evaluator и tracker — обычные классы композиции алгоритма. Начните чтение движка с update → tryTransition →
FieldEvaluator; его Angular-владелец описан ниже.

## Angular API

```ts
import {inject} from '@angular/core';
import {provideTrainingSession, TrainingSession} from '@training-observer/runtime';

// providers компонента: [provideTrainingSession({root: '#main-area'})]
const session = inject(TrainingSession);
session.feedback$.subscribe((feedback) => showMessage(feedback.message, feedback.kind));
session.start(validatedScenario);
// session.progress(), session.screen(), session.error()
```

Передавайте сценарий, проверенный `parseScenario` из contracts. `start(scenario)` создаёт новую попытку, сбрасывает
подтверждения прежней попытки и получает исходное состояние после рендера. `stop()` отменяет попытку и останавливает
наблюдение. DestroyRef владельца освобождает ресурсы и завершает `feedback$`; подписку UI также ограничивайте своим
DestroyRef. Настройки `root`, `observation` и необязательный `screen` определяют область; без явного `screen` работают
зарегистрированные адаптеры. Сеанс записи и сеанс тренировки одного компонента остаются независимыми.

## Алгоритм обновления

1. Неготовый экран даёт waiting/blocked. Проблема наблюдения не считается ошибкой ответа.
2. При другом ключе проверить уходящий экран, включая последнее blur-подтверждение.
3. Перейти только на ожидаемый следующий экран, если обязательные поля прошлого выполнены.
4. При входе запомнить baseline подтверждений и исходные значения каждого экземпляра поля.
5. Сопоставить и оценить поля, затем отдать только новые сообщения.
6. Если последний шаг выполнен, вернуть complete. Наблюдение автоматически не останавливается.

Поля одного экрана заполняются в любом порядке. Правильные предзаполненные ответы, включая сумму, засчитываются сразу.
Неправильные исходные значения остаются невыполненными без сообщения. Последующие Input/Number/Select/ComboBox
проверяются после blur. Checkbox/radio проверяются по изменению. Remount/возврат использует новое исходное состояние.
Ожидаемый false проверяется наравне с true.

## Сопоставление

Тип обязателен. Score: стабильный ID 100, label 80, name 40, placeholder 30, контекст 20. Минимум 80, отрыв от второго
кандидата минимум 30. Генерируемые ID не дают сильного балла. Missing/ambiguous блокируют оценку. Одному контролу нельзя
назначить два обязательных ожидания. Ответ и геометрия не входят в score. Это осторожная эвристика, не гарантия
восстановления любой разметки.

При совпавшем стабильном ID две разные непустые подписи считаются противоречием: кандидат получает нулевую оценку. Это
защищает от передачи старого ID другому полю. Настоящее переименование тоже требует уточнения, если не осталось другого
подходящего кандидата. Измерение и границы: [отчёт](../../docs/reference/matching-resilience.md).

## Прогресс и уведомления

TrainingProgress содержит status, номер/число шагов, выполненные/обязательные поля, issue и feedback. Feedback — новые
сообщения конкретного update. Повторять его на последующих рендерах нельзя. Исправление очищает память ошибки, чтобы
новое неверное изменение снова сообщалось. Правильное → неправильное снимает выполненность; optional исключает поле из
проверки. Taiga вызывает Angular-интеграция, runtime возвращает объекты
`TrainingFeedback {kind: FeedbackKind; message: string}`. `FeedbackKind` экспортирует `Error` и `Success`: UI выбирает
отрицательное или положительное оформление. Это изменение API относительно массива строк: потребителям нужно читать
`.message` и `.kind`.

`message` поля задаёт ошибку, необязательное `successMessage` — успех. Пустой текст отключает только уведомление.
Правильное исходное значение засчитывается молча. Сообщение успеха возникает после подтверждения blur либо изменения
checkbox/radio, как и сообщение ошибки. Память учитывает вид результата и значение: одинаковые подтверждённые ответы не
повторяют сообщение; ошибка → исправление → новая ошибка снова дают обратную связь. Последний blur, пришедший вместе с
переходом на следующий экран, обрабатывается до смены шага.

Временное missing/ambiguous или нечитаемое значение сохраняет память уже выданного сообщения: восстановление поля с тем
же подтверждённым ответом не повторяет уведомление. Прочитанное новое исходное значение после remount остаётся тихим;
последующее подтверждённое изменение снова может выдать сообщение.

## Жизненный цикл и ограничения

`TrainingSession` владеет попыткой, наблюдением и доставкой обратной связи. Ниже — правила непосредственного
использования `ScenarioRuntime` внутри своей интеграции.

Создайте новый runtime на новую попытку, передав результат parseScenario. Конструктор копирует документ. Вызывайте
update при публикациях screen и confirmedControls. Не переиспользуйте подтверждения старого сеанса. Runtime не
восстанавливает неувиденные промежуточные состояния и не различает изменение человеком и backend. Порядок экранов
линейный; общие ветки, группы и произвольные зависимости остаются в плане MVP.

Два соседних шага с одинаковым ключом экрана отклоняются явной ошибкой при импорте и в конструкторе runtime, включая
прямую передачу typed-сценария. Наблюдаемая смена ключа не различает такие посещения; возврат A → B → A поддерживается.

## Проверка

`npx nx build training-runtime`; unit tests — `tests/unit/scenario.test.js`, browser tests — `tests/training.spec.ts`.
`npm run lint` запрещает зависимость runtime → recording. Angular-сеанс и публичный package import проверяются в TestBed
и независимом Angular consumer.
